# MediaForge 生产部署机器申请

> 申请日期：2026-07-13  
> 目标规模：公司内部 50 人使用  
> 部署范围：MediaForge、Nginx、PostgreSQL、MinIO 同机部署  
> 评估依据：`scripts/mediaforge-capacity-report.txt`（2026-07-13 17:34 采集）

## 1. 申请结论

当前生产机器可以维持采样时的低负载运行，但**不建议认定为能够稳定承载 50 人使用的生产配置**。主要问题不是采样时 CPU 已经跑满，而是内存、Swap、磁盘容量和服务隔离均没有足够的峰值余量；同时本次仅有 10 秒低负载采样，没有 50 人并发压测或历史监控数据可以证明现有机器满足目标。

建议申请一台专用于 MediaForge 的生产虚拟机，配置如下：

| 项目 | 申请配置 |
| --- | --- |
| CPU | **16 vCPU**，现代 x86_64 处理器，建议主频不低于 2.8 GHz，非突发型、避免高比例超分 |
| 内存 | **32 GB**，支持后续扩容到 64 GB |
| 系统盘 | **200 GB SSD/NVMe** |
| 数据盘 | **2 × 1.92 TB 企业级 NVMe/SSD，RAID 1**，可用容量约 1.92 TB；若云盘已有多副本保障，可申请单块 2 TB 高性能云盘 |
| 磁盘性能 | 建议不低于 10,000 IOPS、300 MB/s，要求提供稳定性能而非突发额度 |
| 网络 | **1 Gbps** 对称内网带宽，建议支持后续升级到 2.5 Gbps；与外部 AI 服务/ComfyUI 低时延互通 |
| 操作系统 | Debian 12 或 Ubuntu 24.04 LTS，x86_64 |
| GPU | **不需要**；本申请不包含 ComfyUI/本地模型推理 |
| 备份 | 独立于本机的数据备份空间不少于 2 TB，保留 PostgreSQL 与 MinIO 定期备份 |

这是一套面向 50 人、保留合理增长余量的配置，不包含模型推理算力。如果后续要把 ComfyUI 或其他本地 AI 模型迁入该机器，需要单独评估 GPU、显存、模型并发和额外内存，不能复用本申请结论。

## 2. 容量设计假设

本申请按以下业务边界估算：

- 最多 50 人保持登录或 WebSocket 在线。
- 普通页面/API 峰值并发约 15 个请求。
- 同时进行 5 至 10 路图片或视频上传、下载、缩略图/封面处理。
- AI 生成通过外部 API 或独立 ComfyUI 完成，本机只承担请求转发、结果保存和媒体预处理。
- PostgreSQL、MinIO 与 MediaForge 部署在同一台机器，但不再混跑 Jenkins、MySQL、机器人网关等无关服务。
- 每用户默认存储配额保持当前代码中的 10 GiB，输入、上传和输出文件默认保留 30 天。

如果实际目标是“50 人同时上传大视频”或“50 个本地媒体处理任务并行”，应在压测后升级为 32 vCPU、64 GB 内存和更高网络带宽。

## 3. 当前机器实测情况

### 3.1 资源概况

| 指标 | 当前实测 | 判断 |
| --- | --- | --- |
| CPU | 8 vCPU，KVM 通用兼容 CPU，约 2.3 GHz | 低负载时充足，但宿主型号和现代指令集能力不可见，无法证明峰值能力 |
| CPU 负载 | load average 约 0.08；10 秒采样 CPU 空闲 97% 至 99% | 采样期间几乎无业务压力，不能外推至 50 人 |
| 内存 | 总计 7.8 GiB，使用 3.1 GiB，可用 4.6 GiB | 当前尚未耗尽，但容量过小、缺少并发处理余量 |
| Swap | 约 974 MiB，已使用约 974 MiB | 本次 `si/so=0`，没有正在抖动，但满占用表明出现过内存压力或长期冷页换出 |
| 本地磁盘 | 502 GiB，已用 261 GiB，可用 216 GiB | 无法覆盖 50 人默认 500 GiB 的总配额 |
| 磁盘类型 | 系统报告 `ROTA=1` 的 QEMU 磁盘 | 不应作为 PostgreSQL 和 MinIO 的高性能生产盘 |
| 磁盘 IO | 低负载采样 `await` 基本低于 1 ms、利用率接近 0 | 当前无 IO 压力，不能证明并发媒体读写能力 |
| 网络 | 采集时 74 个 TCP 已建立连接，3000 端口约 10 个连接 | 单次连接数不等于在线人数，但不足以证明 50 人场景，且报告缺少网卡速率 |

### 3.2 MediaForge 进程

MediaForge 当前通过单个 `python3 main.py` 进程运行：

- 常驻内存约 453 MiB。
- 虚拟内存峰值约 3.27 GiB。
- 已有约 22 MiB 内存被换出到 Swap。
- 软限制仅为 1,024 个打开文件。
- 采集期间平均 CPU 很低，说明这次采样不是业务高峰。

50 个 WebSocket 本身资源消耗不高，真正的峰值来自图片解码、缩略图生成、视频封面提取、大文件上传转发以及 MinIO 读写。这些操作会产生明显的瞬时内存和磁盘吞吐，不能只按当前 453 MiB 的空闲常驻内存进行配置。

### 3.3 PostgreSQL

PostgreSQL 15 当前状态正常：

- `max_connections=100`，采集时共 9 个连接，其中 1 个 active。
- `shared_buffers` 约 160 MiB，`work_mem=4 MiB`。
- 最大数据库 `ai_portal` 仅约 11 MiB。
- 缓存命中率约 99.99%，没有临时文件写入。

因此 PostgreSQL **当前不是性能瓶颈**。不过现有配置偏向 8 GB 小内存机器，迁移至 32 GB 后应重新设置缓存参数，并监控连接池和慢查询。

### 3.4 MinIO 与存储

用户说明 MinIO 与应用同机，但报告中：

- 没有发现名为 `minio` 的进程。
- Docker 中也没有 MinIO 容器。
- 没有安装 `mc`，未取得 Bucket 实际容量和吞吐。
- 机器挂载了一个约 5 TB 的 CIFS 共享目录，但报告无法证明它是否是 MinIO 数据目录。

因此，本次不能验证当前 MinIO 的部署位置和性能。迁移前必须确认 `MINIO_ENDPOINT` 指向的实例、数据目录和备份方式。若 MinIO 实际位于远端共享存储，本申请中的本地数据盘可按真实存储架构重新核减，但不能在未确认前按“已有 5 TB 空间”计算。

### 3.5 资源混跑

当前机器除了 MediaForge、PostgreSQL 和 Nginx，还运行了：

- Jenkins Java 进程，常驻内存约 1.3 GiB，启动参数最大堆 2 GiB。
- 另一套 Uvicorn 应用，常驻内存约 175 MiB。
- 多个 Python/Lark 网关进程。
- MySQL、两个 Redis 服务及其他 Docker 服务。

这些服务会与 MediaForge 争用内存、页缓存、磁盘和网络，且 Jenkins 等进程的峰值与 MediaForge 业务峰值不可预测。50 人生产环境应使用专用机器或至少设置严格的容器资源上限。

## 4. 为什么当前配置不能作为 50 人生产配置

1. **内存余量不足。** 总内存只有 7.8 GiB，Swap 已用满，MediaForge 和多个后台进程也已经存在换出页。采样时没有持续换入换出，但发生并发图片/视频处理时，仍可能出现延迟突增或 OOM。
2. **本地容量不满足默认配额。** 50 人乘以默认 10 GiB 配额即 500 GiB，现有本地盘仅剩 216 GiB，还未计入系统、Docker、数据库、临时文件、缩略图和安全余量。
3. **机器并非专用。** Jenkins、MySQL、Redis、其他 Python 服务共同占用资源，无法为 MediaForge 提供可预测的服务等级。
4. **磁盘性能缺乏保障。** 当前为虚拟旋转盘标识，低负载延迟虽低，但没有并发写入压测，也没有明确 IOPS/吞吐保障。
5. **采样不代表高峰。** 报告只有 10 秒数据，CPU 几乎完全空闲，应用端口约 10 个连接，缺少 50 人压力下的 p95 延迟和错误率。
6. **MinIO 情况未核实。** 当前报告没有发现 MinIO 服务，无法确认媒体文件实际落盘位置、冗余和吞吐。

综合判断：**当前机器适合继续承载现有轻负载，但不具备验收为 50 人生产环境所需的资源余量和证据。建议批准新机器。**

## 5. 推荐配置的计算依据

### 5.1 CPU

16 vCPU 用于分担以下工作：

- MediaForge 异步请求与线程任务。
- Pillow 图片解码、缩放与编码。
- FFmpeg 视频封面提取。
- MinIO 校验、网络传输和对象读写。
- PostgreSQL 查询、清理任务和检查点。
- Nginx TLS 与大文件代理。

当前应用存在进程内 WebSocket、队列和锁，不能在没有改造共享状态的情况下简单启动多个 Uvicorn worker。16 vCPU 的价值主要是保证数据库、对象存储、媒体工具与应用进程互不挤占，并为后续服务拆分保留空间，而不是直接将当前 Python 进程扩成 16 倍吞吐。

### 5.2 内存

建议 32 GB 的规划如下：

| 用途 | 规划内存 |
| --- | ---: |
| 操作系统、Nginx、基础服务 | 2 至 3 GB |
| MediaForge 及并发媒体处理 | 6 至 10 GB |
| PostgreSQL 与连接 | 4 至 6 GB |
| MinIO | 4 至 6 GB |
| 文件系统页缓存和峰值余量 | 8 GB 以上 |

32 GB 可以覆盖 50 人中等并发，并避免依赖 Swap 维持运行。若要继续混跑 Jenkins/MySQL 等服务，应直接申请 64 GB；更推荐将这些无关服务留在原机器。

### 5.3 存储

当前默认配额上限为：

```text
50 人 × 10 GiB/人 = 500 GiB
```

再计入操作系统、应用、数据库、Docker、临时处理空间、缩略图、日志、升级空间以及至少 30% 的空闲容量，建议生产数据盘可用容量不低于 1 TB。申请约 1.92 TB 可用容量，可避免短期扩盘，并能覆盖业务增长和迁移期间的双份数据。

推荐使用 RAID 1 或云盘多副本能力，原因是 PostgreSQL 与 MinIO 同机部署后，单块数据盘故障会同时影响文件元数据和媒体对象。RAID 不能替代备份，备份必须放在独立设备或远端存储。

## 6. 配置档位

| 档位 | CPU | 内存 | 数据盘可用容量 | 适用范围 |
| --- | ---: | ---: | ---: | --- |
| 最低可接受 | 8 个现代 vCPU | 16 GB | 1 TB NVMe/SSD | 50 人在线、低并发，最多约 3 路重媒体操作；必须专机部署 |
| **推荐申请** | **16 vCPU** | **32 GB** | **约 1.92 TB NVMe/SSD** | 50 人在线、中等并发、5 至 10 路上传/媒体处理，保留增长余量 |

不建议申请低于 16 GB 内存或使用机械盘/无性能保障的普通云盘。

## 7. 部署要求

新机器交付时应同时满足以下要求，否则硬件升级不能完整解决稳定性问题：

1. 只部署 MediaForge、Nginx、PostgreSQL、MinIO 和必要监控，不部署 Jenkins、MySQL 或其他业务应用。
2. PostgreSQL 数据目录、MinIO 数据目录放在高性能数据盘；系统盘只放系统、应用和日志。
3. PostgreSQL 和 MinIO 仅监听业务内网或本机地址，不直接暴露到非可信网络。
4. MediaForge 使用 systemd 或容器托管，配置自动重启、启动依赖和日志轮转，不再依赖 tmux 前台进程。
5. 将 MediaForge 进程打开文件数软限制提高至至少 65,535，并同步检查 Nginx、PostgreSQL、MinIO 限制。
6. 配置 PostgreSQL 每日备份和恢复演练；MinIO 配置版本/生命周期策略及异机备份。
7. 配置 CPU、内存、Swap、磁盘容量、磁盘延迟、HTTP p95、错误率、PostgreSQL 连接数和 MinIO 容量告警。
8. 当前 WebSocket、队列和部分锁保存在进程内。在引入 Redis 等共享状态机制之前，不要直接增加多个 Uvicorn worker，否则可能出现连接广播和任务状态不一致。

## 8. 上线验收标准

迁移后应执行至少 30 分钟的模拟高峰测试，覆盖 50 个 WebSocket 在线连接、15 个普通并发请求以及 5 至 10 路代表性媒体上传/处理。建议验收指标如下：

| 指标 | 验收目标 |
| --- | --- |
| CPU | 持续平均低于 70%，无长期单核 100% |
| 内存 | 持续低于 80%，测试期间无 OOM，`si/so` 持续为 0 |
| 磁盘 | 数据盘持续利用率低于 70%，业务高峰平均 `await` 低于 20 ms |
| 容量 | 数据盘至少保留 30% 空间，并配置 80%/90% 分级告警 |
| 网络 | 无持续丢包；高峰带宽低于链路能力的 70% |
| HTTP | 不含外部 AI 生成耗时的核心 API p95 小于 2 秒 |
| 稳定性 | 5xx/超时错误率低于 1%，WebSocket 无批量异常断开 |
| PostgreSQL | 连接数低于上限的 70%，无持续锁等待和慢查询堆积 |

若未完成上述压测，机器规格只能视为容量估算，不能视为已经证明可承载所有 50 人同时进行重媒体操作。

## 9. 申请说明摘要

MediaForge 是公司内部 AI 图片/视频创作与资产管理平台，生产环境同时依赖 FastAPI/WebSocket、PostgreSQL 和 MinIO。现有机器仅有 8 vCPU、7.8 GiB 内存和约 216 GiB 本地剩余空间，Swap 已接近 100% 使用，并与 Jenkins、MySQL、Redis 及多个其他服务混跑。虽然本次低负载采样 CPU 空闲，但现有内存、存储容量和资源隔离无法覆盖 50 人使用时的媒体上传、转码、缩略图生成及对象存储峰值。

为保证 50 人规模下的稳定性、数据安全和后续扩展，申请一台专用生产机器：**16 vCPU、32 GB 内存、200 GB 系统盘、约 1.92 TB 可用高性能数据盘、1 Gbps 内网带宽**，并配套独立备份空间。该机器不承担本地 AI 模型推理，无需 GPU。
