# 文件系统删除、过期、清理逻辑分析

本文梳理 MediaForge 当前与文件系统删除、过期、清理相关的实现，重点覆盖：

- 统一存储生命周期清理
- 业务层软删除与回收站
- 用户操作触发的即时删除
- 临时文件清理
- 当前实现中的不一致和潜在残留点

## 1. 总体结论

项目当前的文件删除 / 过期 / 清理逻辑主要分成 3 层：

1. 统一存储生命周期清理
   由 `app/services/storage.py` 负责，面向 MinIO + PostgreSQL 元数据体系，支持保留期和后台循环清理。
2. 业务层软删除 / 回收站
   目前最明确的是画布回收站，删除后先写 `deleted_at`，再在后续访问时做延迟物理删除。
3. 用户操作触发的即时删除
   包括历史记录、本地上传素材、对话、工作流等，通常由 API 直接删除对应文件或远端对象。

此外，项目中还有不少临时文件清理逻辑，主要体现在图像处理、视频抽帧、缩略图生成等函数的 `finally` 块中。

## 2. 统一存储生命周期清理

### 2.1 配置项

配置位于 [app/config.py](/home/zhang/workspace/MediaForge/app/config.py:48)：

- `STORAGE_CLEANUP_ENABLED`
- `STORAGE_CLEANUP_INTERVAL_SECONDS`
- `STORAGE_CLEANUP_BATCH_SIZE`
- `STORAGE_METADATA_PURGE_ENABLED`
- `STORAGE_METADATA_PURGE_RETENTION_DAYS`
- `STORAGE_INPUT_RETENTION_DAYS`
- `STORAGE_UPLOAD_RETENTION_DAYS`
- `STORAGE_OUTPUT_RETENTION_DAYS`
- `STORAGE_TEMP_RETENTION_DAYS`
- `STORAGE_CACHE_DIR`

当前默认值：

- 每 1 小时清理一次
- 每批最多扫描 500 条
- 已删除元数据默认保留 30 天后再尝试硬删除
- `input / uploads / output` 默认保留 30 天
- `temp` 默认保留 3 天

对应代码位置：

### 2.3 过期判定规则

核心逻辑在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:255) 的 `cleanup_reason_for_entry()`。

判定规则如下：

1. `library` 类别永不过期。
2. 如果有 `expires_at` 且已到期，则判定为 `expired`。
3. 否则读取该类别的 retention days。
4. 用 `last_accessed_at` 作为优先活动时间；如果没有访问时间，则回退到 `created_at`。
5. 若活动时间早于 retention 截止点，则判定为 `<category>_retention`。

这意味着统一存储里的文件不是单纯按创建时间清理，而是按“最后访问时间优先”的策略清理。

### 2.4 候选文件扫描

候选集查询逻辑在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:283) 的 `_cleanup_candidates()`。

查询条件：

- `deleted_at IS NULL`
- `status <> 'deleted'`
- `category <> 'library'`
- 满足以下之一：
  - `expires_at <= now`
  - `input/uploads/output/temp` 超过各自 retention 截止时间

排序逻辑：

- 按 `COALESCE(expires_at, created_at)` 升序

说明：

- 实际上是优先清理“更早过期 / 更早创建”的对象。
- `library` 类别会被显式排除在后台生命周期清理之外。

### 2.5 真正执行删除

执行逻辑在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:331) 的 `run_storage_cleanup_once()`。

每条候选记录的处理顺序：

1. 再次调用 `cleanup_reason_for_entry()` 做保护性判定。
2. 调用 `_mark_file_deleted()`，将数据库行更新为：
   - `status = 'deleted'`
   - `deleted_at = now`
   - `updated_at = now`
3. 尝试删除 MinIO 对象：
   - 主对象
   - 图片缩略图 `media_thumb_object_key(...)`
   - 视频海报 `media_poster_object_key(...)`
4. 删除本地缓存文件：
   - `cached_media_path(entry)`
   - 若该路径存在则执行 `os.remove(...)`

因此，统一存储的生命周期清理本质上是：

- 元数据先标记删除
- 再尝试删远端主对象和派生对象
- 再删本地缓存

对应删除辅助逻辑位于：

- [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:1133)
- [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:1145)

### 2.6 后台循环

循环逻辑在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:406)：

- 每轮执行 `run_storage_cleanup_once()`
- 每轮执行 `run_storage_metadata_purge_once()`
- 捕获异常后忽略，避免后台任务退出
- 休眠 `max(60, STORAGE_CLEANUP_INTERVAL_SECONDS)`

说明：

- 这是一种“尽量持续运行”的保守实现。
- 任何单次异常不会中断后续清理轮次。

### 2.7 已删除元数据的延迟硬删除

当前统一存储已经实现“两阶段删除”。

第一阶段：

- 业务删除或生命周期清理时，先把 `files` 表记录标记为软删除：
  - `status = 'deleted'`
  - `deleted_at = now`

第二阶段：

- 后台循环执行 `run_storage_metadata_purge_once()`
- 仅对 `deleted_at` 早于保留窗口的记录尝试硬删除
- 默认保留窗口由 `STORAGE_METADATA_PURGE_RETENTION_DAYS` 控制，默认 30 天

关键逻辑位于：

- [app/config.py](/home/zhang/workspace/MediaForge/app/config.py:69)
- [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:333)
- [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:353)
- [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:388)

硬删除条件：

1. 元数据已被软删除
2. `deleted_at` 早于 purge 保留窗口
3. 主对象和派生对象都已不存在

只有满足以上条件，才会真正执行：

- `DELETE FROM files WHERE id = %s`

这样做的目的：

- 保留近期删除记录，便于审计、排障和补偿
- 避免对象存储删除失败后，元数据过早丢失
- 防止 `files` 表长期只增不减

### 2.8 访问会刷新存活时间

访问时间刷新逻辑在：

- [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:1066)
- [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:1078)

`materialize_media_url()` 在命中缓存或从对象存储拉取文件后，都会调用 `_touch_access(file_id)`，更新：

- `last_accessed_at`
- `updated_at`

这意味着：

- 被频繁预览、下载的对象会不断续命
- 生命周期清理偏向“最近未被访问”的对象，而不是“创建最早”的对象

### 2.9 temp 类别的显式过期时间

在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:1219) 的 `save_compat_media_bytes()` 中：

- 若 `category == "temp"` 且 `STORAGE_TEMP_RETENTION_DAYS > 0`
- 会直接写入 `expires_at = now + retention`

因此 `temp` 类别既受 retention 控制，也能通过 `expires_at` 直接进入过期清理路径。

### 2.10 相关测试

测试文件为 [tests/test_storage_lifecycle.py](/home/zhang/workspace/MediaForge/tests/test_storage_lifecycle.py:1)。

已覆盖的点包括：

- 配额超限触发异常
- `library` 类别不参与生命周期清理
- `last_accessed_at` 优先于 `created_at`
- 清理时会：
  - 标记删除
  - 删除主对象和派生对象
  - 删除缓存
- 显式媒体删除时会删除主对象和派生对象
- 延迟硬删除只会在对象已不存在时删除 PostgreSQL 元数据

## 3. 业务层软删除与回收站

物理删除接口在 [app/routers/canvases.py](/home/zhang/workspace/MediaForge/app/routers/canvases.py:331)。

逻辑非常直接：

- 计算画布文件路径
- 若文件存在则 `os.remove(path)`

### 3.5 自动清理回收站

自动清理函数在 [app/routers/canvases.py](/home/zhang/workspace/MediaForge/app/routers/canvases.py:172) 的 `cleanup_expired_canvas_trash()`。

逻辑如下：

1. 计算截止时间 `now_ms() - CANVAS_TRASH_RETENTION_MS`
2. 遍历当前用户画布目录中的所有 `.json`
3. 读取每个画布文件
4. 若存在 `deleted_at` 且早于截止时间，则 `os.remove(path)`

### 3.6 自动清理的触发方式

`cleanup_expired_canvas_trash()` 不是后台定时任务，而是在列举画布时触发：

- [app/routers/canvases.py](/home/zhang/workspace/MediaForge/app/routers/canvases.py:189)

`iter_canvas_records()` 每次执行时都会先调用一次回收站清理。

这意味着：

- 如果用户长期不访问画布列表，过期回收站文件不会主动被后台清掉
- 它属于“访问时顺手清理”，而不是“定时主动清理”

## 4. 用户操作触发的即时删除

### 4.1 历史记录删除

路由在 [app/routers/history.py](/home/zhang/workspace/MediaForge/app/routers/history.py:66)。

删除流程：

1. 打开当前用户历史文件
2. 根据 `timestamp` 定位要删的记录
3. 将记录从历史 JSON 中移除并写回
4. 调用 `delete_history_files(target_record)`
5. 遍历历史里的图片 URL，若能解析到本地路径，则再次尝试 `os.remove(file_path)`

其中 `delete_history_files()` 位于 [app/services/history.py](/home/zhang/workspace/MediaForge/app/services/history.py:57)，会对每个媒体引用调用：

- `remove_media_url(url, delete_remote=True)`

所以历史记录删除可能同时触发：

- 元数据标记删除
- 远端对象删除
- 本地缓存删除
- 本地输出文件删除

### 4.2 本地上传素材删除

路由在 [app/routers/local_assets.py](/home/zhang/workspace/MediaForge/app/routers/local_assets.py:265)。

分两种情况：

1. 启用统一存储
   - 根据 basename 找到 `uploads` 类媒体
   - 调用 `remove_media_url(..., delete_remote=True)`
2. 未启用统一存储
   - 先尝试 `remove_media_url(...)`
   - 若未命中，再直接删除 `assets/uploads/<name>`

### 4.3 统一媒体删除封装

统一封装在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:998) 的 `remove_media_url()`。

其行为与后台生命周期清理类似：

1. 查找媒体记录
2. 若启用元数据库，则更新：
   - `status = 'deleted'`
   - `deleted_at = now`
   - `updated_at = now`
3. 如果 `delete_remote=True`，则尝试删除远端对象
   - 主对象
   - 缩略图对象
   - 视频海报对象
4. 删除本地缓存文件

说明：

- 它本身是“删除媒体记录”的核心复用点
- 多个上层路由都依赖它

### 4.4 对话删除

路由在 [app/routers/conversations.py](/home/zhang/workspace/MediaForge/app/routers/conversations.py:140)。

逻辑：

这属于纯本地文件的即时物理删除，没有软删除层。

### 4.5 工作流删除

路由在 [app/routers/workflows.py](/home/zhang/workspace/MediaForge/app/routers/workflows.py:137)。

逻辑：

### 4.6 资产库的“删除”不是删底层媒体

在 [app/routers/assets.py](/home/zhang/workspace/MediaForge/app/routers/assets.py:76) 及后续路由中，资产库项目删除、本地分类删除、批量删除等，主要是在资产库 JSON 结构中移除条目。

现阶段这类删除通常是：

- 删资产库记录
- 不直接删底层源文件或对象存储文件

这说明资产库更像“引用管理层”，不是底层媒体的生命周期所有者。

## 6. 当前实现中的值得注意的问题

### 6.1 画布回收站显示值与真实保留期不一致

真实配置：

- [app/config.py](/home/zhang/workspace/MediaForge/app/config.py:48)
- `CANVAS_TRASH_RETENTION_MS = 7 天`

但回收站接口返回：

- [app/routers/canvases.py](/home/zhang/workspace/MediaForge/app/routers/canvases.py:228)
- `retention_days: 30`

这两个值不一致，会导致前端或用户认知与实际清理行为不一致。

### 6.2 画布回收站依赖“访问时清理”

画布回收站不是后台定时器，而是在列举接口里清理。结果是：

- 没人访问画布列表，就没人触发过期回收
- 过期文件可能长期滞留在用户目录中

如果希望画布回收站具备更稳定的空间回收能力，应该考虑：

- 增加后台周期清理
- 或把画布回收站统一纳入一个定时 housekeeping 任务

### 6.3 历史删除路径存在重复删除尝试

历史删除流程会：

1. 调用 `delete_history_files()`，内部可能已删除远端对象 / 缓存
2. 随后再次对 `output_file_from_url()` 解析到的本地文件做 `os.remove`

这未必是 bug，但说明该路径存在：

- 统一存储删除
- 本地输出删除

两层并行尝试，后续若继续统一存储化，需要重新梳理职责边界。

## 7. 建议的后续梳理方向

如果要继续优化这一块，建议优先处理以下问题：

1. 统一“展示保留期”和“真实保留期”
   修正画布回收站接口中的 `retention_days`。
2. 区分“引用删除”和“底层文件删除”
   尤其是资产库、历史记录、画布内媒体引用，避免多处重复承担底层删除职责。
3. 给本地 JSON 型数据增加统一 housekeeping
   包括画布回收站、旧临时文件、孤儿缓存等。
