# 业务元数据系统方案

> 日期：2026-07-08
> 适用范围：MediaForge 当前架构演进规划

## 一、背景

当前 MediaForge 的文件存储主线已经逐步收口到下面这套模型：

- 二进制文件放 `MinIO`
- 文件身份统一收口到 `files` 表
- 业务侧统一用 `file_id` 引用媒体文件

但用户业务数据本身，很多还保留在本地 JSON：

- `data/users/<user_id>/history.json`
- `data/users/<user_id>/asset_library.json`
- `data/users/<user_id>/conversations/*.json`
- `data/users/<user_id>/canvases/*.json`

这些文件本质上已经不是“文件系统问题”，而是“业务元数据存储问题”。

如果继续长期保留本地 JSON 作为主存储，会有几个明显问题：

- 多实例部署时一致性差
- 写入中断容易留下半成品
- 不方便做分页、筛选、检索、统计
- 不方便做事务和引用约束
- 文件清理、配额、误删保护只能做半套

所以这部分应该单独抽象成一个“业务元数据系统”。

## 二、目标

业务元数据系统的目标不是替代文件存储，而是承接“围绕文件产生的业务对象”。

目标定义如下：

- 用户历史、资产库、对话、智能画布不再依赖本地 JSON 作为主存储
- 业务对象和文件对象通过 `file_id` 建立稳定关系
- 支持查询、分页、筛选、统计、审计
- 支持事务写入和引用一致性校验
- 支持后续多实例部署
- 为后续清理、配额、归档、导出打基础

## 三、系统边界

这套系统要和“文件存储系统”明确分层。

### 3.1 文件存储系统负责什么

- MinIO bucket / object
- 本地缓存与临时文件
- `files` 表
- `file_id`
- 上传、下载、预签名 URL
- 配额和物理清理

### 3.2 业务元数据系统负责什么

- `history`
- `asset_library`
- `conversations`
- `smart_canvases`
- 这些对象内部对媒体文件的引用关系

### 3.3 两者的关系

关系很简单：

- 文件存储系统负责“文件本身”
- 业务元数据系统负责“谁在用这些文件”

也就是说：

- 文件系统是底座
- 业务元数据系统是上层业务数据模型

## 四、总体方案

总体方案建议定成下面这样：

- PostgreSQL 作为业务元数据主存储
- 主业务对象尽量结构化建模
- 节点内容、复杂消息体保留 `jsonb`
- 文件引用关系统一显式落 `file_id`
- 本地 JSON 逐步降级为导出格式或迁移回退材料

这里不建议把这类元数据放到 MinIO，原因很明确：

- MinIO 适合存对象，不适合做高频结构化读写
- 每次更新 JSON 都要整文件覆盖
- 无法方便做查询、约束、事务和并发控制
- 文件引用统计和清理判断会很难做

所以这部分的正确归宿不是对象存储，而是 PostgreSQL。

## 五、核心设计原则

### 5.1 文件引用统一走 `file_id`

后续所有媒体相关业务对象都不应该再把 URL 当主键使用。

正确方式是：

- 主引用字段存 `file_id`
- URL 由服务端按 `file_id` 动态解析

### 5.2 主体结构化，复杂内容 JSONB 化

不建议把所有内容粗暴塞进一个大 JSONB。

建议做法：

- 主业务对象单独建表
- 列表项、消息项、节点项单独建表
- 难结构化、变化快的局部字段再用 `jsonb`

### 5.3 引用关系显式建表

如果一个对象内部可以挂多个文件，就不要只在 JSONB 里藏一个数组。

更建议：

- 单独建引用表
- 一条引用对应一行
- 保留 `sort_order / role / field_name` 这类辅助信息

这样后面做清理、统计、审计都会顺很多。

### 5.4 本地 JSON 不是长期主存储

本地 JSON 在迁移阶段仍然有价值：

- 兼容旧数据
- 导出/导入
- 临时回退

但不应继续作为主写入源。

## 六、建议数据模型

下面是首版推荐的数据模型。

## 七、为什么这样设计

### 7.1 比本地 JSON 更适合查询

比如后面要做：

- 最近 30 天生成历史
- 某类资产数量统计
- 某用户最常用参考图
- 某智能画布的所有媒体引用

本地 JSON 会越来越难查，数据库则天然适合。

### 7.2 比全 JSONB 更适合清理和约束

如果所有东西都塞成一个大 JSONB，短期开发快，但长期会遇到：

- 难做文件引用统计
- 难做唯一约束
- 难做级联删除保护
- 难做分页和筛选

所以更好的办法是：

- 结构稳定部分拆表
- 变化快部分留 JSONB

### 7.3 能真正闭环文件清理

只有业务元数据进入数据库后，后面才容易做到：

- 判断某个 `file_id` 是否仍被引用
- 删除历史记录时同步减少引用
- 删除资产条目时判断文件是否可物理删除
- 精确识别孤儿文件

## 八、和当前文件系统改造的关系

这套方案不是文件系统本身，但和文件系统改造强相关。

更准确的边界是：

### 8.1 文件系统改造主线

- MinIO
- `files` 表
- `file_id`
- 上传下载链路
- 配额和清理
- 存量文件迁移

### 8.2 业务元数据系统改造主线

- `history`
- `asset_library`
- `conversations`
- `smart_canvases`

所以：

- 它不是完全无关的另一套系统
- 但也不应该再混在“文件系统”这个词里

更合理的表达是：

- 文件存储系统
- 业务元数据系统

## 九、迁移顺序建议

这部分不建议一次做完。

推荐顺序如下：

### 第一步：`history`

优先原因：

- 结构最简单
- 收益最大
- 和文件引用关系最直接

### 第二步：`conversations`

优先原因：

- 数据结构规整
- 附件关系清晰
- 迁移成本中等

### 第三步：`smart_canvases`

优先原因：

- 和 `file_id` 关系最深
- 当前已经有较强媒体依赖
- 但结构最复杂，需要排在前两步之后

### 第四步：`asset_library`

优先原因：

- 需要考虑分类、批量移动、重命名等操作
- 最终也应该结构化，但可以稍后推进

## 十、分阶段实施方案

### 10.1 第一阶段：建表和双写

先做：

- PostgreSQL 建业务元数据表
- 业务写入时同时写 DB 和本地 JSON
- 读取暂时仍以本地 JSON 为主

目标：

- 不立刻切读路径
- 先把新数据稳定沉到 DB

### 10.2 第二阶段：读切换

再做：

- `history` 改成从 DB 读
- `conversations` 改成从 DB 读
- `smart_canvases` 改成从 DB 读
- `asset_library` 改成从 DB 读

目标：

- 本地 JSON 降级成兼容层

### 10.3 第三阶段：引用闭环

进一步做：

- 删除业务对象时同步更新引用
- 基于引用表做孤儿文件识别
- 基于引用关系做物理删除判断

目标：

- 清理和防误删真正闭环

### 10.4 第四阶段：下线本地 JSON 主写入

最后做：

- 停止业务写本地 JSON
- JSON 只保留导出/备份用途
- 逐步移除历史兼容逻辑

## 十一、风险和注意点

### 11.1 不要一开始就把所有对象都塞进一个 JSONB

这样短期看省事，后面很容易变成新的技术债。

### 11.2 不要把业务元数据放 MinIO

对象存储不是元数据主库。

### 11.3 不要跳过引用表

如果只把 `file_id` 藏在 JSON 里，后续清理和统计还是做不完整。

### 11.4 迁移期要保留回退路径

建议在双写阶段保留：

- 本地 JSON 导出
- DB 校验脚本
- 抽样对账工具

## 十二、推荐下一步

建议按下面顺序推进：

1. 先把这份方案定为边界文档
2. 先从 `history` 开始做 PostgreSQL 表设计和读写改造
3. 把 `conversations` 作为第二个对象域推进
4. 再处理 `smart_canvases`
5. 最后收口 `asset_library`

如果继续往下做，我建议下一份文档直接落成：

- `docs/业务元数据系统-历史记录落地方案.md`

或者直接开始第一批表结构设计和迁移脚本开发。
