# 文件系统方案

> 日期：2026-07-08
> 适用范围：MediaForge 当前版本

## 一、背景和判断

现在这套系统的文件数据基本都直接落在本地磁盘上。短期看这样实现简单，但只要用户数和使用时长上来，磁盘占用一定会持续增长，而且增长速度不会太慢。

文件主要存放目录主要是这几类：

- `assets/input/`
- `assets/output/`
- `assets/library/`
- `assets/uploads/`

这部分对应的代码入口主要在：

- `app/config.py`
- `app/core/media.py`

除了文件本身，系统里还有一批元数据目前也还是本地 JSON：

- `data/users/<user_id>/history.json`
- `data/users/<user_id>/asset_library.json`
- `data/users/<user_id>/prompt_libraries.json`
- `data/sessions.json`
- `data/users_registry.json`
- `data/shared_folders.json`

所以现在的问题其实分成两层：

1. 文件长期堆在本地，磁盘迟早会吃满。
2. 元数据也放在本地 JSON 里，后面无论是并发、查询、清理、统计都会越来越别扭。

## 二、目标

- 长期文件从应用本地磁盘剥离出去
- 文件访问不再依赖本地绝对路径和静态目录暴露
- 文件和元数据分层管理
- 后续能做配额、清理、归档、迁移
- 后续如果从 MinIO 切到 S3，改造成本可控

## 三、总体方案

这套方案我定成三层：

- 文件内容放 `MinIO`
- 元数据逐步迁到 `PostgreSQL`
- 本地磁盘只保留临时文件和缓存

对应关系如下：

```text
Browser
  |
  v
FastAPI
  |
  +-- PostgreSQL
  |     - 用户
  |     - 文件元数据
  |     - 历史记录
  |     - 资产库记录
  |     - 文件引用关系
  |
  +-- MinIO
  |     - 上传文件
  |     - 生成结果
  |     - 资产库媒体
  |     - 临时导出文件
  |
  +-- Local Temp Disk
        - 下载中转
        - 转码缓存
        - 临时处理文件
```

这里的边界要明确：

- 应用本地磁盘不再承担长期存储职责
- MinIO 只负责对象存储，不承担业务权限判断
- PostgreSQL 负责业务侧的文件身份、引用关系和状态管理

## 四、为什么选 MinIO

MinIO 有几个现实优势：

- 兼容 S3 API，后面要迁 S3 比较顺
- 可以先内网部署，不受外网环境限制
- 文件量起来以后比继续堆本地目录更可控
- 生命周期、对象管理、扩容路径都比本地文件系统清楚

## 五、当前目录到对象存储的映射

现在的本地目录和后续对象前缀，建议按下面这个关系来处理：

| 当前目录 | MinIO 前缀 | 说明 |
|------|------|------|
| `assets/input/` | `users/{user_id}/inputs/` | 用户输入参考图、音视频输入 |
| `assets/output/` | `users/{user_id}/outputs/` | 业务输出文件 |
| `assets/library/` | `users/{user_id}/assets/library/` | 资产库文件 |
| `assets/uploads/` | `users/{user_id}/uploads/` | 用户上传的本地素材 |
| 临时压缩包/中间产物 | `temp/...` | 短期保留，自动过期 |

这里有个原则：不要再让业务代码依赖“URL 反查本地路径”。

当前项目里已经有不少逻辑是通过 URL 去反查本地文件路径，例如：

- `/output/...`
- `/assets/...`

这一套在本地目录时代还能凑合用，但迁到对象存储以后就不合适了。后面要改成：

- 业务只认 `file_id`
- 存储层认 `bucket + object_key`
- 是否能访问，由业务层判断

## 六、Bucket 规划

Bucket 我不建议只建一个，把所有东西全塞进去。最少拆成下面三个：

### 6.1 `mediaforge-private`

放长期文件：

- 用户上传
- 生成结果
- 资产库原始文件
- 历史相关文件

默认不公开，下载走预签名 URL。

### 6.2 `mediaforge-public`

放可直接公开访问的对象，但前提是业务上已经明确“允许裸链”：

- 公开分享页封面
- 公开缩略图
- 不涉用户隐私的静态导出物
- 需要挂 CDN 的公开媒体

这个 bucket 不应该默认承接普通用户上传、生成原图、历史附件这类业务文件。否则权限边界会很快混乱。

这里要强调一个原则：

- `mediaforge-private` 解决“业务文件安全访问”
- `mediaforge-public` 解决“明确可公开的稳定直链访问”

如果某类文件是否公开还不稳定，就先放 `private`，后面再通过业务流程转成公开对象，不要一开始就直接落 `public`。

对 MediaForge 当前这期改造来说，`mediaforge-public` 先作为后续能力预留即可。第一步“新上传文件先改写 MinIO”默认仍应先写 `mediaforge-private`。

### 6.3 `mediaforge-temp`

放短期文件：

- 临时 zip
- 中转文件
- 导出缓存
- 处理过程中的临时对象

这个 bucket 必须配生命周期规则，自动删，不走人工清理。

## 七、Object Key 规划

对象 key 不要直接沿用当前本地文件名，也不要继续保留“原始目录结构拼 URL”的思路。统一按业务含义组织会更稳。

建议格式：

```text
users/{user_id}/inputs/{yyyy}/{mm}/{file_id}.{ext}
users/{user_id}/outputs/{yyyy}/{mm}/{file_id}.{ext}
users/{user_id}/history/{yyyy}/{mm}/{file_id}.{ext}
users/{user_id}/assets/{category}/{file_id}.{ext}
shared/{source}/{yyyy}/{mm}/{file_id}.{ext}
temp/{yyyy}/{mm}/{dd}/{task_id}/{filename}
```

这么做有几个好处：

- 用户隔离直接体现在对象路径上
- 后面做配额统计和离线清理比较方便
- 不依赖原始文件名，能避开重名和路径污染
- 同一类数据可以直接做批量生命周期管理

## 八、文件访问方式

访问方式我定成“私有对象 + 预签名 URL”，不走公开目录。

标准流程：

1. 前端请求业务接口。
2. 业务接口校验用户和资源关系。
3. 服务端生成短时有效的预签名 URL。
4. 前端再拿这个 URL 去下载或预览。

这样做的原因很现实：

- 文件不会裸暴露
- 访问控制还在业务层
- 应用服务不需要长期中转大文件流量

不建议长期保留现在这种对外直接暴露：

- `/output/...`
- `/assets/...`

后续统一收口成类似：

- `/api/files/{file_id}`
- `/api/files/{file_id}/download`
- `/api/files/{file_id}/preview`

## 九、元数据设计

文件上对象存储以后，元数据就不能继续散在 JSON 里硬存 URL 了。否则后面还是一样难管。

### 9.1 `files` 表

建议单独建立统一文件表，字段至少包括：

- `id`
- `user_id`
- `bucket`
- `object_key`
- `original_name`
- `ext`
- `mime_type`
- `size_bytes`
- `sha256`
- `kind`
- `source`
- `is_public`
- `status`
- `created_at`
- `updated_at`
- `last_accessed_at`
- `expires_at`
- `deleted_at`

其中：

- `kind`：`image / video / audio / model / archive / document`
- `source`：`upload / generated / imported / shared / temp`
- `status`：`active / deleting / deleted / failed`

### 9.2 引用关系

后面的业务表不要再直接存 URL，统一引用 `files.id`。

这里至少包括：

- 历史记录
- 资产库条目
- 画布输出
- 对话附件
- 共享目录导入记录

这样做的意义只有两个，但都很关键：

1. 一个文件被多处引用时不会误删。
2. 可以识别孤儿文件，后面能回收。

## 十、生命周期和清理策略

文件迁到 MinIO 以后，不代表容量问题自动消失。只是从“本地磁盘爆掉”变成“对象存储持续增长”。所以清理策略必须一起定。

### 10.1 临时文件

范围：

- `mediaforge-temp/temp/...`

处理方式：

- `1~3 天`自动删除

### 10.2 历史输出

范围：

- `users/{user_id}/history/...`

处理方式：

- 按时间保留最近 `N` 天
- 或按数量保留最近 `N` 条
- 超限后只保留元数据，不再保留文件内容

### 10.3 输入文件

范围：

- `users/{user_id}/inputs/...`

处理方式：

- 如果没有被历史记录或资产库引用，`7~30 天`后清理

### 10.4 资产库文件

范围：

- `users/{user_id}/assets/...`

处理方式：

- 不做自动过期
- 只有业务删除且确认没有引用时才物理删除

### 10.5 当前实现口径

当前 MediaForge 已经先落了一版“定时清理 + 配额控制”，口径如下：

- 用户总配额按 `files` 表中“未删除文件”的 `size_bytes` 汇总计算
- 新写入对象时先检查配额，超限直接拒绝写入
- 自动清理只处理 `input / uploads / output / temp`
- `library` 不参与自动过期
- 清理依据优先看 `expires_at`
- 没有 `expires_at` 的对象，再按 `last_accessed_at` 或 `created_at` 对照保留期判断

这版还是“分类保留期驱动”的清理，不是“精确引用计数驱动”的物理回收。也就是说：

- 历史记录、资产库、智能画布等业务已经开始引用 `file_id`
- 但自动清理任务目前还没有做跨业务表的统一引用统计
- 所以生产环境里不要把 `output / input / uploads` 的保留期设得过短
- `library` 继续保持只手动删除，不自动回收

## 十一、上传和下载流程

### 11.1 上传

当前阶段我倾向先走“服务端中转上传”，理由很简单：改动最小，最贴合现有项目。

流程如下：

1. 前端把文件传给 FastAPI。
2. FastAPI 校验类型、大小、用户身份。
3. 服务端写入 MinIO。
4. 服务端写入 `files` 元数据。
5. 返回 `file_id`。

优点是接入快，基本不需要前端大改。缺点是大文件流量会经过应用服务。

如果后面视频、大图、3D 文件多起来，再补“预签名直传”：

1. 前端先向服务端申请上传凭证。
2. 服务端返回预签名 URL。
3. 前端直接上传到 MinIO。
4. 上传完成后通知业务接口入库。

所以这部分我定成两阶段：

- 第一阶段：服务端中转
- 第二阶段：按业务压力再补直传

### 11.2 下载

下载统一改成：

1. 前端传 `file_id`
2. 服务端校验资源归属
3. 服务端生成短期有效下载地址
4. 前端下载

这个流程能替代当前本地文件直读模式，也方便后面切换存储后端。

## 十二、代码改造点

### 12.1 配置层

`app/config.py` 里增加对象存储配置：

- `MINIO_ENDPOINT`
- `MINIO_ACCESS_KEY`
- `MINIO_SECRET_KEY`
- `MINIO_SECURE`
- `MINIO_BUCKET_PRIVATE`
- `MINIO_BUCKET_PUBLIC`
- `MINIO_BUCKET_TEMP`
- `DATABASE_URL`
- `STORAGE_QUOTA_ENABLED`
- `STORAGE_USER_QUOTA_BYTES`
- `STORAGE_CLEANUP_ENABLED`
- `STORAGE_CLEANUP_INTERVAL_SECONDS`
- `STORAGE_CLEANUP_BATCH_SIZE`
- `STORAGE_INPUT_RETENTION_DAYS`
- `STORAGE_UPLOAD_RETENTION_DAYS`
- `STORAGE_OUTPUT_RETENTION_DAYS`
- `STORAGE_TEMP_RETENTION_DAYS`

其中当前阶段的使用建议是：

- `MINIO_BUCKET_PRIVATE`：第一步立即启用，承接新上传文件
- `MINIO_BUCKET_PUBLIC`：保留配置项，后面有公开资源场景时再正式启用
- `MINIO_BUCKET_TEMP`：给中转/导出/短期对象预留

参数含义建议统一成下面这样：

| 参数 | 当前默认值 | 含义 |
|------|------|------|
| `DATABASE_URL` | 空 | PostgreSQL 连接串，启用 `files` 元数据表 |
| `STORAGE_QUOTA_ENABLED` | `true` | 是否启用写入前配额检查 |
| `STORAGE_USER_QUOTA_BYTES` | `10737418240` | 单用户总存储配额，默认 `10GB` |
| `STORAGE_CLEANUP_ENABLED` | `true` | 是否启用后台定时清理 |
| `STORAGE_CLEANUP_INTERVAL_SECONDS` | `3600` | 清理任务执行间隔，默认 `1` 小时 |
| `STORAGE_CLEANUP_BATCH_SIZE` | `500` | 单次清理最多扫描/处理的候选对象数 |
| `STORAGE_INPUT_RETENTION_DAYS` | `30` | 输入参考文件保留天数 |
| `STORAGE_UPLOAD_RETENTION_DAYS` | `30` | 本地素材上传保留天数 |
| `STORAGE_OUTPUT_RETENTION_DAYS` | `30` | 普通输出文件保留天数 |
| `STORAGE_TEMP_RETENTION_DAYS` | `3` | 临时对象保留天数 |

推荐的生产环境起步值：

| 参数 | 推荐值 | 说明 |
|------|------|------|
| `STORAGE_QUOTA_ENABLED` | `true` | 正式环境建议始终开启 |
| `STORAGE_USER_QUOTA_BYTES` | `21474836480` | 建议先给 `20GB/用户`，比默认值更稳 |
| `STORAGE_CLEANUP_ENABLED` | `true` | 正式环境建议开启 |
| `STORAGE_CLEANUP_INTERVAL_SECONDS` | `1800` | 建议 `30` 分钟，回收更及时 |
| `STORAGE_CLEANUP_BATCH_SIZE` | `1000` | 用户量上来后比 `500` 更合适 |
| `STORAGE_INPUT_RETENTION_DAYS` | `30` | 参考输入通常保留一个月比较稳 |
| `STORAGE_UPLOAD_RETENTION_DAYS` | `30` | 本地素材上传先按一个月处理 |
| `STORAGE_OUTPUT_RETENTION_DAYS` | `60` | 输出建议比输入更长，避免用户回看时误清 |
| `STORAGE_TEMP_RETENTION_DAYS` | `3` | 临时对象保持短保留即可 |

如果是内测环境或单机试运行，建议先用下面这组：

```env
STORAGE_QUOTA_ENABLED=true
STORAGE_USER_QUOTA_BYTES=10737418240
STORAGE_CLEANUP_ENABLED=true
STORAGE_CLEANUP_INTERVAL_SECONDS=3600
STORAGE_CLEANUP_BATCH_SIZE=500
STORAGE_INPUT_RETENTION_DAYS=30
STORAGE_UPLOAD_RETENTION_DAYS=30
STORAGE_OUTPUT_RETENTION_DAYS=30
STORAGE_TEMP_RETENTION_DAYS=3
```

如果是正式环境，建议起步改成：

```env
STORAGE_QUOTA_ENABLED=true
STORAGE_USER_QUOTA_BYTES=21474836480
STORAGE_CLEANUP_ENABLED=true
STORAGE_CLEANUP_INTERVAL_SECONDS=1800
STORAGE_CLEANUP_BATCH_SIZE=1000
STORAGE_INPUT_RETENTION_DAYS=30
STORAGE_UPLOAD_RETENTION_DAYS=30
STORAGE_OUTPUT_RETENTION_DAYS=60
STORAGE_TEMP_RETENTION_DAYS=3
```

### 12.2 存储抽象层

新增统一存储服务，比如：

- `app/services/storage.py`

对外只暴露几个稳定接口：

- `save_bytes(...)`
- `save_fileobj(...)`
- `get_presigned_get_url(...)`
- `get_presigned_put_url(...)`
- `delete_object(...)`
- `stat_object(...)`

业务代码不应该直接到处散着写 MinIO SDK 调用。

### 12.3 媒体工具层

`app/core/media.py` 里现在不少工具函数都是基于本地路径设计的，例如：

- `output_path_for`
- `output_url_for`
- `output_file_from_url`
- `local_media_file_by_basename`

这些函数后面要拆成两类：

- 本地临时文件工具
- 对象存储工具

不要继续让业务代码依赖“给我一个 URL，我反查本地路径”。

### 12.4 路由层

现有这些接口后面都要动：

- `POST /api/ai/upload`
- `POST /api/local-assets/upload`
- `GET /api/download-output`
- 资产库相关上传接口
- 历史记录保存和删除接口

统一改造方向：

- 上传后返回 `file_id`
- 业务层存 `file_id`
- 删除按 `file_id` 查对象，不按 URL 反查路径

## 十三、迁移顺序

这件事不适合一次改完。我倾向分四步走。

### 第一步：引入 MinIO，但先兼容本地存储

先做这些：

- 接入对象存储配置
- 增加统一 `storage service`
- 新上传文件改写 MinIO
- 老数据和老接口先保持兼容

这一步做完以后，新增文件就不会继续快速堆本地磁盘。

### 第二步：文件元数据入库

先把新文件的身份和状态纳入数据库：

- 建 `files` 表
- 业务记录开始引用 `file_id`
- 新逻辑不再依赖 URL 反查物理文件

这一步是后续清理、统计、权限控制的基础。

### 第三步：存量文件迁移

把历史目录扫一遍：

- 扫描 `output/` 和 `assets/`
- 上传到 MinIO
- 建立对象映射
- 回写元数据

这一阶段要做校验，至少校验：

- 对象数量
- 文件大小
- 抽样下载是否正常

### 第四步：收口本地长期存储

最后再做收尾：

- 本地只保留临时目录
- 业务接口不再依赖 `/output` 和 `/assets` 作为长期静态文件入口
- 老的本地清理逻辑逐步下线

## 十四、部署要求

### 14.1 MinIO 部署

如果是内部部署，我这里分两档：

- 试运行：单节点 MinIO
- 正式环境：多磁盘或分布式 MinIO

### 14.2 基础要求

- 存储盘独立，不和应用日志混放
- MinIO 数据和 PostgreSQL 都要备份
- 配容量监控和告警
- 配生命周期规则
- 业务使用专用账号，不直接拿 root 账号跑

### 14.3 恢复能力

后面上线前至少要补一次恢复演练，确认：

- 对象数据能恢复
- 元数据能恢复
- 应用能重新挂回文件引用关系

## 十五、注意点

### 15.1 不能只迁文件，不迁元数据

如果只是把文件从本地盘搬到 MinIO，但历史记录、资产库还是直接存 URL，问题并没有真正解决。后面还是会碰到：

- 文件引用关系不清楚
- 删除不安全
- 容量统计不准
- 孤儿文件不好回收

### 15.2 不能把 MinIO 当目录共享来用

错误思路是继续大量拼 URL、拆 URL、反查路径。

正确思路是：

- 业务层认 `file_id`
- 存储层认 `bucket + object_key`
- 元数据层维护文件状态和引用关系

### 15.3 不能无限保留历史

就算对象存储够大，也不应该无限堆历史文件。系统上线以后还是要把下面几项补上：

- 用户配额
- 文件过期策略
- 自动清理任务
- 孤儿文件回收

## 十六、实施建议

1. 新上传文件先改写 MinIO
2. 建统一 `files` 元数据表
3. 历史记录和资产库改成引用 `file_id`
4. 加入定时清理和配额控制
5. 最后迁移存量文件
