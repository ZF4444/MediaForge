# MediaForge 50 人使用容量评估与优化建议

评估日期：2026-07-21

## 1. 结论

当前项目具备 PostgreSQL 连接池、MinIO、存储配额、健康检查和 Prometheus 指标等基础能力。对于 50 个注册用户、5 至 10 人普通并发操作，硬件和基础存储大概率够用。

如果目标是 50 人同时在线，且多人并发生图、上传视频、保存大型画布，目前还不能直接按生产级稳定性来承诺。主要限制不是 CPU，而是同步 I/O 阻塞、任务治理不足，以及多用户权限隔离问题。

## 2. 优先优化项

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| P0 | 认证和路由中的同步数据库、文件操作阻塞事件循环 | 一个慢查询或大文件操作可能拖慢其他用户 |
| P1 | 生成任务已有 Redis Streams 持久化和崩溃接管，但仍无全局/用户并发上限 | 高并发可能压垮上游或本机 |
| P0 | 登录、管理员、WebSocket、文件访问隔离不完整 | 多用户场景存在越权和数据泄漏风险 |
| P0 | 上传文件完整读入内存 | 多人同时上传视频时内存快速上涨 |
| P1 | 不能安全地直接增加 Uvicorn worker | 任务、WebSocket、运行配置在多个进程间不一致 |
| P1 | 画布、历史记录存在 N+1 查询和全量返回 | 数据积累后响应逐渐变慢 |
| P1 | 可观测指标不足，尚无并发压测 | 无法量化 50 人下的容量和退化位置 |
| P2 | 静态资源和媒体下载仍由应用进程承担 | 浪费 API worker，增加出口压力 |

## 3. 解除事件循环阻塞

认证中间件每次 API 请求都会同步访问 PostgreSQL，并更新 `last_seen`，位置见 `app/core/auth.py:get_session`。画布、历史、素材等大量 `async` 路由也直接执行同步数据库调用。

建议：

- 短期将同步数据库、MinIO、图片和 ZIP 操作统一放入线程池，或将纯同步路由声明为普通 `def`。
- 中期改用异步 PostgreSQL 客户端。
- `last_seen` 改成每个会话最多 5 至 10 分钟更新一次，避免前端轮询不断产生数据库写入。
- 增加事件循环延迟指标，建议告警阈值为 100 至 200ms。

## 4. 引入持久任务队列和背压

画布异步任务状态持久化在 Redis，并通过租约保证多 worker 之间只有一个执行者；worker 重启后会扫描可恢复任务重新投递。相关实现位于 `app/services/canvas_tasks.py` 与 `main.py` 的画布任务执行函数。

当前已具备的能力：

- 任务记录、结果和用户归属存入 Redis，具备 TTL 清理。
- Redis Streams 消费组支持 pending 消息接管；任务租约避免多个 worker 同时执行。
- Web API 与任务 worker 可以拆分部署，任务查询不依赖提交任务的进程。

仍需补齐：

- 没有用户级或全局并发限制。
- 高成本上游调用没有统一预算、限流和熔断。
- 任务取消、超时和可审计的重试策略尚未完整实现。

建议使用 Redis 加 Dramatiq、Celery、RQ 或 Arq，至少实现：

- 全局生成并发上限。
- 每用户并发上限，例如图片 2 个、视频 1 个。
- 排队长度与预计等待时间。
- 任务用户归属校验。
- 失败重试、超时、取消和结果 TTL。
- ComfyUI 每个实例独立容量控制，而不只根据远端瞬时队列选择实例。

## 5. 修复多用户安全问题

这是 50 人上线前的阻断项：

- 系统按固定用户名 `admin` 判定管理员，但当前登录完全无密码，任何人只要使用已注册用户名就能登录。
- SSO 直接信任 URL 中的 `user_id`，没有签名或可信代理校验。
- `/api/providers`、工作流管理、ComfyUI 实例配置缺少后端管理员校验。
- `/api/config/token` 会向普通登录用户返回完整 ModelScope Token。
- WebSocket 没有认证，`client_id` 由客户端自行提供，生图结果会广播给全部连接。
- 文件查询只按 `file_id`，没有校验文件所属 `user_id`。结合全局 WebSocket 广播，可能泄露其他用户媒体。

建议：

- 接入真实 SSO 或密码认证，并验证 SSO 签名。
- 将管理员身份存储为数据库角色，不以用户名作为角色判断依据。
- 所有文件、任务、配置接口执行服务端授权。
- WebSocket 握手校验 session，并按用户或业务房间广播。
- API 响应不返回任何完整密钥。

## 6. 上传和媒体处理改成流式

当前部分上传接口使用 `await file.read()` 将完整文件加载到内存，例如 `app/routers/local_assets.py:upload_local_assets`。50 人同时上传较大视频时会造成明显的内存峰值。

建议：

- 使用现有 `save_fileobj()` 路径直接流式写入 MinIO。
- 在反向代理和应用层同时设置文件大小限制。
- 限制单用户同时上传数。
- 缩略图异步预生成，避免首个预览请求现场执行图片或视频处理。
- 给 `/tmp/mediaforge-storage-cache` 设置容量上限和 LRU 清理。
- 对同一媒体的缩略图生成增加互斥或幂等保护，避免并发请求重复生成。

## 7. 优化数据库查询

明显的增长型问题包括：

- 画布列表先查询全部 ID，再逐个加载完整画布和节点。
- 历史记录对每条记录再次查询文件引用。
- 本地素材接口仍有全量查询路径。
- 保存画布会删除全部节点后逐条重建。
- 素材库每次修改会删除并重建全部分类和条目。
- 部分高频外键查询缺少对应索引。

建议优先增加以下索引，并使用 `EXPLAIN ANALYZE` 验证：

- `smart_canvas_nodes(canvas_id, sort_order)`
- `smart_canvas_node_files(node_id, sort_order)`
- `history_record_files(history_record_id, sort_order)`
- `conversation_messages(conversation_id, sort_order)`
- `conversation_message_files(message_id, sort_order)`

接口层建议：

- 画布列表直接通过聚合查询返回元数据和节点数量，不加载节点正文。
- 历史记录、会话和本地素材全部使用分页或游标查询。
- 批量加载媒体引用，消除 N+1 查询。
- 对大型画布考虑节点增量更新，而不是每次全量删除重建。
- 素材库逐步改成以关系表为主数据源，避免反复重写完整 JSON 文档。

## 8. 部署结构

画布任务状态和队列已可跨进程使用，但 WebSocket 广播、部分运行配置缓存和维护任务仍不具备完整的多副本协调。不要只通过增加 Uvicorn worker 来扩大所有能力；应将 API 与任务 worker 分开部署。

推荐部署形态：

```text
Nginx
  |-- 静态资源和媒体缓存
  `-- 2 个 FastAPI API worker
          |-- PostgreSQL
          |-- MinIO
          |-- Redis（会话缓存、任务、WebSocket Pub/Sub）
          `-- 独立生成任务 worker
```

数据库连接池要按总进程数计算。例如 2 个 API worker 加 2 个任务 worker，每进程 `max_size=20` 会允许最多 80 个连接，通常偏高。建议先按每进程 5 至 10 个配置，再根据连接等待指标调整。

API 副本应设置 `CANVAS_TASK_WORKER_ENABLED=false` 和 `CANVAS_TASK_RECOVERY_ENABLED=false`；独立任务进程使用 `python -m app.workers.canvas`。存储清理等定时任务仍需要独立调度器或数据库分布式锁，避免每个 API worker 重复执行。

## 9. 可观测性补充

目前指标主要覆盖 PostgreSQL、MinIO 和后台清理任务，仍建议增加：

- HTTP 请求量、状态码、请求耗时直方图。
- 当前请求数和事件循环延迟。
- 各类生成任务的排队数、运行数、等待时间和成功率。
- 按 provider 统计外部请求耗时、超时率和 429 比例。
- 上传吞吐量、上传失败数和进程 RSS。
- WebSocket 当前连接数、发送失败数和消息积压。
- 本地媒体缓存大小和清理数量。

注意避免将 `user_id`、`task_id`、URL 等高基数字段直接作为 Prometheus label。

## 10. 50 人压测方案

项目当前没有并发或负载测试，不能仅根据代码断言支持 50 人。建议在模拟上游服务下执行至少 30 分钟的混合压测：

- 50 个登录用户保持在线。
- 20 人浏览素材和画布。
- 10 人持续保存画布。
- 10 人提交图片任务。
- 5 人上传 50 至 200MB 文件。
- 5 人提交视频任务。

建议验收目标：

- 普通 API `p95 < 300ms`。
- 画布保存 `p95 < 800ms`。
- 5xx 比例小于 1%。
- PostgreSQL 连接等待 `p95 < 50ms`。
- 事件循环延迟小于 100ms。
- 任务服务重启后可恢复。
- 压测期间内存和本地缓存不持续增长。
- 任意用户不能读取、查询或订阅其他用户的任务和媒体。

建议分别测试以下场景：

1. 上游 AI 服务全部使用低延迟 Mock，定位本应用自身容量。
2. 上游加入 5 至 30 秒延迟，验证任务排队和超时行为。
3. PostgreSQL 或 MinIO 短暂不可用，验证重试、503 和恢复能力。
4. API worker 重启，验证任务状态、WebSocket 重连和幂等性。

## 11. 推荐实施顺序

1. 修复认证、管理员权限、文件归属和 WebSocket 隔离。
2. 建立持久任务队列、任务归属和并发控制。
3. 消除事件循环中的同步阻塞，上传改为流式。
4. 优化查询、补充索引和分页。
5. 补齐 HTTP、任务队列和事件循环指标。
6. 执行 50 人混合压测。
7. 根据压测数据决定 API worker 数、任务 worker 数和数据库连接池大小。
