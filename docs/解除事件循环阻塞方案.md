最终方案建议采用：

> 异步请求平面 + 有界同步适配层 + 独立重任务平面

不是把所有函数机械改成 async def。数据库和 HTTP 使用真正异步客户端；MinIO 等只有同步 SDK 的操作进入有并发上限的线程池；Pillow、
FFmpeg、ZIP 等重任务离开 API 进程。

## 最终执行模型

| 操作类型 | 最终执行位置 | 实现方式 |
| --- | --- | --- |
| PostgreSQL | API 事件循环 | psycopg_pool.AsyncConnectionPool |
| 会话验证 | Redis，PostgreSQL兜底 | 异步 Redis 客户端 |
| 外部 API、ComfyUI | API 事件循环 | 应用级共享 httpx.AsyncClient |
| MinIO 元数据、小文件操作 | 有界 I/O 线程池 | anyio.to_thread.run_sync() |
| 浏览器媒体预览和下载 | 浏览器直连 MinIO | 鉴权后返回短期预签名 URL |
| 上传 | 流式读取和写入 | 不再 await file.read() 全量加载 |
| Pillow、FFmpeg、FBX、缩略图 | 独立任务 worker | 持久任务队列 |
| ZIP 导入导出 | 独立任务 worker | 生成后写入 MinIO |
| 长时间生图、视频轮询 | 独立任务 worker | 不占用 API 请求和事件循环 |

## 1. 数据库全面使用异步连接池

当前同步池位于 app/core/database.py:91，所有数据库调用都会阻塞调用线程。最终应替换为 AsyncConnectionPool：

from contextlib import asynccontextmanager
from psycopg.rows import dict_row
from psycopg_pool import AsyncConnectionPool

_pool = AsyncConnectionPool(
    conninfo=DATABASE_URL,
    min_size=2,
    max_size=10,
    open=False,
    kwargs={
        "autocommit": True,
        "row_factory": dict_row,
        "connect_timeout": DATABASE_CONNECT_TIMEOUT_SECONDS,
        "options": (
            f"-c statement_timeout={DATABASE_STATEMENT_TIMEOUT_MS} "
            f"-c lock_timeout={DATABASE_LOCK_TIMEOUT_MS}"
        ),
    },
)

@asynccontextmanager
async def database_connection():
    try:
        async with _pool.connection(timeout=DATABASE_POOL_TIMEOUT_SECONDS) as conn:
            yield conn
    except Exception as exc:
        raise DatabaseUnavailableError(
            "PostgreSQL 服务暂时不可用，请稍后重试"
        ) from exc

业务仓储方法全部改为异步：

async def load_canvas_payload(user_id: str, canvas_id: str):
    async with database_connection() as conn:
        async with conn.cursor() as cur:
            await cur.execute(
                "SELECT * FROM smart_canvases WHERE id=%s AND user_id=%s",
                (canvas_id, user_id),
            )
            return await cur.fetchone()

调用链必须从路由到仓储全部 await，不能在异步仓储外再包装同步函数。

## 2. 认证改成异步缓存读取

当前每个请求都会同步执行一次 PostgreSQL UPDATE：app/core/auth.py:88。这是最优先需要移除的阻塞和写放大。

最终会话流程：

1. 登录时将会话写入 PostgreSQL。
2. 同时写入 Redis，键为 session token hash，TTL 与 session 有效期一致。
3. 请求认证首先异步读取 Redis。
4. Redis 未命中时异步查询 PostgreSQL，并回填 Redis。
5. last_seen 只在 Redis 中更新。
6. 每 5 至 10 分钟批量刷新 PostgreSQL，不再每次请求写库。
7. 注销时同时删除 Redis 和 PostgreSQL 会话。

中间件变成：

sess = await session_store.get(token)

这样绝大多数认证请求不占用数据库连接，也不会阻塞事件循环。

## 3. 同步 SDK 统一进入有界适配层

MinIO Python SDK是同步接口，不需要为了“全异步”换成不成熟的第三方 SDK。建立统一适配器：

import anyio
from functools import partial

storage_limiter = anyio.CapacityLimiter(12)

async def run_storage_io(func, *args, **kwargs):
    call = partial(func, *args, **kwargs)
    return await anyio.to_thread.run_sync(
        call,
        limiter=storage_limiter,
    )

所有异步路由只能通过该适配器调用 MinIO：

entry = await run_storage_io(save_fileobj, ...)

不要在业务代码中随意使用 asyncio.to_thread()，否则无法统一控制并发、队列长度和指标。

建议配置：

BLOCKING_IO_WORKERS=12
BLOCKING_IO_QUEUE_LIMIT=50

队列满时返回 503 或 429，而不是无限堆积请求。

## 4. 上传和下载不再经过应用内存

目前多处使用 await file.read()，例如 app/routers/local_assets.py:155。

最终上传流程：

UploadFile.file
-> 分块读取/流式 MinIO put_object
-> 写入 PostgreSQL 文件元数据
-> 提交缩略图后台任务
-> 返回 file_id

禁止将完整图片或视频转换成 bytes 后再保存。需要计算 SHA256 时，在流式读取过程中增量计算。

预览和下载流程：

请求 /api/files/{id}/preview
-> 异步查询文件及 user_id
-> 校验当前用户权限
-> 生成 1 至 5 分钟预签名 URL
-> 返回 302
-> 浏览器直接从 MinIO 下载

这样视频流量、文件缓存和慢客户端下载都不再占用 FastAPI worker。

## 5. 外部 HTTP 统一使用共享异步客户端

删除异步调用链中的：

- requests.get/post
- urllib.request.urlopen
- time.sleep

当前典型阻塞位置包括 main.py:8366 和 app/services/history.py:77。

应用启动时创建共享客户端：

app.state.http = httpx.AsyncClient(
    timeout=httpx.Timeout(connect=5, read=300, write=60, pool=5),
    limits=httpx.Limits(
        max_connections=100,
        max_keepalive_connections=30,
    ),
)

业务中复用：

response = await request.app.state.http.get(url)
await asyncio.sleep(1)

不能每次请求创建新的 AsyncClient，否则会损失连接池和 keep-alive。

## 6. CPU 和重文件任务移出 API

以下操作不应在线程池内长期运行：

- Pillow 大图压缩、裁剪、缩略图。
- FFmpeg 视频抽帧。
- FBX 处理。
- 大型 ZIP 压缩和解压。
- 生图、视频长轮询。
- 批量导入 200 个媒体文件。

这些任务提交到独立 worker：

API -> 创建任务记录 -> Redis 队列 -> Worker
                                    -> MinIO
                                    -> PostgreSQL 更新状态

API 只负责快速返回 202 + task_id。这样即使 ZIP 或 FFmpeg 占满 CPU，也不会影响登录、画布保存和健康检查。

## 7. 迁移顺序

1. 引入应用 lifespan，集中管理异步数据库池、HTTP 客户端和线程池。
2. 先改认证中间件，消除每请求同步数据库写入。
3. 将 business_metadata、画布、会话、历史和素材仓储改成异步。
4. 将所有 requests、urllib 替换为共享 httpx.AsyncClient。
5. 建立 MinIO 有界适配器和流式上传。
6. 预览、下载切换为预签名 URL。
7. 将 Pillow、FFmpeg、ZIP 和长任务迁入 worker。
8. 最后启用 2 个 API worker，并用 Redis Pub/Sub 支持跨进程 WebSocket。

迁移期间可以临时用 to_thread() 包裹旧同步函数，但这只是兼容桥接，不是最终状态。

## 验收标准

完成后必须满足：

- async def 调用链内不存在直接同步 PostgreSQL、MinIO、requests、urllib、time.sleep。
- 50 用户混合压测时事件循环延迟 p95 < 50ms，p99 < 100ms。
- 普通 API p95 < 300ms。
- 数据库连接等待 p95 < 50ms。
- 大文件上传期间登录、画布列表和健康检查延迟不明显升高。
- ZIP、FFmpeg、生图任务不增加 API 进程 CPU。
- 阻塞线程池和任务队列都有容量上限，满载时明确返回 429/503。
- 客户端断开后，上游 HTTP 请求和数据库操作能够取消，不留下失控任务。

这套方案的核心边界是：数据库和网络请求真正异步，无法异步的短 I/O 有界地进入线程池，CPU 和长任务完全离开 API 进程
