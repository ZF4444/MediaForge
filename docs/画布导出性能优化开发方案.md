# 画布导出性能优化开发方案

## 背景

画布管理页面的“下载画布和资产”以及画布编辑器的“导出模板（带资产）”都通过 `/api/canvas-workflows/export` 生成 ZIP。当前实现将完整 ZIP 保存在 `BytesIO` 中，资源逐个解析并打包；资源多、体积大或多人同时导出时，可能造成明显的内存、磁盘、数据库、对象存储带宽和 CPU 压力。

本方案分阶段优化：先降低同步导出的内存和重复 I/O，再增加后台导出任务，最后按规模将大型 ZIP 交给对象存储承载下载。

## 一期：同步导出优化

目标是在保持现有导出体验和模板格式兼容的基础上，避免 ZIP 全量驻留内存，并减少资源查找开销。

### 资源提取与去重

- 从节点数据中提取 `/api/files/{file_id}` 引用，优先以 `file_id` 作为资源身份。
- 在提取阶段去重，避免同一文件经多个节点或多个字段重复处理。
- 使用现有批量查询能力（如 `get_files_by_ids()`）批量获取文件元数据，避免逐文件查询数据库。
- 对无法解析为 `file_id` 的旧格式 URL 保留兼容路径。
- 元数据至少包含 `file_id`、bucket、object key、文件名、大小和内容类型。
- 资源提取阶段只处理引用和元数据，不触发媒体文件物化或下载。

### ZIP 构建与响应

- 使用临时文件构建 ZIP，替换当前 `BytesIO` 全量缓冲。
- 对 JPEG、PNG、WebP、MP4、WebM、音频等已压缩媒体使用 `ZIP_STORED`；对 JSON、文本和 CSV 等使用 `ZIP_DEFLATED`。
- 保持现有 `workflow.json` 格式和资源映射，保证现有模板仍可导入。
- 使用 `FileResponse` 返回临时 ZIP；响应完成后删除文件。构建或响应异常时也要可靠清理临时文件。
- 设置正确的下载文件名、内容类型和文件大小响应头。

### 并发、限制与前端状态

- 增加导出专用并发上限，通过配置控制。达到上限时返回明确的繁忙响应，避免导出请求无限占用线程、磁盘和对象存储连接。
- 对单次节点数、资源数、单文件大小和总资源大小设置可配置上限，并返回可理解的错误信息。
- 管理页和画布编辑器的导出按钮在请求期间禁用，显示准备资源/打包状态，结束、失败或取消后恢复，防止重复点击触发重复任务。
- 记录导出耗时、资源数量、输入总大小、ZIP 大小、缓存命中情况和失败原因。

## 二期：后台导出任务

目标是让大文件导出不占用 HTTP 请求生命周期，并为进度展示、重试和取消提供基础。

### 任务模型

建议新增 `canvas_export_jobs` 表，至少包含：

| 字段 | 用途 |
| --- | --- |
| `id` | 导出任务 ID |
| `user_id`、`canvas_id` | 所属用户和画布，用于授权校验 |
| `status` | `queued`、`running`、`succeeded`、`failed`、`expired` |
| `mode`、`include_resources` | 导出类型与是否包含资源 |
| `resource_count`、`total_bytes`、`progress` | 任务规模和进度 |
| `output_path`、`output_size` | 结果位置与大小 |
| `error_message` | 面向用户的失败原因 |
| `created_at`、`started_at`、`completed_at`、`expires_at` | 生命周期时间 |

### API 与 Worker

建议提供以下接口：

```text
POST /api/canvas-exports
GET  /api/canvas-exports/{job_id}
GET  /api/canvas-exports/{job_id}/download
POST /api/canvas-exports/{job_id}/cancel
```

创建接口完成参数和权限校验后快速返回任务 ID。后台 Worker 负责读取画布快照、批量解析资源、生成 ZIP、更新进度和结果状态。优先复用项目现有的 Redis stream/worker 模式，避免在 Web 进程内启动不可恢复的长任务。

进度可分为收集引用、解析元数据、打包资源和完成收尾几个阶段。前端先采用轮询展示任务状态；若后续接入现有事件推送体系，再改为推送。

### 权限、下载与清理

- 创建任务和下载结果都校验登录用户与任务 `user_id` 的归属关系。
- 本地临时文件结果在任务保留期内可重复下载，过期后删除文件并更新任务状态。
- Worker 重启后应能恢复或将失联的 `running` 任务标记为失败，不能让任务永久卡在运行中。
- 支持取消排队任务；运行中任务的取消应在资源处理边界检查取消标记。

## 三期：对象存储承载大文件

当导出包达到 GB 级，或下载并发导致应用服务器带宽、连接和磁盘压力明显时，将 ZIP 结果上传至私有对象存储（当前部署为 MinIO），由对象存储直接向浏览器提供下载。

流程如下：

1. Worker 生成 ZIP，并将结果上传到私有 bucket 中的临时导出对象路径。
2. Worker 将对象标识、文件大小和过期时间写入导出任务记录。
3. 用户请求下载时，应用先验证身份，并确认任务归属当前用户且任务尚未过期。
4. 校验通过后，应用生成仅对该对象有效、短时间过期的预签名 URL，并返回给浏览器。
5. 浏览器使用该 URL 直接从 MinIO 下载，下载数据流不经过 MediaForge 应用服务器。
6. 清理任务在过期后删除对象和对应记录；签名 URL 即使未使用，也会因过期而失效。

预签名 URL 是由对象存储认可的临时访问凭证。它不要求 bucket 对公网开放，也不应被当作永久链接保存或写入公开日志。下载接口每次发放 URL 前仍须进行用户和任务归属校验；URL 的有效时间应尽量短，并覆盖合理的下载启动时间。生成 URL 只负责授权和签名，不会替代对象过期清理。

该方案主要减轻 ZIP 下载阶段的应用服务器带宽、连接占用和转发压力。ZIP 的生成与上传仍消耗 Worker 的 CPU、临时磁盘、对象存储带宽和容量，所以任务并发限制、体积限制和过期清理仍然必要。

### 对象存储实现注意事项

- 导出 bucket 或导出对象前缀保持私有，不设置匿名读取策略。
- 结果对象 key 使用不可预测的任务 ID 或随机 ID，不能只用用户提供的文件名。
- 下载接口按任务 ID 查询对象位置，不接受客户端直接传入任意 bucket/key。
- 预签名 URL 只授予单个对象的 `GET` 权限，过期时间按配置限制。
- 通过反向代理/浏览器确认 MinIO 下载地址可达；若内外网 endpoint 不同，需要使用浏览器可达的签名 endpoint 配置。
- 清理任务删除过期对象；任务数据库记录与对象删除应具备重试能力，避免一侧失败后遗留孤儿数据。
- 大文件上传使用对象存储 SDK 的流式或 multipart 上传能力，避免再把完整 ZIP 读入内存。

## 同步与后台模式的切换策略

第一阶段继续使用现有同步接口，但实现改为临时文件响应。后台任务完成后，再根据配置阈值决定同步还是异步，例如：

```text
预计总资源大小 <= 256 MiB 且资源数 <= 200：同步导出
超过任一阈值：创建后台导出任务
```

阈值只是初始建议，应通过部署环境压测确定，并做成配置项。估算大小优先基于批量查询得到的元数据；元数据缺失时采用保守策略进入后台任务或拒绝超限导出。对象存储结果交付可在后台任务阶段按实际 ZIP 大小或部署策略启用。

## 推荐实施顺序

1. 抽取资源引用，按 `file_id` 去重并批量加载元数据。
2. 将 ZIP 构建改为临时文件，并按媒体类型选择压缩方式。
3. 使用 `FileResponse` 和可靠的完成/异常清理逻辑。
4. 增加同步导出并发、规模限制、日志指标和前端按钮状态。
5. 增加任务表、Redis Worker、任务状态/取消/下载接口。
6. 前端增加后台任务进度展示和结果下载。
7. 大型结果上传 MinIO，增加经权限校验后发放短期预签名 URL 的下载流程。
8. 增加对象和任务过期清理、失败重试及监控告警。

## 验收与测试

- 空资源、单资源、多资源和同一 `file_id` 多处引用均能正确导出。
- 新旧 URL 格式、缺失文件和已删除文件处理符合约定。
- 同名资源、特殊字符文件名可安全写入 ZIP，资源映射与归档内容一致。
- 导出的 JSON/ZIP 可由现有画布模板导入流程读取。
- 图片/视频等媒体不进行无效压缩，文本和 JSON 仍压缩。
- 大 ZIP 不会完整驻留应用内存；响应结束和异常路径都会清理临时文件。
- 并发请求受限，按钮重复点击不会产生重复导出。
- 后台任务状态可查询、失败可见、取消可用、Worker 重启后状态可恢复。
- 其他用户不能查询或下载任务；预签名 URL 到期后不可继续访问。
- 过期清理同时覆盖任务记录、本地临时文件和对象存储结果。
- 压测覆盖多个并发导出、缓存冷热、数百个小资产及少量大视频，记录耗时、峰值内存、磁盘空间和对象存储流量。
