# 前端重构计划

> 生成日期：2026-08-04
> 范围：`static/` 下的前端代码（HTML/CSS/JS）
> 前置文档：`docs/代码重构分析报告.md`（2026-06-05，后端拆分已落地；前端当时只给出"低风险物理拆分"的保守方案，未执行）
>
> **明确边界（本次计划的前提）**：
> - `static/js/canvas.js` + `static/js/canvas.css` + `static/canvas.html`（"无限画布"/普通画布）**不纳入本次重构**，只需确保现状能正常打开、正常使用即可。除非某项改动（如引入构建工具、抽取公共基础库）不改动它的行为却能顺带受益，否则不为它花费额外成本。
> - 本次重构的核心目标是 `static/js/smart-canvas.js`（"智能画布"，16590 行，是当前实际持续迭代、承担最多新功能的模块），以及围绕它缺失的工程基础设施（构建、测试、lint）。
> - 严格遵循"页面/功能完全不变"的硬约束：这是一次结构重构，不是产品重做。

## 一、现状评估（结论先行）

| 维度 | 现状 | 生产级要求 | 差距 |
|------|------|-----------|------|
| 模块化 | `smart-canvas.js` 单文件 16590 行 / 650+ 函数，全局作用域共享 289 个顶层变量 | 按功能边界拆分为可独立测试的模块 | 大 |
| 构建工具 | 无 `package.json`，无 bundler；Tailwind 靠浏览器端 JIT（`vendor/js/tailwindcss-cdn.js`）实时编译 | 构建期产出静态资源，支持 tree-shaking / minify / source map | 大 |
| 类型检查 | 纯 JS，无 TypeScript，无 JSDoc 类型标注 | 至少有基本的类型约束防止低级错误 | 中 |
| 自动化测试 | 0 个前端测试文件 | 关键业务逻辑（布局计算、状态流转）有回归测试 | 大 |
| Lint / 格式化 | 无 ESLint / Prettier 配置 | 统一风格，自动抓未用变量/死代码 | 中 |
| 错误处理 | 64 处裸 `innerHTML =`，20 处 `catch(_) {}` 静默吞错 | 结构化错误处理，关键路径有日志 | 中 |
| 安全（XSS） | 有 `escapeHtml`，但靠人工在每处调用，无强制机制 | 模板层强制转义或有 lint 规则兜底 | 中 |

`canvas.js`（13170 行）与 `smart-canvas.js` 结构问题类似，但按本次范围约定不处理，仅在"打得开"这条底线上做验证。

## 二、重构目标与不做的事

### 目标
1. 引入构建工具链，摆脱浏览器端 Tailwind JIT 编译，产出可 minify / 可做 source map 的静态资源。
2. 把 `smart-canvas.js` 按已经存在的天然功能边界拆成 ES module，消除全局作用域污染。
3. 为拆分后的高风险逻辑（循环级联布局、连线、状态持久化）补齐自动化测试，建立类似后端 `route_baseline.json` 的"契约快照"安全网。
4. 引入 ESLint + Prettier，把这次审查中人工发现的死代码/无效样式问题变成机器可自动捕获的。
5. 全程保持 `smart-canvas.html` 打开后功能与现状零差异（同样的 DOM 结构、同样的交互行为）。

### 明确不做
- 不引入 React / Vue / Svelte 等前端框架，不改变现有"直接操作 DOM + 手写模板字符串"的编程模型。**理由**：框架迁移等价于重写，成本与本次"结构重构不改变行为"的约束冲突，性价比低。
- 不对 `canvas.js` 做模块拆分或架构调整。
- 不引入 TypeScript（放在本计划之外，作为未来可选项，见「七、后续可选项」）。
- 不改变现有 API 接口、URL 路径、数据存储格式。

## 三、总体架构方案

### 3.1 构建工具选型：Vite

选择 Vite 而非 webpack/rollup 的理由：
- 零配置起步，对"多页面 + 大量全局脚本"的现有结构兼容度最高（`build.rollupOptions.input` 支持多入口，天然匹配现在的多 HTML 页面结构）。
- 内置 Tailwind 支持，可以直接替换掉 `vendor/js/tailwindcss-cdn.js` 的运行时编译。
- 开发模式下有 HMR，迁移期间调试效率高。
- 支持"保留全局变量风格代码"的渐进迁移：拆出来的 ES module 之间用 `import`/`export`，但仍可以在入口文件里挂到 `window` 上，兼容 HTML 里内联的 `onclick="xxx()"` 之类写法（`smart-canvas.js` 里有不少这种内联事件绑定，不能要求一次性清理干净）。

### 3.2 目录结构调整

```
frontend/                      # 新增：前端源码目录（构建输入）
├── package.json
├── vite.config.js
├── src/
│   ├── smart-canvas/          # 智能画布模块（本次重构主体）
│   │   ├── main.js            # 入口：import 各子模块，挂载必要的 window.xxx 兼容层
│   │   ├── state.js           # 画布全局状态：nodes / canvas / viewport / selection 等
│   │   ├── i18n.js            # re-export 现有 i18n 逻辑（暂不改动 i18n 内部实现）
│   │   ├── node-layout.js     # imageLayout / nodeRect / smartLoopHeight 等布局计算
│   │   ├── node-model.js       # createNode / cloneSmartNode / normalizeLegacySmartNode 等节点数据模型
│   │   ├── connections.js     # addConnection / connectInputNode / renderConnections 等连线逻辑
│   │   ├── loop-node.js        # 循环节点：smartLoopCount / smartLoopInputImages / cloneLoopChainForRound 等
│   │   ├── cascade-run.js      # runSmartCascade / runGeneration / 各 provider 的生成调用
│   │   ├── prompt-node.js      # Prompt 节点相关
│   │   ├── image-editor.js     # 图片编辑器（裁剪/蒙版/画笔/文字工具等，openImageEditor 及其子函数）
│   │   ├── asset-library.js    # 素材库面板
│   │   ├── canvas-render.js    # render() 主渲染循环、DOM 绑定（bindNodeEvents 等）
│   │   ├── upload.js           # 上传/拖拽/配额弹窗
│   │   └── utils.js            # 通用工具（escapeHtml / uid / trf 等无状态函数）
│   ├── canvas-legacy/          # 普通画布：整体搬入但不拆分，作为一个大模块直接引用
│   │   └── canvas.js           # 直接拷贝现有 canvas.js，仅做「能被构建工具正确打包」所需的最小改动
│   └── shared/                 # 真正跨两个画布复用的基础设施（谨慎抽取，避免过度设计）
│       ├── theme.js
│       └── i18n-core.js
├── static-src/                 # 现有 static/ 下不参与构建的资源（图片、vendor 第三方库等）原样保留
└── dist/                       # 构建产物，FastAPI 静态挂载指向这里（替代现在直接挂载 static/js|css）
```

**关于 `canvas-legacy/`**：按约定不重构其内部结构，只做"搬进构建流程"这一件事——目的是让它和智能画布共享同一套构建/部署流程，避免维护两套静态资源发布方式。如果搬入过程中发现任何一点行为风险，优先选择**保持 `canvas.js` 完全不动、继续用现有 `<script src>` 方式加载**，不为了统一而引入风险。

### 3.3 迁移期间的兼容策略：新旧并存

不做"一次性切换"，而是让 Vite 构建产物与现有 `<script src>` 方式**并存**，通过 HTML 里的 script 引入方式区分：

- `smart-canvas.html`：逐步把 `<script src="/static/js/smart-canvas.js">` 换成 `<script type="module" src="/dist/smart-canvas/main.js">`，且**只在完成对应功能域拆分并验证通过后**才切换，未拆分完的部分继续保留在原 `smart-canvas.js` 里，两者通过 `window` 上挂载的共享状态对象过渡期共存。
- `canvas.html`：不改动，继续用现有加载方式。

这样可以让重构按模块逐步推进、逐步上线，而不是憋一个大版本切换（大版本切换回归测试成本高、风险大，与"页面功能完全不变"的约束冲突）。

## 四、`smart-canvas.js` 拆分方案（核心工作）

### 4.1 拆分依据

按 `code` 工具生成的文档符号（`get_document_symbols`）梳理出的自然边界，与函数间调用关系聚类，得到以下 12 个功能域。括号内为当前文件里对应的代表性函数/行号区间（会随后续改动漂移，仅供定位参考）：

| 模块 | 职责 | 代表函数 | 大致行数占比 |
|------|------|---------|------------|
| `state.js` | 全局状态定义（`nodes`/`canvas`/`viewport`/`selectedId` 等） | 顶层 `let`/`const` 声明区 | ~3% |
| `node-layout.js` | 节点尺寸/位置计算 | `imageLayout`, `nodeRect`, `smartLoopHeight`, `smartGroupLayoutSize` | ~8% |
| `node-model.js` | 节点数据模型的创建/克隆/规范化 | `createNode`, `cloneSmartNode`, `normalizeLegacySmartNode` | ~6% |
| `connections.js` | 连线数据与渲染 | `addConnection`, `connectInputNode`, `renderConnections`, `handlePortDrop` | ~8% |
| `loop-node.js` | 循环节点专属逻辑 | `smartLoopCount`, `smartLoopInputImages`, `cloneLoopChainForRound`, `bindLoopNodeControls` | ~7%（近期改动最密集的区域，优先拆） |
| `cascade-run.js` | 一键运行/级联生成调度 | `runSmartCascade`, `runGeneration`, `runComfyGeneration`, `runApiGeneration` | ~15% |
| `prompt-node.js` | Prompt 节点 | `bindPromptNodeControls`, `promptNodeBodyHtml` | ~3% |
| `image-editor.js` | 图片编辑器（裁剪/蒙版/画笔/文字/九宫格拼合等） | `openImageEditor`, `applyImageCrop`, `applyImageMask`, `renderGridJoinPreview` | ~18%（体量最大，内部再按工具细分） |
| `asset-library.js` | 素材库面板 | `renderAssetLibrary`, `bindAssetItemEvents` | ~5% |
| `canvas-render.js` | 主渲染循环、节点 DOM 事件绑定 | `render`, `bindNodeEvents`, `updateComposer` | ~12% |
| `upload.js` | 上传/拖拽/配额弹窗 | `uploadFiles`, `handleFiles`, `checkQuotaWarningFromResult` | ~5% |
| `utils.js` | 无状态工具函数 | `escapeHtml`, `uid`, `trf`, `nowMs` | ~2% |

其余（右键菜单、快捷键、历史记录/撤销、小地图、预览对比等）归入以上模块或视情况单独再拆，不在本计划中逐一列出，执行阶段按实际调用关系确定归属。

### 4.2 拆分原则

1. **先拆低耦合、高频改动的模块**：`loop-node.js` 是最近几周改动最密集的区域（循环节点排布、次数计算等），优先拆出来能立刻获得"改动前后可自动对比"的收益。
2. **State 单一来源**：`nodes` / `canvas` / `viewport` / `selectedId` 等全局状态集中到 `state.js`，其他模块通过 `import { getState, ... } from './state.js'` 访问，不允许模块内自建影子状态。这是消除"全局作用域共享 289 个变量"问题的关键一步。
3. **保留函数签名与行为**：拆分阶段**不重命名、不改签名、不改内部逻辑**，只做"剪切-粘贴-补 import/export"，把行为变更完全排除在这一阶段之外。
4. **循环依赖处理**：现有代码里函数互相调用非常密集（比如 `render()` 会调用几乎所有模块的渲染函数），允许模块间循环 `import`（ES module 原生支持），不强行拆出额外的间接层。

### 4.3 拆分顺序（分批次，每批可独立验证上线）

1. **第 0 批**：搭建 Vite + 构建产物挂载，`smart-canvas.js` 整体不拆，只是原样作为一个 chunk 被 Vite 打包（验证构建链路本身可用，不改变任何行为）。
2. **第 1 批**：拆 `utils.js` + `state.js`（无副作用/低风险，其他模块的地基）。
3. **第 2 批**：拆 `loop-node.js`（最近改动最多，优先建立测试保护网）。
4. **第 3 批**：拆 `node-layout.js` + `node-model.js`。
5. **第 4 批**：拆 `connections.js`。
6. **第 5 批**：拆 `cascade-run.js`（体量大、调用链深，放在前面几批验证通过、模式跑通之后再做）。
7. **第 6 批**：拆 `canvas-render.js`（依赖前面所有模块，必须最后拆）。
8. **第 7 批**：拆剩余的 `image-editor.js` / `asset-library.js` / `prompt-node.js` / `upload.js`。

每一批的验证标准见「五、验证与安全网」。

## 五、验证与安全网

### 5.1 引入前端测试框架：Vitest

选择 Vitest（而非 Jest）的理由：与 Vite 共享配置和转换管线，零额外配置成本，速度快。

### 5.2 分层测试策略

| 层级 | 覆盖内容 | 示例 |
|------|---------|------|
| 纯函数单元测试 | `node-layout.js` / `loop-node.js` 里不依赖 DOM 的计算函数 | `smartLoopCount({imageInput:true, imageBatchSize:2}, images=[10张])` 应返回 5 |
| 布局快照测试 | 给定一组 mock 节点数据，断言 `cloneLoopChainForRound` 产出的每个节点的 `x`/`y` 不重叠 | 对应本次会话里修的"循环节点 Y 轴重叠"问题，转成永久回归测试 |
| DOM 渲染快照 | 用 `happy-dom` 或 `jsdom` 跑 `render()`，断言关键 DOM 结构（节点数量、connection SVG path 数量）符合预期 | 类似后端的 `route_baseline.json`，建一份"渲染契约基线" |
| 手动回归清单 | 无法自动化的交互（拖拽连线、图片编辑器画笔）列成清单，每次重大改动后人工过一遍 | 写入 `docs/` 下的手测清单文档 |

### 5.3 每批拆分的验证流程

1. 拆分前：对当前行为跑一遍手动回归清单，记录基线截图/状态（如已有单测则跑单测）。
2. 拆分：按 4.2 的原则做剪切式迁移。
3. 拆分后：
   - `node --check` 语法检查（延续现在的最低要求）。
   - 跑该模块的单元测试（新建的）。
   - 跑 DOM 渲染快照测试（如涉及渲染相关模块）。
   - 在浏览器里手动过一遍该功能域的回归清单。
4. 只有以上全部通过才合并，每批独立提交、独立可回滚。

## 六、代码质量基础设施

### 6.1 ESLint

- 使用 `eslint` 官方推荐规则 + 少量项目定制规则（如禁止 `catch(_) {}` 空块、强制 `innerHTML` 赋值前必须经过 `escapeHtml` 或明确标注 `// trusted-html` 豁免注释）。
- 先跑一遍现有 `smart-canvas.js` 生成报告，**不要求一次性清零**，按"新增代码零警告、历史代码逐步清理"的策略执行，避免为了修 lint 而做大量无关改动。

### 6.2 Prettier

- 统一格式化风格，只对新拆出的模块生效；未拆分完的旧代码保持原样，避免一次性格式化产生海量无意义 diff。

### 6.3 CI 集成

- 在现有 CI（如有）或至少在 PR 流程里跑：`vite build` + `vitest run` + `eslint`，任一失败阻止合并。
- 与后端的 `pytest`（`tests/test_route_snapshot.py` 等）并列执行，形成前后端统一的质量门槛。

## 七、`canvas.js`（普通画布）的最小化处理

按本次约定，仅做以下两件事，不做更多：

1. **纳入 Vite 构建流程作为一个整体 chunk**（如果第 0 批构建链路搭建顺利、风险可控）：直接把整份 `canvas.js` 作为一个入口文件交给 Vite 打包，不拆分内部结构。目的仅是让它和智能画布共用同一套构建/部署方式，减少运维两套静态资源发布逻辑的成本。
2. **回归验证**：每次涉及共享基础设施（`theme.js`、`i18n.js`、构建配置）的改动后，必须验证 `canvas.html` 依然能正常打开、核心操作（创建节点、连线、保存画布）不受影响。

如果在第 0 批验证中发现把 `canvas.js` 纳入构建流程有任何不确定的风险（比如它依赖了某些全局执行时机、`<script>` 顺序敏感的行为），**立即放弃第 1 点，让 `canvas.js` 继续用现有 `<script src>` 方式加载，不做任何改动**。这条是本计划里唯一允许"直接放弃"的分支，因为它完全符合用户"不需要重构、不需要消耗太多成本"的要求。

## 八、后续可选项（不在本次计划范围内，仅供参考）

- **TypeScript 化**：等 ES module 拆分稳定运行一段时间后，可以逐模块加 `.d.ts` 或直接改 `.ts`，优先级最低。
- **状态管理库**：如果 `state.js` 变得复杂到手写状态同步逻辑难以维护，可以考虑引入轻量状态管理（如 nanostores），但目前的状态规模不足以支撑这个投入。
- **`canvas.js` 的正式重构**：如果未来产品决定加大对"普通画布"的投入，可以参照本文档第四节的方法论重新评估，届时应作为独立计划。

## 九、里程碑与验收标准

| 里程碑 | 内容 | 验收标准 |
|--------|------|---------|
| M0 | Vite 构建链路搭建 | `vite build` 产出的 `smart-canvas.html` 打开后功能与现状零差异；Tailwind 改为构建期编译 |
| M1 | `utils.js` + `state.js` 拆出 | 单元测试通过；`smart-canvas.html` 功能回归清单全过 |
| M2 | `loop-node.js` 拆出 + 布局快照测试建立 | 循环节点相关的所有已知 bug（本次会话修的几个）转为永久回归测试并通过 |
| M3 | `node-layout.js` / `node-model.js` / `connections.js` 拆出 | 对应回归清单通过 |
| M4 | `cascade-run.js` 拆出 | 一键运行/循环级联的端到端手测通过 |
| M5 | `canvas-render.js` 拆出，`smart-canvas.js` 剩余部分清空或收敛为极小的兼容层 | 整体功能回归清单全过，`smart-canvas.js` 原文件基本退役 |
| M6 | ESLint + Prettier 接入 CI | 新增代码零警告 |
| M7（可选） | `canvas.js` 纳入构建流程（若 M0 验证风险可控） | `canvas.html` 功能零差异；若风险不可控则跳过，保留现状 |

每个里程碑之间没有强制时间要求，建议按团队实际迭代节奏安排，核心原则是**每完成一个里程碑就是一个可稳定运行的状态**，不允许出现"重构进行到一半、新旧代码混杂导致不可用"的中间态。
