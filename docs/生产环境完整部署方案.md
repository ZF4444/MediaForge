# MediaForge 单机多容器生产部署方案与操作流程

本文替代旧 Docker 部署文档及旧生产部署方案，是当前生产部署入口。业务架构、安装参考等其他文档保留；PostgreSQL、Redis、MinIO 的原生安装教程不再作为本方案的安装步骤。

## 1. 已确定的部署方式

- 同一台 Debian 12 服务器：8 个逻辑 CPU、约 8 GiB 内存，数据盘挂载 `/data`。
- 五个独立容器：API、画布 Worker、PostgreSQL、Redis、MinIO，属于同一个 Compose 项目。
- 所有容器共享宿主机内存，不设置 `mem_limit`、内存 reservation 或 `deploy.resources`；不关闭 OOM killer，也不禁用 Swap。
- Redis 不配置 `maxmemory`，使用 `noeviction`，避免把会话、任务和队列当作普通缓存淘汰。该策略不会阻止整机内存耗尽。
- 应用单 API 进程，画布任务交给独立 Worker；Agent 命令消费、事件 outbox、WebSocket Pub/Sub 和定期维护保留在 API。不要直接扩容 API，否则要先重新分配后台职责。
- Nginx 在宿主机终止 HTTPS，转发至回环端口 3000。PostgreSQL、Redis 不发布宿主机端口；MinIO API/控制台仅发布到回环 19000/19001。
- 应用、配置、工作流、日志和中间文件存放 `/data/mediaforge`，不放容器可写层。

容器化提供部署可重复性与服务隔离，不提供机器级高可用。机器、数据盘、Docker 故障仍会影响全站。正式切换前需要完成恢复演练和异机备份。

配置对应关系：

| 文件 | 用途 |
| --- | --- |
| `Dockerfile` | 前端构建、Python 锁文件依赖、FFmpeg 和应用运行镜像 |
| `.dockerignore` | 排除密钥、本地依赖、数据、日志等构建上下文 |
| `config/deploy/compose.yml` | 五个容器、健康检查、网络和持久化 |
| `config/dev/.env.example` | 本地开发模板，复制为 `config/.env`，不用于生产部署 |
| `config/deploy/.env.example` | 生产 Docker 部署模板，复制为 `config/deploy/.env` |
| `config/deploy/minio.Dockerfile` | 从固定上游版本源码构建 MinIO |
| `config/deploy/nginx.conf` | 宿主机反向代理模板 |

## 2. 先盘点原生产环境

迁移前记录旧应用版本、Python 版本、PostgreSQL 主版本及扩展、Redis 版本和 ACL、MinIO 版本及桶配置。确认实际数据目录和远端服务地址，不要根据默认值猜测。

同时盘点：数据库大小、MinIO 对象数量/总大小/版本控制、旧 `data/`、`config/`、`workflows/`、供应商密钥、定时任务、域名和证书。保留旧 `APP_SECRET_KEY`，重新生成会导致已有加密连接凭据无法解密。

先决定停机窗口、允许丢失数据的时间（RPO）、恢复时间（RTO），至少做一次完整备份与恢复验证。旧、新应用不能同时消费同一条任务队列。已有生成任务应先排空或确认如何处理，防止上游重复提交计费。

默认 PostgreSQL 镜像为 16，Redis 为 7.4，只是新部署起点。迁移现有服务必须核对兼容性；优先同主版本完成迁移，再另开窗口升级。不得把不同 PostgreSQL 主版本的数据目录直接挂入容器。

## 3. 安装 Docker（Debian 12，root 执行）

先检查是否已有 Docker、containerd、Podman 和旧服务；有其他工作负载时先评估冲突，不盲目卸载。全新 Debian 主机可使用官方 apt 仓库：

```bash
apt-get update
apt-get install -y ca-certificates curl
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
cat > /etc/apt/sources.list.d/docker.sources <<'SOURCES'
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: bookworm
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
SOURCES
apt-get update
apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker
docker version
docker compose version
```

上面架构针对本机；其他架构需调整。若改 Docker 数据根目录，应在首次运行工作负载前规划，并合并已有 `daemon.json`，不要覆盖现有配置。当前系统盘约 62 GB，镜像和构建缓存可能占满系统盘，需监控 `docker system df`。

## 4. 准备环境和持久化目录

以下操作均从项目根执行；所有命令使用同一份环境文件、Compose 文件和项目名。

```bash
cd /data/workspace/MediaForge
cp config/deploy/.env.example config/deploy/.env
chmod 600 config/deploy/.env
# 每个新密码分别执行一次，复制输出到 config/deploy/.env
openssl rand -hex 32
```

编辑 `config/deploy/.env`，替换所有 `CHANGE_ME`、域名和镜像标签。新密码建议使用十六进制，避免数据库 URL 中的特殊字符编码问题。旧密码含特殊字符时应改为正确 URL 编码的连接串，不能直接使用模板插值。

`APP_IMAGE` 每次发布使用唯一标签；基础镜像在验收后记录实际 digest，可把镜像值换成 `image@sha256:...`。本地构建的应用和 MinIO 镜像应推送私有仓库或 `docker save` 异机保存，不能只依赖本机缓存。

MinIO 上游目前采用源码分发，仓库已归档，不沿用旧 `minio/minio:latest`。此处从固定发布标签构建作为兼容迁移基线，并非承诺该旧版本持续获得安全更新。正式生产需审核其安全维护状态与现有数据兼容性；有内部审核的维护镜像时，填写 `MINIO_IMAGE`，拉取该镜像并跳过 MinIO 构建，不能让 `build` 覆盖它。版本或源码 ref 变更必须同时更换镜像标签。

```bash
# 定义 dc 快捷命令，统一指定部署环境文件和 Compose 文件，并透传后续参数；重新登录后需重新定义
dc() { docker compose --env-file config/deploy/.env -f config/deploy/compose.yml "$@"; }

# 查看 /data 的挂载信息，确认数据盘已挂载后再创建目录
findmnt /data
# 创建数据根目录，权限 0750：所有者可读写进入，同组可读取和进入，其他用户无权限
install -d -m 0750 /data/mediaforge
# 创建应用、临时文件、缓存、日志、配置、工作流及 MinIO 目录，归属容器运行用户 UID/GID 10001
install -d -o 10001 -g 10001 -m 0750 \
  /data/mediaforge/app /data/mediaforge/app/tmp /data/mediaforge/app/cache \
  /data/mediaforge/logs /data/mediaforge/config /data/mediaforge/workflows \
  /data/mediaforge/minio
# 创建数据库、Redis 和备份目录，权限 0700：仅所有者可访问；数据库和 Redis 的目录权限由镜像首次启动时初始化
install -d -m 0700 /data/mediaforge/postgres /data/mediaforge/redis /data/mediaforge/backups
```

如果修改 `DATA_ROOT`，必须同步修改上面的路径和后续备份路径。`/data` 必须已挂载，避免把数据误写系统盘；配置开机挂载，确保它在 Docker 恢复容器前可用。PostgreSQL/Redis 官方镜像首次启动负责初始化目录权限，应用和自建 MinIO 使用 UID 10001。

生产 Docker 部署以 `config/deploy/.env` 为唯一配置来源，由 Compose 注入 API 和 Worker；不要求创建或维护 `/data/mediaforge/config/.env`。配置目录仍整体挂载到容器的 `/app/config`，用于兼容旧原生部署迁移和保留应用运行文件；全新生产部署可以为空。迁移时只复制仍需使用的应用环境配置和工作流并修正权限。不要在应用配置中重复写入 `DATABASE_URL`、`REDIS_URL`、`MINIO_*` 等基础设施连接设置，连接统一由 Compose 注入，也不要把部署密码重复复制到应用配置目录。

ComfyUI 实例地址也作为 `comfyui` 连接的 Base URL 保存在数据库；旧 `COMFYUI_INSTANCES` 不再读取或自动导入，升级前应在 API 设置中录入地址并关联工作流资源。Docker 内不要用 `127.0.0.1` 指向宿主机 ComfyUI。

AI 连接、模型和资源保存在 PostgreSQL，供应商 API Key 等连接凭据加密保存在 `ai_connection_secrets` 表，由 API 设置页面维护，不写入应用 `.env`。部署文件中的 `APP_SECRET_KEY` 是加解密主密钥，必须长期固定，API 和 Worker 使用同一个值。当前 AI 连接执行链路不读取旧 `COMFLY_API_KEY`、`MODELSCOPE_API_KEY`、`RUNNINGHUB_API_KEY` 作为凭据；迁移旧环境时不能只复制这些变量，应验证数据库中的连接配置与密钥已迁移成功。

API 和 Worker 共享应用配置目录及数据库；数据库业务配置保存后跨进程刷新依赖应用机制。修改部署环境变量需重新创建容器，单纯 `restart` 不会加载新的 Compose 环境。

## 5. 构建、检查和首次启动

```bash
# -q 避免把展开后的密码输出到终端或日志
# 校验 Compose 配置、环境变量和服务定义是否有效；不启动容器
dc config -q
# 拉取 PostgreSQL 和 Redis 基础镜像，避免启动时临时下载
dc pull postgres redis
# 一次构建一个服务，降低本机构建时的资源争抢
# 构建固定源码版本的 MinIO 镜像
dc build minio
# 构建应用镜像，包含后端依赖和前端静态文件
dc build api
# 后台启动数据库、缓存和对象存储，并等待它们通过健康检查
dc up -d --wait postgres redis minio
```

Go 编译及前端构建会使用 CPU、内存和系统盘缓存。正式业务运行后优先在 CI/其他机器构建，再拉取经过验收的镜像。无内存限额不代表可以无限并行构建。

**新安装（无生产数据迁移）**可继续：

```bash
# 后台启动 API，并等待 API 健康检查通过
dc up -d --wait api
# 后台启动画布 Worker；Worker 没有 HTTP 健康检查，因此不使用 --wait
dc up -d worker
# 查看 API、Worker 及依赖服务的运行状态
dc ps
# 查看 API 和 Worker 最近 100 行日志，用于确认启动结果
dc logs --tail=100 api worker
# 检查进程存活接口；请求失败时返回非零退出码
curl -fsS http://127.0.0.1:3000/health/live
# 检查应用及数据库、Redis、MinIO 等依赖是否已就绪
curl -fsS http://127.0.0.1:3000/health/ready
```

**有生产数据迁移**时，先按第 6 节恢复，再启动应用；不要让新应用对待恢复的数据库先执行初始化。API 成功启动后再启动 Worker，避免并行首次初始化。

`CANVAS_TASK_WORKER_CONCURRENCY=10` 是起步并发配置，可按供应商配额和负载调整；它不是内存限额。Worker 没有 HTTP 健康端口，必须验证任务真实消费，不能仅凭进程为 running 判定正常。Compose 的 unhealthy 状态也不会自动重启容器，`unless-stopped` 主要处理进程退出。

## 6. 原生部署迁移流程

### 6.1 确认迁移范围和预演环境

迁移不是只搬 PostgreSQL。以下内容必须来自同一个停写窗口，并记录源位置、目标位置和校验结果：

| 内容 | 新环境位置 | 核对重点 |
| --- | --- | --- |
| PostgreSQL 业务库 | Compose 的 `postgres` 服务 | 用户、文件元数据、任务、AI 连接及加密凭据 |
| MinIO 完整数据或 S3 对象 | `/data/mediaforge/minio` | 桶名、对象、版本、策略和权限 |
| Redis 持久化数据 | `/data/mediaforge/redis` | 会话、队列、Streams 消费组及 pending |
| 旧应用 `data/` | `/data/mediaforge/app` | 本地文件、任务中间文件及实际仍被引用的路径 |
| 旧应用配置、工作流 | `/data/mediaforge/config`、`/data/mediaforge/workflows` | 保留必要文件，修正旧绝对路径和服务地址 |
| 原 `APP_SECRET_KEY` | `config/deploy/.env` | 原值保留，API 与 Worker 一致 |

先完成第 2～4 节，构建好镜像。迁移不同时升级数据库主版本或更换 MinIO 存储布局；确需升级时，必须先完成兼容性预演。以下命令沿用第 4 节的 `dc`，默认 `DATA_ROOT=/data/mediaforge`，从项目根目录执行。

预演使用另一台机器最直接。同机预演必须同时隔离 Compose 项目名、`DATA_ROOT`、数据库和桶、宿主机端口；仅修改项目名仍会冲突，因为模板固定绑定了 3000、19000、19001。不能让预演应用连接生产 PostgreSQL、Redis 或 MinIO。

用一份完整备份走通 6.3～6.6，隔离公网入口，并阻断预演环境访问真实供应商，防止恢复出的任务自动提交计费。API 自身也会运行 Agent 消费和定期维护，不能认为“不启动 Worker”就没有后台写入。验证登录、权限、文件、模型配置、WebSocket、Agent 和画布任务；真实生成验证使用明确授权的测试连接。记录备份、传输、恢复耗时、磁盘峰值，以及旧服务恢复入口的方法，据此确定停机窗口。

### 6.2 进入维护窗口并冻结旧环境

按以下顺序操作，每一步成功后再继续；命令失败时停止切换，不要直接粘贴执行后续步骤。

1. 提前准备好新镜像、部署配置、证书和反向代理配置，检查 `dc config -q`。确认新容器端口不与旧进程冲突；同机迁移需要先释放旧应用的 3000 端口，或预先修改新端口及反向代理。
2. 入口进入维护状态，停止接受新的生成、上传和其他写请求。单纯隐藏页面不足以停写，还应阻止 API 请求、WebSocket 写入及外部自动化调用。
3. 保持旧消费者运行，观察并排空已提交的任务。仍在供应商执行的任务要记录任务 ID 和状态；无法排空时，应先确定恢复后如何查询、接续，不能直接重新提交。
4. 停止旧 API、Worker、定时任务及其他写入方，再开始最终备份。旧进程可能由 systemd、Supervisor、Docker 或 cron 管理，应使用现场实际服务名停止，并禁用其自动拉起。记录原启动命令和启用状态，供回滚使用。
5. 确认旧应用进程已退出、没有其他客户端继续写入数据库/Redis/MinIO。此时旧基础服务可暂时运行以完成逻辑导出，离线复制其数据目录前必须再停止对应服务。

保留旧数据库和原始数据目录，最终备份使用新文件名，不覆盖预演备份。记录停写时间、旧版本/镜像、配置与备份校验和。新环境在恢复完成前只允许启动基础服务，不启动 API 或 Worker。

### 6.3 PostgreSQL：导出、恢复和核对

在旧数据库所在主机执行。示例适用于本机 PostgreSQL、存在 `postgres` 系统用户且允许本地认证的部署；其他部署使用实际连接方式和数据库角色。先将 `旧业务库名` 替换为盘点所得值，客户端版本需与源服务兼容，目标 `pg_restore` 需支持该备份格式。

```bash
# 旧机执行：备份目录应位于有足够空间的数据盘，且仅管理员可访问
install -d -m 0700 /data/mediaforge-migration
# 使用自定义格式导出；不要把数据库密码直接写进命令行
sudo -u postgres pg_dump -Fc --dbname='旧业务数据库名' > /data/mediaforge-migration/final.dump
# 检查命令退出码，并确认归档目录可读；此检查不能代替实际恢复预演
sudo -u postgres pg_restore --list < /data/mediaforge-migration/final.dump > /data/mediaforge-migration/final.list
# 计算备份文件的 SHA-256 校验和，并记录输出；传输到新机后执行相同命令
# 对比两端输出的 64 位十六进制值：一致表示文件内容相同，不一致则停止恢复并重新传输
# 此命令用于检查传输前后文件是否一致，不能证明备份完整或数据库一定能恢复
sha256sum /data/mediaforge-migration/final.dump
```

通过受控 SSH/SCP 将备份传到新机同名目录，同机迁移可直接使用；限制目标文件权限并核对两端 SHA-256。不要将密码、部署 `.env` 或备份上传到代码仓库。

在新机恢复到**确认可用于本次迁移的空业务库**。已有数据的目标库先停止排查，不直接覆盖。官方 PostgreSQL 镜像仅在数据目录为空时依据环境变量初始化数据库；修改 `.env` 不会重设已有库名或密码。

```bash
# 新机执行：只启动数据库，不启动应用
dc up -d --wait postgres
# 恢复到模板配置的目标库，遇到 SQL 错误立即停止
dc exec -T postgres sh -ec 'exec pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --no-acl --exit-on-error' < /data/mediaforge-migration/final.dump
# 更新查询规划统计信息
dc exec -T postgres sh -ec 'exec vacuumdb -U "$POSTGRES_USER" -d "$POSTGRES_DB" --analyze-only'
# 查看恢复后的业务表
dc exec -T postgres sh -ec 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -c "\dt public.*"'
```

对照旧库记录核对关键表的行数和抽样记录，例如 `users`、`files`、`ai_connections`、`ai_connection_secrets`、`ai_models`、`ai_resources`，以及实际使用的画布/任务表。按实际 schema 查询；不要把密钥字段打印到终端。大表精确计数可能耗时，应在预演阶段确定核对方式。

`--no-owner --no-acl` 不恢复原角色归属和授权；业务库所需扩展、额外角色和权限应单独盘点并准备。恢复失败后不要启动应用，也不要在部分恢复的库上反复导入。由管理员确认目标确实可丢弃后，重新准备空库再恢复，不能删除旧生产库。

### 6.4 MinIO 和应用目录：停服复制、修正权限

先选定并预演以下一种 MinIO 迁移方式：

- **离线完整复制**：仅用于已经验证源/目标 MinIO 版本、存储布局兼容，且源为完整单机数据目录的情况。源与目标 MinIO 都必须停止，复制整个数据根目录，包括隐藏的 `.minio.sys`，不能仅复制可见的桶目录。
- **通过 S3 接口迁移**：源/目标 MinIO 运行、应用写入保持停止。使用经过预演的 S3 工具复制对象，单独迁移桶策略、用户和配置。有版本控制、保留策略或对象锁时，必须验证工具是否保留历史版本和相应语义，不能把普通对象 mirror 当作完整迁移。

以下为**旧数据已安全暂存到新机**后的离线复制示例。`/path/to/staged/...` 必须替换为真实暂存目录；它们不能指向新环境目标目录。`rsync` 需提前安装，源目录末尾 `/` 表示复制目录内容。

```bash
# 旧 MinIO 也必须已通过原部署方式停止
dc stop minio
# 先预览源、目标是否正确；确认后使用下一条实际复制
rsync -aHn -- /path/to/staged/minio/ /data/mediaforge/minio/
rsync -aH -- /path/to/staged/minio/ /data/mediaforge/minio/
# 旧应用已停止，新 API/Worker 尚未启动
rsync -aH -- /path/to/staged/data/ /data/mediaforge/app/
rsync -aH -- /path/to/staged/workflows/ /data/mediaforge/workflows/
# 配置文件按第 4 节筛选后复制，不直接覆盖生产部署 .env
chown -R 10001:10001 /data/mediaforge/minio /data/mediaforge/app \
  /data/mediaforge/config /data/mediaforge/workflows
dc up -d --wait minio
```

目标应为本次迁移准备的干净目录；上述复制不会移除目标多余文件，发现旧残留应先隔离处理，不直接添加 `--delete`。大量文件的权限修正也会占用时间，需计入停机窗口。不要递归修改 PostgreSQL、Redis 目录为 UID 10001。

启动 MinIO 后，通过受控 S3 客户端或控制台核对桶名、对象数量、总大小、关键对象可读取性及策略。控制台可使用 `ssh -N -L 19001:127.0.0.1:19001 用户@新服务器`，再从本机访问 `http://127.0.0.1:19001`。有版本控制时还要核对版本和删除标记；对象数量/大小相同不能替代内容抽样校验。检查数据库文件引用对应的桶、对象键和应用本地路径仍有效。

### 6.5 Redis：确认持久化格式后恢复

Redis 承载会话和任务，不能通过清空队列来消除迁移错误。先在旧实例使用已认证的 `redis-cli` 记录：

```text
INFO server
INFO keyspace
INFO persistence
CONFIG GET dir
CONFIG GET dbfilename
CONFIG GET appendonly
CONFIG GET appenddirname
```

同时记录实际使用的逻辑库、队列/Stream 键，使用 `XLEN`、`XINFO GROUPS`、`XPENDING` 核对长度、消费组及 pending；这些命令需补充真实 Stream 键和组名。避免生产执行 `KEYS *`，遍历应使用 `SCAN`，也不要把会话内容输出到日志。

模板目标 Redis 启用了 `--appendonly yes`，按源数据分别处理：

- **源启用 AOF**：旧应用停写后正常停止旧 Redis，检查退出日志和持久化结果，再复制完整持久化文件集合。Redis 7 多段 AOF 需要完整的 manifest、base 和增量文件，不能只挑一个 `.aof` 文件；源为旧单文件 AOF 时须先预演升级加载流程。
- **源只有 RDB**：停写后执行并确认一次成功快照，再正常停止旧 Redis。先在隔离实例以 `appendonly no` 加载 RDB，核对数据后启用 AOF，等待重写完成并确认持久化无错误，再正常停服取得完整 AOF 数据，用于本模板目标。该转换必须提前预演，不能把 `dump.rdb` 放进已有 AOF 的目标目录就假定会被加载。
- **源未启用持久化**：停写后先生成并验证快照，再按 RDB 路线处理；不能直接停止服务后再寻找备份。

新 Redis 必须停止后才能放置文件。第 5 节如果已经启动过目标 Redis，会产生新的空 AOF；先将这份目标初始化数据移出到独立留存目录，恢复到干净目录，避免与源文件混用。不要删除旧生产数据。

```bash
dc stop redis
# 将已验证的完整持久化数据复制到干净的目标目录
rsync -aH -- /path/to/staged/redis/ /data/mediaforge/redis/
# 模板使用官方镜像以 root 入口启动，由入口脚本修正 /data 文件归属
dc up -d --wait redis
dc logs --tail=100 redis
# 查看实际加载结果；认证信息从容器环境读取，不在命令行展开密码
dc exec -T redis sh -ec 'export REDISCLI_AUTH="$REDIS_PASSWORD"; redis-cli INFO keyspace; redis-cli INFO persistence'
```

确认无加载错误，AOF 已启用、持久化状态正常；对比各逻辑库键数、关键队列、消费组和 pending，并考虑 TTL 在停机期间继续流逝导致的合理差异。旧 ACL 用户不会自动变成模板的默认用户，需核对应用认证方式。完成前不启动 API/Worker，禁止用 `FLUSHALL` 或删除 Stream 的方式“修复”差异。

### 6.6 启动新应用、验收与放开入口

先确认数据库、对象、本地文件和 Redis 全部恢复完毕；原 `APP_SECRET_KEY` 已填入部署文件；基础服务地址已改为 Compose 网络地址，公网 URL 与实际 HTTPS 域名一致。再次确认旧消费者不会自动重启。

```bash
# 校验部署环境变量和 Compose 配置；-q 不输出展开后的配置，避免泄露密码
# 校验失败应先修正，不继续启动后续服务
dc config -q
# 后台启动 PostgreSQL、Redis、MinIO，并等待三项服务健康检查通过
# 若等待失败，先检查对应服务日志，不继续启动 API
dc up -d --wait postgres redis minio
# API 会执行初始化及部分后台工作，从此刻起新环境可能产生写入
# 后台启动 API，等待应用就绪健康检查通过；此时公共入口仍应保持维护状态
dc up -d --wait api
# 查看 API 最近 100 行日志，排查数据库初始化、凭据解密及依赖连接错误
dc logs --tail=100 api
# 通过宿主机回环端口检查应用就绪状态；HTTP 错误或连接失败会返回非零退出码
# 请求失败时停止后续步骤，不能仅凭容器 running 判断应用已就绪
curl -fsS http://127.0.0.1:3000/health/ready
# API 就绪且日志无迁移/解密/依赖错误后，才启动画布 Worker
# Worker 没有 HTTP 健康检查，此处不使用 --wait；启动后仍需验证真实任务消费
dc up -d worker
# 查看 Worker 最近 100 行日志，确认启动及队列连接情况，排查任务执行错误
dc logs --tail=100 worker
# 汇总查看五个服务的运行状态和已有健康检查结果，确认没有退出或反复重启
dc ps
```

保持公共入口维护状态，先通过受控入口验证旧用户登录、已有文件读取、供应商凭据可解密、工作流资源关联、WebSocket 和任务状态。再按第 7 节启用新 HTTPS 入口并执行第 8 节验收，确认 Worker 实际消费一个受控测试任务，最后放开用户写入。就绪接口成功不能代替业务验收。

记录放开入口时间和首批任务 ID，观察错误率、任务积压、容器重启、内存及磁盘。旧数据和最终备份保留至约定观察期结束，且异机备份、恢复演练完成后，才安排清理。

### 6.7 失败处理与回滚边界

- **新应用尚未启动**：恢复或核对失败就保持维护入口，新 API/Worker 保持停止。需要恢复旧服务时，先确认新环境无消费者，再按原启动方式恢复旧基础服务、旧应用及入口，核对自动启动设置。
- **新 API 或 Worker 已启动**：即使尚未开放公网，也可能已有任务消费、数据库初始化或后台写入。先停新 API/Worker并保存日志、任务状态与数据快照，确认是否产生供应商调用和新数据；不能直接启动旧消费者重新执行同一批任务。
- **新环境已接受用户写入**：不能直接切回停写时的旧库，否则会丢失新用户、上传和任务变更。再次进入维护状态、停止新写入，评估能否将最新数据兼容恢复到旧版本，或在新环境修复。旧版本不兼容新 schema 时，按预演过的恢复方案处理，并明确 RPO/RTO 和受影响数据。

任何回滚都必须确保只有一套应用消费任务。不要同时让旧、新应用连接同一个 Redis 队列，也不要在新版已修改的数据目录上直接启动旧版基础服务。

## 7. Nginx 与 HTTPS

```bash
# 安装 Nginx 反向代理、Let's Encrypt 客户端及 Nginx 集成插件
apt-get install -y nginx certbot python3-certbot-nginx
# 将项目提供的 Nginx 配置复制到系统站点配置目录
cp config/deploy/nginx.conf /etc/nginx/sites-available/mediaforge
# 编辑 server_name，确认 DNS 指向本机
# 启用该站点；目标文件已存在时不要重复创建链接
ln -s /etc/nginx/sites-available/mediaforge /etc/nginx/sites-enabled/mediaforge
# 检查 Nginx 配置语法和引用文件是否正确，不会 reload 配置
nginx -t
# 让 Nginx 重新加载配置，已建立的连接通常不会中断
systemctl reload nginx
# 为指定域名申请证书，并自动修改 Nginx 配置启用 HTTPS
certbot --nginx -d media.example.com
# 在不真正签发证书的情况下演练自动续期流程
certbot renew --dry-run
```

已有 Nginx/证书/网关时合并现有配置，不重复创建冲突站点。公网只开放必要的 80/443 和受控 SSH，不能开放 PostgreSQL、Redis、MinIO 管理端口。容器信任代理头的前提是应用入口仅由可信网关访问。

`PUBLIC_BASE_URL` 和 `PUBLIC_MEDIA_BASE_URL` 设置为实际 HTTPS 地址；模型供应商必须能访问应用签发的素材链接。浏览器或供应商不能使用容器内地址 `minio:9000`。访问 MinIO 控制台可通过 SSH 隧道，不直接公开私有桶。

## 8. 验收与观察

```bash
# 查看五个服务容器的状态、健康状态和运行信息
dc ps
# 汇总查看 API、Worker、PostgreSQL、Redis、MinIO 最近 100 行日志
dc logs --tail=100 api worker postgres redis minio
# 通过实际访问入口检查 API 及其依赖是否已就绪
curl -fsS https://media.example.com/health/ready
# 查看各容器当前的 CPU、内存、网络和磁盘 I/O 使用情况后退出
docker stats --no-stream
# 查看宿主机内存总量、已用量、可用量和 Swap
free -h
# 查看系统盘和数据盘的容量、已用空间及剩余空间
df -h / /data
# 检查今天内核日志中的 OOM 或进程被杀记录；没有匹配项时仍返回成功
journalctl -k --since today | grep -Ei 'oom|out of memory|killed process' || true
```

人工验证：旧用户登录、文件上传/下载、私有文件权限、生成任务及父子任务、画布实时事件、Agent 交互、供应商配置保存并重启后保留、后台清理及退出恢复。

检查实际容器内存上限为 0（无 Docker 硬上限）：

```bash
for id in $(dc ps -q); do
  docker inspect --format '{{.Name}} memory={{.HostConfig.Memory}} reservation={{.HostConfig.MemoryReservation}} oom={{.State.OOMKilled}}' "$id"
done
```

初期关注整机 `MemAvailable`、持续换页、容器重启、OOM、数据库延迟及磁盘余量。单服务异常可能拖垮整机；不要关闭 OOM killer。观察到问题后再调整应用并发、数据库连接数和资源策略。不能仅根据 Linux free 列偏低判断内存不足。

## 9. 备份和恢复

持久化目录不是备份。本机 backups 只是暂存，备份必须复制到另一台机器/独立存储，附带校验和并限制访问权限。数据库备份包含 AI 连接、模型、资源及加密凭据；必须同时保留原 `APP_SECRET_KEY`，仅备份应用 `.env` 无法恢复供应商配置。备份还需要包含 `config/deploy/.env`、应用环境配置和工作流；含密钥的备份必须加密保存。

下面是最直观的**停机一致备份**：维护入口，排空任务并停 API/Worker，在线导出 PostgreSQL，再停止三项依赖，完整归档数据目录。归档期间站点不可用，需预留等同数据量的空间。

```bash
umask 077
backup_stamp=$(date -u +%Y%m%dT%H%M%SZ)
backup_dir=/data/mediaforge/backups/$backup_stamp
mkdir -p "$backup_dir"
dc stop api worker
# 导出失败必须停止后续流程并排查，不把失败文件视作有效备份
dc exec -T postgres sh -ec 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_dir/postgres.dump"
dc exec -T postgres pg_restore --list < "$backup_dir/postgres.dump" > "$backup_dir/postgres.list"
dc stop postgres redis minio
tar -C /data/mediaforge -cpf "$backup_dir/state.tar" app config workflows minio redis
cp config/deploy/.env "$backup_dir/deployment.env"
sha256sum "$backup_dir/postgres.dump" "$backup_dir/state.tar" "$backup_dir/deployment.env" > "$backup_dir/SHA256SUMS"
dc up -d --wait postgres redis minio
dc up -d --wait api
dc up -d worker
```

上述命令按步骤执行，每步确认成功再继续；shell 默认不会因单条命令失败自动停止。归档包含密钥，异机传输/存储需加密。该方案不包含 MinIO 在其他外部系统中的 KMS 密钥等外部依赖，如有使用需同步备份。

恢复演练：在隔离环境使用原镜像版本和新数据根目录，验证校验和；先恢复 app/config/workflows/minio/redis（所有对应进程停止），修正权限；启动空 PostgreSQL 并导入 dump；启动 MinIO、Redis、API、Worker，执行完整业务验收。不得在生产实例运行中直接覆盖挂载目录。Redis 和 MinIO 的备份应使用同版本先恢复，再单独测试升级。

若停机备份窗口不可接受，应另行设计 PostgreSQL WAL/PITR、对象版本备份及跨服务恢复点策略。不能把当前逐项在线备份脚本当作跨服务原子快照。

## 10. 发布、回退和常用操作

发布前备份，记录当前 git commit、所有镜像 ID/digest、环境配置及数据恢复点。`APP_IMAGE` 改为新唯一标签，构建/拉取后：

```bash
# 校验部署环境变量和 Compose 配置；-q 不输出展开后的密码等配置
# 校验失败应先修正，不继续发布
dc config -q
# 使用当前代码构建新 APP_IMAGE 标签的应用镜像，API 和 Worker 共用此镜像
# 若使用 CI 已构建并推送的镜像，此步改为 dc pull api worker，不要重新构建覆盖
dc build api
# 短暂停机发布；不重启数据库和存储
# 停止旧 API 和 Worker，等待进程退出；执行前应进入维护状态并排空任务
dc stop api worker
# 使用新镜像/配置启动 API，并等待健康检查通过
# --no-deps 不启动或重建依赖服务，前提是 PostgreSQL、Redis、MinIO 已正常运行
# 若启动或健康检查失败，先检查 API 日志，不继续启动 Worker
dc up -d --no-deps --wait api
# API 就绪后再启动 Worker；它没有 HTTP 健康检查，仍需通过日志和实际任务验证
dc up -d --no-deps worker
# 从宿主机检查应用就绪状态；HTTP 错误或连接失败会返回非零退出码
# 检查通过后仍需完成业务验收、确认 Worker 消费正常，再解除维护状态
curl -fsS http://127.0.0.1:3000/health/ready
```

新版本启动可能自动修改数据库，发布前必须评估 schema 兼容性。代码回退：仅在 schema 兼容时把 `APP_IMAGE` 改回旧标签，直接启动旧镜像，**不要重新 build 覆盖旧镜像**。若不兼容，应进入维护状态并按完整恢复方案回退数据，明确新版本接收写入后的数据损失和补偿。

日常命令（项目根、已定义 dc）：

```bash
dc logs -f --tail=100 api worker
dc restart worker
dc up -d --no-deps api worker   # 应用配置变更后重新创建
dc stop                      # 停止，保留容器和数据
dc down                      # 移除容器/网络，绑定目录数据仍保留
docker system df
```

不要清理 `/data/mediaforge`，不要运行不明来源的 prune/删除数据命令。本文没有自动执行安装、迁移或生产切换。
