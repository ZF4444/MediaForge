# MediaForge 生产环境完整部署方案

> 方案日期：2026-07-13  
> 修订日期：2026-07-29  
> 服务规模：公司内部约 50 人  
> 当前目标：单台专用主机部署 MediaForge、Nginx、PostgreSQL、MinIO、Redis  
> 推理边界：ComfyUI/本地模型部署在独立机器；本方案不包含 GPU 推理资源

> 本次修订依据 2026-07-13 之后的代码变更同步，主要变化：
>
> - **Redis 已成为强制启动依赖**：认证会话缓存改为异步 Redis，未配置 `REDIS_URL` 或 Redis 不可达时应用拒绝启动。单机部署需新增 Redis 服务。
> - **健康检查已内置**：`/health/live`、`/health/ready` 已实现，`ready` 探针同时校验 PostgreSQL、Redis 与 MinIO Bucket，可直接对接监控。
> - **Prometheus 指标已内置**：新增 `/metrics` 端点，导出数据库连接池、MinIO、Redis、阻塞 IO、本地缓存、后台任务等 `mediaforge_*` 指标，无需再为应用层单独部署 exporter。
> - **数据库/存储/网络可靠性增强**：PostgreSQL 改为异步连接池、MinIO SDK 走有界阻塞 IO 适配层、外部 HTTP 调用走共享异步客户端、上传改为流式落盘、新增受管本地存储缓存。均带来新的环境变量。
> - **启动强校验**：MinIO 与 PostgreSQL 必须同时配置，否则启动失败。
> - 仍未变的 P0 风险：认证无密码/SSO 可冒用、会话有效期 1 年、CORS `allow_origins=["*"]`，上线前仍须整改。

## 1. 结论

近期采用一台专用生产主机可以满足 50 人的中等并发场景，但必须同时完成身份认证加固、独立数据盘、异机备份、健康检查、监控告警和发布回滚。不能只把当前代码复制到更大的机器后继续用 `tmux + python main.py` 运行。

单机需部署的服务已从三件套（Nginx、PostgreSQL、MinIO）增加为四件套，新增 **Redis**：应用的认证会话缓存已强依赖 Redis，Redis 不可用会导致应用无法启动或登录失效。Redis 与应用同机、仅监听回环即可。

推荐生产配置与 [部署机器申请.md](./部署机器申请.md) 保持一致：

- 16 vCPU，32 GB 内存。
- 200 GB 系统盘。
- 2 × 1.92 TB 企业级 NVMe/SSD RAID 1，约 1.92 TB 可用；云盘已有多副本时可使用单块 2 TB 高性能盘。
- 1 Gbps 对称内网带宽。
- 独立于生产主机的 2 TB 以上备份空间。
- Debian 12 或 Ubuntu 24.04 LTS。

这套架构的可用性目标建议定为：

- 服务可用性：内部系统，目标 99.5%。
- RPO：基础方案不超过 24 小时；启用 PostgreSQL WAL 归档后不超过 15 分钟。
- RTO：生产主机完整故障后 4 小时内恢复。
- 单机故障会造成服务中断，RAID 只能防磁盘故障，不能消除主机单点。

## 2. 总体架构

```text
公司终端
   |
   | HTTPS 443 / WSS
   v
公司 DNS -> 防火墙/安全组 -> Nginx + 企业身份网关
                                |
                                | HTTP / WebSocket
                                v
                         MediaForge :3000
                    /       |       |       \
                   /        |       |        \
          PostgreSQL     MinIO    Redis     外部服务
         127.0.0.1:5432  :9000   :6379    HTTPS/ComfyUI 内网
              |              |
              +------ 高性能数据盘 ------+
                             |
                    异机备份/NAS/对象存储

监控：Prometheus 抓取 MediaForge 内置 /metrics + Node/PG/MinIO Exporter
探活：Blackbox/监控探针 -> /health/live、/health/ready
```

请求链路统一为：

1. 浏览器只访问生产域名的 `443`。
2. 企业身份网关完成用户身份认证。
3. Nginx 终止 TLS、限制请求、处理 WebSocket/SSE，并反向代理到 `127.0.0.1:3000`。
4. MediaForge 使用本机回环连接 PostgreSQL、MinIO 和 Redis。
5. PostgreSQL 保存用户、会话、画布、业务元数据和文件索引。
6. MinIO 保存图片、视频、音频、模型和临时对象。
7. Redis 保存认证会话缓存与会话 `last_seen` 等易失状态，是应用的启动强依赖。
8. ComfyUI 和各类 AI API 通过受控内网或 HTTPS 调用，不与应用主机混跑。

内网 AI Provider 默认会被服务端拒绝，以避免 Provider 配置成为 SSRF 入口。确需访问受控内网服务时，只能由部署人员在环境变量中显式列出精确主机名，例如：

```ini
AI_PROVIDER_ALLOWED_HOSTS=ai-gateway.internal.example,model-proxy.internal.example
```

不要填写 IP 段、通配符或来自用户输入的值。

## 3. 上线前必须整改的代码项

以下项目属于 P0 上线门槛。未完成时，即使部署在公司内网，也不应开放给 50 人正式使用。

### 3.1 身份认证

当前认证只检查用户名是否存在，没有密码；当前 `/auth/sso` 直接信任 URL 中的 `user_id` 和 `username`。任何能访问服务的人都可能冒用其他用户身份。

正式方案必须二选一：

1. 推荐：Nginx 前接公司 OIDC/OAuth2 身份网关，应用只信任由 Nginx 清洗并注入的身份头。
2. 备选：改造 `/auth/sso`，增加 HMAC 签名、时间戳、nonce、防重放和来源限制。

同时要求：

- 关闭公开注册，或仅允许管理员创建用户。
- 会话 Cookie 增加 `Secure`，保留 `HttpOnly`、`SameSite=Lax`。
- 会话有效期从当前 1 年缩短为公司安全规范要求的周期，建议 8 至 24 小时，并支持闲置过期。
- WebSocket 握手必须校验同一份会话，不能只依赖 HTTP 中间件。
- Nginx 必须覆盖外部传入的身份头和 `X-Forwarded-For`，不能追加后直接信任。

### 3.2 WebSocket 和多进程

当前 WebSocket 连接、广播对象、部分任务队列和线程锁仍位于 Python 进程内。注意：认证会话已迁移到 Redis，但这只解决了会话共享，WebSocket 广播和任务状态仍是进程内状态。近期部署必须保持：

- 单个 MediaForge/Uvicorn worker。
- 通过 systemd 自动重启。
- 不使用 `--workers 2` 或多副本负载均衡。

如果后续需要多 worker/多主机，应先完成：

- WebSocket 广播迁移到 Redis Pub/Sub（Redis 已就绪，但广播尚未接入）。
- 任务状态和队列迁移到 PostgreSQL/Redis/专用任务系统。
- 本地锁替换成数据库事务、分布式锁或幂等约束。
- 日志改为只写 stdout，由日志代理统一采集（结构化日志已支持 `LOG_STDOUT`）。

### 3.3 健康检查

健康接口已实现，可直接对接监控与负载均衡探针：

- `GET /health/live`：只证明进程和事件循环存活，返回 `{"status":"ok"}`，响应头带 `Cache-Control: no-store`，不访问外部依赖。
- `GET /health/ready`：并发校验 PostgreSQL 查询、Redis PING 和 MinIO 三个 Bucket 可访问；就绪返回 200，任一不可用返回 503 并带 `Retry-After: 5`。响应体形如 `{"status":"not_ready","ready":false,"components":{"postgres":"ok","minio":"unavailable","redis":"ok"}}`。

两个接口都以 `include_in_schema=False` 注册、且在认证中间件的公开路径中放行，返回内容只含组件状态标记，不含连接串、密钥、Bucket 路径或异常堆栈。仍需在 Nginx/安全组层面把 `/health/*` 与 `/metrics` 限制为仅本机、负载均衡器和监控网段访问。

### 3.4 Web 安全

- 将 CORS 从 `*` 收敛到生产域名；同域部署时可不启用跨域。
- 增加可信 Host 校验。
- 对登录、SSO、上传和高成本生成接口配置限流。
- 对管理接口执行服务端角色校验，不能只依赖前端隐藏入口。
- 在不影响现有 iframe/媒体功能的前提下逐步启用 CSP；上线前至少启用 HSTS、`X-Content-Type-Options` 和合理的 Referrer Policy。

## 4. 主机、目录与账号规划

### 4.1 服务账号

每个服务使用独立的不可登录系统账号：

| 服务 | 账号 | 权限边界 |
| --- | --- | --- |
| MediaForge | `mediaforge` | 只读应用代码，可写运行数据和日志 |
| PostgreSQL | `postgres` | 只写 PostgreSQL 数据目录 |
| Redis | `redis` | 只写 Redis 数据/持久化目录 |
| MinIO | `minio` | 只写 MinIO 数据目录 |
| Nginx | 系统默认 `www-data`/`nginx` | 只读证书和代理配置 |

禁止使用 root 运行 MediaForge 和 MinIO。

### 4.2 目录

```text
/opt/mediaforge/
  releases/<version>/       # 每个发布版本，root 只读
  current -> releases/...   # 当前版本软链接

/etc/mediaforge/
  mediaforge.env            # 应用环境变量，root:mediaforge 0640

/var/lib/mediaforge/
  runtime/                  # config/.env、workflows 等当前仍需写入的运行数据
  cache/                    # 可丢弃缓存

/var/log/mediaforge/        # JSON 行日志

/data/mediaforge/
  postgres/                 # PostgreSQL 数据
  redis/                    # Redis 持久化数据（会话缓存）
  minio/                    # MinIO 对象数据
  staging/tmp/              # 上传、FFmpeg、Pillow 临时区，不作为备份
```

代码当前仍会写 `config/.env`、`workflows` 和少量兼容目录。部署时应将这些可变目录迁到 `/var/lib/mediaforge/runtime` 并以软链接接回应用目录，或先完成路径配置化。不要让整个代码目录归应用账号可写，否则应用漏洞可能直接篡改代码并跨重启持久化。

PostgreSQL 与 MinIO 最好使用不同逻辑卷；只有一组 RAID 数据盘时，也应使用独立目录、独立配额和独立监控。

必须将 `TMPDIR` 指向 `/data/mediaforge/staging/tmp`。当前服务包含最大数 GB 的媒体中转，如果继续使用系统盘 `/tmp`，并发上传可能直接写满系统盘。临时目录应配置小时级清理、容量上限和告警，应用运行账号只能访问自己的临时目录。

## 5. 网络与端口

| 端口 | 服务 | 来源 | 暴露策略 |
| ---: | --- | --- | --- |
| 443 | Nginx HTTPS/WSS | 公司用户网段 | 唯一业务入口 |
| 80 | Nginx | 公司用户网段 | 只做 HTTPS 跳转，也可关闭 |
| 22 | SSH | 运维堡垒机 | 禁止全网访问，禁用密码登录 |
| 3000 | MediaForge | `127.0.0.1` | 不对外开放 |
| 5432 | PostgreSQL | `127.0.0.1` | 不对外开放 |
| 6379 | Redis | `127.0.0.1` | 不对外开放，认证会话缓存 |
| 9000 | MinIO API | `127.0.0.1` | 不对用户开放 |
| 9001 | MinIO Console | `127.0.0.1` | 仅 SSH 隧道/运维网访问 |
| 8188 等 | ComfyUI | 指定推理机网段 | 双向白名单，不开放给终端 |

出站只允许必要的 DNS、NTP、公司代理、AI API、ComfyUI、软件源和备份目标。生产域名使用公司 CA 或可信证书，证书自动续期并配置到期告警。

## 6. Nginx 入口设计

下面是核心配置骨架，域名、证书、身份网关和限流值需按公司环境替换：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

limit_req_zone $binary_remote_addr zone=login_limit:10m rate=5r/m;
limit_req_zone $binary_remote_addr zone=api_limit:20m rate=30r/s;

upstream mediaforge_backend {
    server 127.0.0.1:3000;
    keepalive 32;
}

server {
    listen 80;
    server_name mediaforge.internal.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name mediaforge.internal.example.com;

    ssl_certificate     /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;
    client_max_body_size 4g;

    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # 此处接公司 OIDC/OAuth2 auth_request；未认证请求不得进入应用。

    location /ws/ {
        proxy_pass http://mediaforge_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }

    location = /api/chat/stream {
        proxy_pass http://mediaforge_backend;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 1800s;
    }

    location /auth/ {
        limit_req zone=login_limit burst=5 nodelay;
        proxy_pass http://mediaforge_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $remote_addr;
    }

    location / {
        limit_req zone=api_limit burst=100 nodelay;
        proxy_pass http://mediaforge_backend;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_request_buffering off;
        proxy_read_timeout 1800s;
        proxy_send_timeout 1800s;
    }
}
```

`client_max_body_size 4g` 对齐当前最大视频中转上限，但会增加资源风险。正式上线前应按真实业务把单文件限制降到最小可用值，并在应用层同步校验，不能只依赖 Nginx。

以上连接池/阻塞 IO/缓存参数均为默认值，可满足单机 50 人起步；正式压测后按 `mediaforge_pg_pool_*`、`mediaforge_blocking_io_*`、`mediaforge_storage_cache_*` 指标调整。`STORAGE_CACHE_DIR` 默认落在系统临时目录，生产环境应显式指向独立可丢弃目录（如 `/var/lib/mediaforge/cache`），避免与 `TMPDIR` 混用并写满系统盘。

`LOG_TRUST_PROXY_HEADERS=true` 只有在 Nginx 使用 `$remote_addr` 覆盖外部 `X-Forwarded-For` 时才允许开启。

### 7.2 systemd

```ini
[Unit]
Description=MediaForge application
Wants=network-online.target postgresql.service redis-server.service minio.service
After=network-online.target postgresql.service redis-server.service minio.service

[Service]
Type=simple
User=mediaforge
Group=mediaforge
WorkingDirectory=/opt/mediaforge/current
EnvironmentFile=/etc/mediaforge/mediaforge.env
Environment=HOME=/var/lib/mediaforge
ExecStart=/opt/mediaforge/current/.venv/bin/python main.py --host 127.0.0.1 --port 3000
Restart=on-failure
RestartSec=5
TimeoutStartSec=120
TimeoutStopSec=120
KillSignal=SIGINT
UMask=0027
LimitNOFILE=65535
PrivateTmp=true
NoNewPrivileges=true
ProtectSystem=full
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

保持单 worker。应用启动时会依次打开数据库连接池、Redis 客户端、共享 HTTP 客户端，并验证 MinIO/PostgreSQL 配置一致（二者必须同时配置，否则启动失败）与初始化业务表；Redis PING 失败会直接拒绝启动。启动失败应由 systemd 记录并重试，但持续失败必须触发告警，不能无限静默重启。

`PrivateTmp=true` 会让服务使用独立的 `/tmp`，需确保 `TMPDIR` 与 `STORAGE_CACHE_DIR` 指向服务账号可写的持久目录，而非被 `PrivateTmp` 隔离的临时空间。

## 8. PostgreSQL

安装和目录初始化按 [PostgreSQL安装流程.md](./PostgreSQL安装流程.md) 执行，并补充以下生产要求：

- 仅监听 `127.0.0.1`，认证使用 `scram-sha-256`。
- 应用使用 `mediaforge` 专用账号，不使用超级用户。
- 数据目录位于 `/data/mediaforge/postgres`。
- 32 GB 主机初始可从 `shared_buffers=4GB`、`effective_cache_size=16GB` 起步，再根据监控调整。
- `max_connections` 保持 100 以内；应用后续连接增长时优先引入连接池，不盲目增大。
- 开启慢查询日志，建议从 1 秒阈值起步，并限制日志体积。
- 每次结构变更必须有向前迁移、版本记录和回滚/恢复方案。

PostgreSQL 与 MinIO 之间存在引用一致性：数据库中的 `bucket + object_key` 是对象索引，不能只备份数据库或只备份对象。

## 9. MinIO

安装和服务配置按 [MinIO安装流程.md](./MinIO安装流程.md) 执行，并采用以下策略：

- API 和 Console 只监听回环或受限管理网。
- 单机同部署时将启动参数设置为 `--address 127.0.0.1:9000 --console-address 127.0.0.1:9001`。
- 数据目录位于 `/data/mediaforge/minio`。
- 创建 `mediaforge-private`、`mediaforge-public`、`mediaforge-temp` 三个 Bucket。
- 应用使用专用 Access Key 和最小 Bucket 权限，不使用 MinIO root 凭据。
- Bucket 默认禁止匿名列举；公开对象只通过明确业务路径访问。
- `mediaforge-temp` 配置 3 天生命周期规则，应用清理与 MinIO 生命周期形成双保险。
- 开启容量、对象数、请求错误、磁盘离线和延迟监控。

单节点 MinIO 即使位于 RAID 1 上也不是高可用对象存储。机器损坏、误删除和勒索风险必须依靠异机版本化备份解决。

## 9.5 Redis（认证会话缓存，强依赖）

应用的认证会话缓存已改为异步 Redis。启动时 `open_redis_client()` 会校验 `REDIS_URL` 并执行 `PING`，失败即抛出 `RedisUnavailableError` 拒绝启动；`/health/ready` 也会持续校验 Redis。因此 Redis 属于与 PostgreSQL、MinIO 同级的运行时强依赖，必须随应用一起纳入部署、监控和恢复。

单机部署要求：

- 只监听回环 `127.0.0.1:6379`，不对用户网段开放；建议设置 `requirepass` 并在 `REDIS_URL` 中携带密码。
- 使用独立不可登录账号 `redis` 运行，数据/持久化目录位于 `/data/mediaforge/redis`。
- Redis 中仅为会话缓存等易失状态，**不是**业务数据主库；即便丢失，最坏后果是全体用户需要重新登录，不会丢失画布/文件等业务数据。因此可用轻量持久化（如仅 AOF `everysec` 或关闭持久化）即可，无需按业务库标准做全量备份。
- 通过 systemd 托管、开机自启，并置于 MediaForge 的 `After=`/`Wants=` 依赖之前启动。
- 设置合理的 `maxmemory` 与 `maxmemory-policy`（会话建议 `volatile-ttl` 或 `noeviction` 视规模而定），避免内存无上限增长。
- 监控可用性（`mediaforge_redis_available`）、命令延迟（`mediaforge_redis_operation_seconds`）、内存占用与连接数。

会话相关行为：会话在 Redis 中以 `REDIS_SESSION_PREFIX`（默认 `mediaforge:session:`）为前缀存储，有效期跟随 `SESSION_MAX_AGE`（当前代码为 1 年，见 3.1 要求缩短）。会话 `last_seen` 采用写入合并（`REDIS_LAST_SEEN_WRITE_INTERVAL_SECONDS`）与周期落库（`REDIS_LAST_SEEN_FLUSH_INTERVAL_SECONDS`）降低写放大。

## 10. 备份与恢复

### 10.1 备份策略

| 数据 | 方式 | 频率 | 建议保留 |
| --- | --- | --- | --- |
| PostgreSQL | `pg_dump -Fc` 全量 | 每日 | 14 个日备份、8 个周备份、12 个同月备份 |
| PostgreSQL WAL | WAL 归档 | 持续 | 至少 7 天，用于时间点恢复 |
| MinIO | `mc mirror`/备份产品同步到异机版本化存储 | 每日增量或持续 | 30 天以上 |
| 配置 | 加密备份 `/etc/mediaforge`、Nginx/服务配置 | 每次变更 | 最近 10 个版本 |
| Redis | 仅会话缓存，通常无需备份；如需可选 RDB 快照 | 可选 | 最近 1~2 份即可 |
| 审计日志 | 推送到独立日志平台或只追加存储 | 实时 | 180 天或公司规范 |

备份目标不能挂载在同一主机的同一块数据盘。备份凭据与生产应用凭据分离，备份文件加密并限制下载权限。Redis 仅承载易失会话缓存，丢失只导致用户重新登录，不参与业务数据一致性备份。

### 10.2 一致性与恢复顺序

计划内一致性备份建议短暂进入只读/维护模式：

1. Nginx 阻止新的写请求，等待正在执行的写任务结束。
2. 记录应用版本和数据库迁移版本。
3. 生成 PostgreSQL 备份。
4. 完成 MinIO 增量同步并记录对象版本/时间点。
5. 恢复业务写入。

灾难恢复顺序：

1. 准备相同或兼容版本的 PostgreSQL、Redis、MinIO 和 MediaForge。
2. 先恢复 MinIO 对象，再恢复与其时间点匹配的 PostgreSQL。
3. 启动依赖服务（含 Redis），执行只读一致性检查和对象引用抽查。
4. 启动 MediaForge，验证健康检查、登录、画布、上传、预览和删除。
5. 最后开放 Nginx 流量。

每季度至少做一次恢复演练，并记录实际 RPO、RTO、丢失对象和修复步骤。

## 11. 日志、监控与告警

应用日志按 [日志系统说明.md](./日志系统说明.md) 配置。单 worker 时可继续写本地 JSON 日志，同时由 Vector/Filebeat/Promtail 采集到集中平台。

### 11.1 应用内置指标

应用已内置 Prometheus 抓取端点 `GET /metrics`（`text/plain; version=0.0.4`，`include_in_schema=False`，认证放行），抓取前会刷新数据库连接池、MinIO 目录容量、阻塞 IO 等实时指标。相比外部 exporter，这些指标直接反映应用内部状态，应优先接入 Prometheus。当前导出的 `mediaforge_*` 指标覆盖：

- 数据库连接池与查询：`mediaforge_pg_pool_size`、`mediaforge_pg_pool_available`、`mediaforge_pg_pool_waiting`、`mediaforge_pg_pool_wait_seconds`、`mediaforge_pg_query_seconds`、`mediaforge_pg_slow_queries_total`、`mediaforge_pg_active_connections`、`mediaforge_pg_lock_waiting`。
- Redis：`mediaforge_redis_available`（是否可用，0/1）、`mediaforge_redis_operation_seconds`、`mediaforge_auth_session_cache_requests_total`。
- MinIO/对象存储：`mediaforge_minio_operation_seconds`、`mediaforge_minio_failures_total`、`mediaforge_minio_bucket_catalog_bytes`、`mediaforge_minio_bucket_catalog_objects`。
- 有界阻塞 IO 适配层：`mediaforge_blocking_io_active`、`mediaforge_blocking_io_queued`、`mediaforge_blocking_io_rejected_total`。
- 本地存储缓存：`mediaforge_storage_cache_bytes`、`mediaforge_storage_cache_files`、`mediaforge_storage_cache_hits_total`、`mediaforge_storage_cache_misses_total`、`mediaforge_storage_cache_evictions_total`、`mediaforge_storage_cache_download_bytes_total`、`mediaforge_storage_cache_materialize_seconds`、`mediaforge_storage_cache_cleanup_failures_total`。
- 后台任务与重试：`mediaforge_background_runs_total`、`mediaforge_background_failures_total`、`mediaforge_transient_retries_total`。

`/metrics` 与 `/health/*` 一样，只允许监控网段/本机访问，须在 Nginx 或安全组层面限制，不能暴露给用户网段。

### 11.2 外部 Exporter 与探针

在应用内置指标之外，建议再部署：

- Node Exporter：CPU、内存、Swap、磁盘、网络、文件系统。
- PostgreSQL Exporter：连接数、事务、锁、缓存、检查点、数据库大小（与应用内置连接池指标互补）。
- Redis Exporter：内存占用、连接数、命中率、持久化与阻塞情况；结合应用侧 `mediaforge_redis_available` 判断会话缓存健康。
- MinIO Prometheus 指标：容量、对象数、请求、错误和磁盘状态。
- Blackbox Exporter 或公司探针：HTTPS、登录页、`/health/live`、`/health/ready`。
- 日志平台：按 `request_id`、`user_id`、`task_id` 查询应用、访问、任务和审计日志。

最低告警：

| 指标 | Warning | Critical |
| --- | ---: | ---: |
| CPU 5 分钟平均 | 70% | 85% |
| 内存使用 | 75% | 85% |
| Swap 持续换入换出 | 任意持续 5 分钟 | 伴随延迟/内存 90% |
| 数据盘使用 | 75% | 85% |
| 磁盘 `await` | 20 ms | 50 ms |
| PostgreSQL 连接 | 60% 上限 | 80% 上限 |
| 连接池等待 `mediaforge_pg_pool_waiting` | 持续 >0 | 伴随 p95 上升 |
| Redis 可用性 `mediaforge_redis_available` | — | =0（会话缓存不可用，登录/鉴权失效） |
| 阻塞 IO 拒绝 `mediaforge_blocking_io_rejected_total` | 出现增长 | 持续增长（MinIO 背压） |
| HTTP 5xx | 1% | 5% |
| 核心 API p95 | 2 秒 | 5 秒 |
| 健康检查 | 连续失败 2 次 | 连续失败 5 次 |
| 备份 | 超过 26 小时未成功 | 超过 48 小时未成功 |

外部 AI 任务耗时需要单独统计，不能与本地 API 延迟混在一起。

## 12. 发布、回滚与变更管理

### 12.1 发布流程

1. 固定 Git commit 和 `VERSION`，使用 `uv.lock` 安装确定版本依赖。
2. CI 执行完整测试、依赖漏洞检查和静态检查。
3. 在临时目录构建 `/opt/mediaforge/releases/<version>`，不在生产目录执行 `git pull` 覆盖运行版本。
4. 发布前验证数据库和 MinIO 备份成功。
5. 若有数据库迁移，先在备份副本/预发布环境演练。
6. 停止入口写流量，等待任务收敛，再停止应用。
7. 切换 `current` 软链接，启动应用并检查 `/health/ready`。
8. 执行登录、画布读写、上传、预览、SSE 和 WebSocket 冒烟测试。
9. 恢复流量并观察 30 分钟错误率、延迟和资源指标。

### 12.2 回滚原则

- 代码无数据库变更：切回上一版本并重启。
- 数据库变更向后兼容：先回滚代码，保留兼容结构。
- 破坏性数据库变更：进入维护模式，从匹配备份恢复；不能仅切代码版本。
- MinIO 对象写入使用不可变 UUID Key，避免新旧版本覆盖同一个对象。

任何生产变更都应记录操作者、时间、版本、变更内容、验证结果和回滚点。

## 13. 上线实施顺序

### 阶段 A：基础设施

1. 交付专用主机、系统盘、数据盘、DNS、证书和安全组。
2. 创建服务账号和目录，挂载并验证数据盘。
3. 安装 PostgreSQL、Redis、MinIO、Nginx、Python/uv、FFmpeg 和监控代理。

### 阶段 B：安全整改

1. 接企业身份网关，关闭不可信注册/SSO入口。
2. 补 WebSocket 会话验证、Secure Cookie、CORS/Host 收敛。
3. 补 live/ready 健康检查和管理接口授权。

### 阶段 C：数据迁移

1. 执行 PostgreSQL 数据迁移并对账。
2. 使用现有存储迁移脚本将本地文件迁入 MinIO。
3. 校验文件数、总字节数、抽样哈希、业务引用和用户配额。
4. 保留原数据只读副本至迁移验收结束。

### 阶段 D：灰度与验收

1. 先开放 5 名用户，观察 1 至 2 个工作日。
2. 扩大到 20 人，检查容量、错误和任务峰值。
3. 执行 50 人模拟压测和故障恢复演练。
4. 达到验收指标后全量开放。

## 14. 上线验收清单

- [ ] 生产域名只开放 HTTPS，HTTP 自动跳转。
- [ ] 企业身份与 MediaForge 用户一一对应，无法冒用其他用户名。
- [ ] WebSocket 未登录连接被拒绝。
- [ ] PostgreSQL、MinIO、Redis、3000 端口不对用户网段开放。
- [ ] MediaForge、PostgreSQL、Redis、MinIO 均由 systemd 托管且开机自启。
- [ ] 应用不是 root 运行，文件权限符合最小权限。
- [ ] `/health/live`、`/health/ready` 可被监控探测，`/metrics` 已接入 Prometheus 且仅监控网段可访问。
- [ ] 数据库与 MinIO 备份成功，完成至少一次恢复演练。
- [ ] 日志可按 request/user/task 查询，密钥未进入日志。
- [ ] 50 WebSocket、15 普通并发、5 至 10 路媒体操作压测通过。
- [ ] CPU 低于 70%、内存低于 80%、无持续 Swap、磁盘 `await` 低于 20 ms。
- [ ] 核心本地 API p95 小于 2 秒，5xx/超时率低于 1%。
- [ ] 数据盘至少保留 30%，配额和生命周期清理生效。
- [ ] 发布和回滚至少演练一次，值班人员持有操作手册。

## 15. 后续演进

当在线人数、媒体吞吐或可用性要求继续提高时，按以下顺序拆分：

1. PostgreSQL 迁至独立数据库或托管 RDS。
2. MinIO 迁至多节点集群或公司统一对象存储。
3. Redis 已引入并承载认证会话缓存；下一步是把 WebSocket 广播迁到 Redis Pub/Sub、任务状态迁到 Redis/PostgreSQL，并为 Redis 本身提供高可用（哨兵/集群），使其从"单机强依赖"升级为"可容错依赖"。
4. MediaForge 改成无状态多副本，部署到容器平台并滚动发布。
5. Nginx 前增加双实例负载均衡，消除入口单点。
6. 引入 OpenTelemetry 和统一指标/日志/链路追踪（应用已内置 Prometheus `/metrics`，可作为迁移起点）。

在完成第 3 步中的广播/任务去进程内化之前，不应通过简单增加 Uvicorn worker 或复制应用实例来扩容。
