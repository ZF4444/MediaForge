# MediaForge 单机多容器生产部署方案与操作流程

本文替代旧 Docker 部署文档及旧生产部署方案，是当前生产部署入口。业务架构、安装参考等其他文档保留；PostgreSQL、Redis、MinIO 的原生安装教程不再作为本方案的安装步骤。

## 1. 已确定的部署方式

- 同一台 Debian 12 服务器：8 个逻辑 CPU、约 8 GiB 内存，数据盘挂载 `/data`。
- 五个独立容器：API、画布 Worker、PostgreSQL、Redis、MinIO，属于同一个 Compose 项目。
- 所有容器共享宿主机内存，不设置 `mem_limit`、内存 reservation 或 `deploy.resources`；不关闭 OOM killer，也不禁用 Swap。
- Redis 不配置 `maxmemory`，使用 `noeviction`，避免把会话、任务和队列当作普通缓存淘汰。该策略不会阻止整机内存耗尽。
- 应用单 API 进程，画布任务交给独立 Worker；Agent 命令消费、事件 outbox、WebSocket Pub/Sub 和定期维护保留在 API。不要直接扩容 API，否则要先重新分配后台职责。
- Nginx 在宿主机终止 HTTPS，转发至回环端口 3000。PostgreSQL、Redis 不发布宿主机端口；MinIO API/控制台仅发布到回环 19000/19001。
- 应用、配置、工作流、日志和中间文件存放 `/data/mediaforge`，不放容器可写层。

容器化提供部署可重复性与服务隔离，不提供机器级高可用。机器、数据盘、Docker 故障仍会影响全站。正式切换前需要完成恢复演练和异机备份。

配置对应关系：

| 文件 | 用途 |
| --- | --- |
| `Dockerfile` | 前端构建、Python 锁文件依赖、FFmpeg 和应用运行镜像 |
| `.dockerignore` | 排除密钥、本地依赖、数据、日志等构建上下文 |
| `config/deploy/compose.yml` | 五个容器、健康检查、网络和持久化 |
| `config/dev/.env.example` | 本地开发模板，复制为 `config/.env`，不用于生产部署 |
| `config/deploy/.env.example` | 生产 Docker 部署模板，复制为 `config/deploy/.env` |
| `config/deploy/minio.Dockerfile` | 从固定上游版本源码构建 MinIO |
| `config/deploy/nginx.conf` | 宿主机反向代理模板 |

## 2. 先盘点原生产环境

迁移前记录旧应用版本、Python 版本、PostgreSQL 主版本及扩展、Redis 版本和 ACL、MinIO 版本及桶配置。确认实际数据目录和远端服务地址，不要根据默认值猜测。

同时盘点：数据库大小、MinIO 对象数量/总大小/版本控制、旧 `data/`、`config/`、`workflows/`、供应商密钥、定时任务、域名和证书。保留旧 `APP_SECRET_KEY`，重新生成会导致已有加密连接凭据无法解密。

先决定停机窗口、允许丢失数据的时间（RPO）、恢复时间（RTO），至少做一次完整备份与恢复验证。旧、新应用不能同时消费同一条任务队列。已有生成任务应先排空或确认如何处理，防止上游重复提交计费。

默认 PostgreSQL 镜像为 16，Redis 为 7.4，只是新部署起点。迁移现有服务必须核对兼容性；优先同主版本完成迁移，再另开窗口升级。不得把不同 PostgreSQL 主版本的数据目录直接挂入容器。

## 3. 安装 Docker（Debian 12，root 执行）

先检查是否已有 Docker、containerd、Podman 和旧服务；有其他工作负载时先评估冲突，不盲目卸载。全新 Debian 主机可使用官方 apt 仓库：

```bash
apt-get update
apt-get install -y ca-certificates curl
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
cat > /etc/apt/sources.list.d/docker.sources <<'SOURCES'
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: bookworm
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
SOURCES
apt-get update
apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker
docker version
docker compose version
```

上面架构针对本机；其他架构需调整。若改 Docker 数据根目录，应在首次运行工作负载前规划，并合并已有 `daemon.json`，不要覆盖现有配置。当前系统盘约 62 GB，镜像和构建缓存可能占满系统盘，需监控 `docker system df`。

## 4. 准备环境和持久化目录

以下操作均从项目根执行；所有命令使用同一份环境文件、Compose 文件和项目名。

```bash
cd /data/workspace/MediaForge
cp config/deploy/.env.example config/deploy/.env
chmod 600 config/deploy/.env
# 每个新密码分别执行一次，复制输出到 config/deploy/.env
openssl rand -hex 32
```

编辑 `config/deploy/.env`，替换所有 `CHANGE_ME`、域名和镜像标签。新密码建议使用十六进制，避免数据库 URL 中的特殊字符编码问题。旧密码含特殊字符时应改为正确 URL 编码的连接串，不能直接使用模板插值。

`APP_IMAGE` 每次发布使用唯一标签；基础镜像在验收后记录实际 digest，可把镜像值换成 `image@sha256:...`。本地构建的应用和 MinIO 镜像应推送私有仓库或 `docker save` 异机保存，不能只依赖本机缓存。

MinIO 上游目前采用源码分发，仓库已归档，不沿用旧 `minio/minio:latest`。此处从固定发布标签构建作为兼容迁移基线，并非承诺该旧版本持续获得安全更新。正式生产需审核其安全维护状态与现有数据兼容性；有内部审核的维护镜像时，填写 `MINIO_IMAGE`，拉取该镜像并跳过 MinIO 构建，不能让 `build` 覆盖它。版本或源码 ref 变更必须同时更换镜像标签。

```bash
# 本流程后续命令使用该 shell 函数；重新登录后需重新定义
 dc() { docker compose --env-file config/deploy/.env -f config/deploy/compose.yml "$@"; }

findmnt /data
install -d -m 0750 /data/mediaforge
install -d -o 10001 -g 10001 -m 0750 \
  /data/mediaforge/app /data/mediaforge/app/tmp /data/mediaforge/app/cache \
  /data/mediaforge/logs /data/mediaforge/config /data/mediaforge/workflows \
  /data/mediaforge/minio
install -d -m 0700 /data/mediaforge/postgres /data/mediaforge/redis /data/mediaforge/backups
```

如果修改 `DATA_ROOT`，必须同步修改上面的路径和后续备份路径。`/data` 必须已挂载，避免把数据误写系统盘；配置开机挂载，确保它在 Docker 恢复容器前可用。PostgreSQL/Redis 官方镜像首次启动负责初始化目录权限，应用和自建 MinIO 使用 UID 10001。

应用启动时读取 `config/.env`，运行时不创建或修改该文件；配置目录整体挂载，用于提供运维人员维护的运行环境配置。宿主机 `/data/mediaforge/config/.env` 对应容器内 `/app/config/.env`，与 Compose 使用的 `config/deploy/.env` 是两份不同的文件。新安装的应用配置目录可以为空；迁移应复制仍需使用的应用环境配置和工作流并修正权限。清除旧 `DATABASE_URL`、`REDIS_URL`、`MINIO_*` 等基础设施连接设置，连接统一由 Compose 注入。不要把部署密码重复复制到应用环境配置中。

ComfyUI 实例地址也作为 `comfyui` 连接的 Base URL 保存在数据库；旧 `COMFYUI_INSTANCES` 不再读取或自动导入，升级前应在 API 设置中录入地址并关联工作流资源。Docker 内不要用 `127.0.0.1` 指向宿主机 ComfyUI。

AI 连接、模型和资源保存在 PostgreSQL，供应商 API Key 等连接凭据加密保存在 `ai_connection_secrets` 表，由 API 设置页面维护，不写入应用 `.env`。部署文件中的 `APP_SECRET_KEY` 是加解密主密钥，必须长期固定，API 和 Worker 使用同一个值。当前 AI 连接执行链路不读取旧 `COMFLY_API_KEY`、`MODELSCOPE_API_KEY`、`RUNNINGHUB_API_KEY` 作为凭据；迁移旧环境时不能只复制这些变量，应验证数据库中的连接配置与密钥已迁移成功。

API 和 Worker 共享应用配置目录及数据库；数据库业务配置保存后跨进程刷新依赖应用机制。修改部署环境变量需重新创建容器，单纯 `restart` 不会加载新的 Compose 环境。

## 5. 构建、检查和首次启动

```bash
# -q 避免把展开后的密码输出到终端或日志
dc config -q
dc pull postgres redis
# 一次构建一个服务，降低本机构建时的资源争抢
dc build minio
dc build api
dc up -d --wait postgres redis minio
```

Go 编译及前端构建会使用 CPU、内存和系统盘缓存。正式业务运行后优先在 CI/其他机器构建，再拉取经过验收的镜像。无内存限额不代表可以无限并行构建。

**新安装**可继续：

```bash
dc up -d --wait api
dc up -d worker
dc ps
dc logs --tail=100 api worker
curl -fsS http://127.0.0.1:3000/health/live
curl -fsS http://127.0.0.1:3000/health/ready
```

**有生产数据迁移**时，先按第 6 节恢复，再启动应用；不要让新应用对待恢复的数据库先执行初始化。API 成功启动后再启动 Worker，避免并行首次初始化。

`CANVAS_TASK_WORKER_CONCURRENCY=10` 是起步并发配置，可按供应商配额和负载调整；它不是内存限额。Worker 没有 HTTP 健康端口，必须验证任务真实消费，不能仅凭进程为 running 判定正常。Compose 的 unhealthy 状态也不会自动重启容器，`unless-stopped` 主要处理进程退出。

## 6. 原生部署迁移流程

### 6.1 预演

使用独立数据库、桶和数据路径恢复一份备份。隔离访问入口，防止对真实供应商发起生成任务。验证登录、权限、文件、模型配置、WebSocket、Agent 和画布任务。记录复制耗时、恢复耗时、磁盘峰值和回滚步骤。

### 6.2 正式切换

1. 构建并准备新镜像，确认新端口没有与旧进程冲突。
2. 入口进入维护状态，停止旧 API、Worker、定时任务及其他写入方，排空上游任务。
3. 创建最终 PostgreSQL 逻辑备份，保持 MinIO、Redis 和应用可写目录在同一个停写窗口内同步。
4. 新数据库恢复完成后，复制 MinIO、Redis 和应用数据，核对权限、对象数量和关键记录。
5. 禁用旧应用的自动启动及消费任务，启动新 API，确认 ready 成功，再启动 Worker。
6. 配置 HTTPS 并切换入口，执行第 8 节验收；旧数据保留，暂不清理。

PostgreSQL：旧机用与服务版本兼容的 `pg_dump -Fc` 生成备份。新空库启动后恢复（将文件路径替换为实际值）：

```bash
dc exec -T postgres sh -ec 'exec pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --no-acl --exit-on-error' < /path/to/final.dump
```

恢复失败后不要继续启动应用，也不要在部分恢复的库上反复执行恢复。重新创建确认可丢弃的目标空库再重试；不能删除旧生产库。跨版本升级还需核对扩展、权限和数据库兼容性。

MinIO：有版本控制、保留策略或对象锁时，普通对象复制可能丢失历史和语义，应采用兼容迁移方案。不能在线复制不断变化的底层数据目录。只有验证了版本/存储布局兼容、源和目标均已停止且源为完整单机数据目录时，才采用离线完整复制；否则通过 S3 工具迁移对象，并单独迁移桶策略、用户和配置。

Redis：它承载会话和任务，不应随意清空。通过经过验证的 RDB/AOF 迁移，目标 Redis 停止后放置数据并修正权限。启用 AOF 时需处理现有 AOF 与 RDB 的加载优先级，不能只复制 `dump.rdb` 就假定恢复生效。旧 ACL 用户也不会自动变成新模板的默认用户。验证 Streams、消费组、pending 和会话状态后再启动 Worker。

## 7. Nginx 与 HTTPS

```bash
apt-get install -y nginx certbot python3-certbot-nginx
cp config/deploy/nginx.conf /etc/nginx/sites-available/mediaforge
# 编辑 server_name，确认 DNS 指向本机
ln -s /etc/nginx/sites-available/mediaforge /etc/nginx/sites-enabled/mediaforge
nginx -t
systemctl reload nginx
certbot --nginx -d media.example.com
certbot renew --dry-run
```

已有 Nginx/证书/网关时合并现有配置，不重复创建冲突站点。公网只开放必要的 80/443 和受控 SSH，不能开放 PostgreSQL、Redis、MinIO 管理端口。容器信任代理头的前提是应用入口仅由可信网关访问。

`PUBLIC_BASE_URL` 和 `PUBLIC_MEDIA_BASE_URL` 设置为实际 HTTPS 地址；模型供应商必须能访问应用签发的素材链接。浏览器或供应商不能使用容器内地址 `minio:9000`。访问 MinIO 控制台可通过 SSH 隧道，不直接公开私有桶。

## 8. 验收与观察

```bash
dc ps
dc logs --tail=100 api worker postgres redis minio
curl -fsS https://media.example.com/health/ready
docker stats --no-stream
free -h
df -h / /data
journalctl -k --since today | grep -Ei 'oom|out of memory|killed process' || true
```

人工验证：旧用户登录、文件上传/下载、私有文件权限、生成任务及父子任务、画布实时事件、Agent 交互、供应商配置保存并重启后保留、后台清理及退出恢复。

检查实际容器内存上限为 0（无 Docker 硬上限）：

```bash
for id in $(dc ps -q); do
  docker inspect --format '{{.Name}} memory={{.HostConfig.Memory}} reservation={{.HostConfig.MemoryReservation}} oom={{.State.OOMKilled}}' "$id"
done
```

初期关注整机 `MemAvailable`、持续换页、容器重启、OOM、数据库延迟及磁盘余量。单服务异常可能拖垮整机；不要关闭 OOM killer。观察到问题后再调整应用并发、数据库连接数和资源策略。不能仅根据 Linux free 列偏低判断内存不足。

## 9. 备份和恢复

持久化目录不是备份。本机 backups 只是暂存，备份必须复制到另一台机器/独立存储，附带校验和并限制访问权限。数据库备份包含 AI 连接、模型、资源及加密凭据；必须同时保留原 `APP_SECRET_KEY`，仅备份应用 `.env` 无法恢复供应商配置。备份还需要包含 `config/deploy/.env`、应用环境配置和工作流；含密钥的备份必须加密保存。

下面是最直观的**停机一致备份**：维护入口，排空任务并停 API/Worker，在线导出 PostgreSQL，再停止三项依赖，完整归档数据目录。归档期间站点不可用，需预留等同数据量的空间。

```bash
umask 077
backup_stamp=$(date -u +%Y%m%dT%H%M%SZ)
backup_dir=/data/mediaforge/backups/$backup_stamp
mkdir -p "$backup_dir"
dc stop api worker
# 导出失败必须停止后续流程并排查，不把失败文件视作有效备份
dc exec -T postgres sh -ec 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$backup_dir/postgres.dump"
dc exec -T postgres pg_restore --list < "$backup_dir/postgres.dump" > "$backup_dir/postgres.list"
dc stop postgres redis minio
tar -C /data/mediaforge -cpf "$backup_dir/state.tar" app config workflows minio redis
cp config/deploy/.env "$backup_dir/deployment.env"
sha256sum "$backup_dir/postgres.dump" "$backup_dir/state.tar" "$backup_dir/deployment.env" > "$backup_dir/SHA256SUMS"
dc up -d --wait postgres redis minio
dc up -d --wait api
dc up -d worker
```

上述命令按步骤执行，每步确认成功再继续；shell 默认不会因单条命令失败自动停止。归档包含密钥，异机传输/存储需加密。该方案不包含 MinIO 在其他外部系统中的 KMS 密钥等外部依赖，如有使用需同步备份。

恢复演练：在隔离环境使用原镜像版本和新数据根目录，验证校验和；先恢复 app/config/workflows/minio/redis（所有对应进程停止），修正权限；启动空 PostgreSQL 并导入 dump；启动 MinIO、Redis、API、Worker，执行完整业务验收。不得在生产实例运行中直接覆盖挂载目录。Redis 和 MinIO 的备份应使用同版本先恢复，再单独测试升级。

若停机备份窗口不可接受，应另行设计 PostgreSQL WAL/PITR、对象版本备份及跨服务恢复点策略。不能把当前逐项在线备份脚本当作跨服务原子快照。

## 10. 发布、回退和常用操作

发布前备份，记录当前 git commit、所有镜像 ID/digest、环境配置及数据恢复点。`APP_IMAGE` 改为新唯一标签，构建/拉取后：

```bash
dc config -q
dc build api
# 短暂停机发布；不重启数据库和存储
dc stop api worker
dc up -d --no-deps --wait api
dc up -d --no-deps worker
curl -fsS http://127.0.0.1:3000/health/ready
```

新版本启动可能自动修改数据库，发布前必须评估 schema 兼容性。代码回退：仅在 schema 兼容时把 `APP_IMAGE` 改回旧标签，直接启动旧镜像，**不要重新 build 覆盖旧镜像**。若不兼容，应进入维护状态并按完整恢复方案回退数据，明确新版本接收写入后的数据损失和补偿。

日常命令（项目根、已定义 dc）：

```bash
dc logs -f --tail=100 api worker
dc restart worker
dc up -d --no-deps api worker   # 应用配置变更后重新创建
dc stop                      # 停止，保留容器和数据
dc down                      # 移除容器/网络，绑定目录数据仍保留
docker system df
```

不要清理 `/data/mediaforge`，不要运行不明来源的 prune/删除数据命令。本文没有自动执行安装、迁移或生产切换。
