# MediaForge 存储缓存清理机制

> 更新日期：2026-07-21
>
> 适用范围：MinIO + PostgreSQL 存储模式
>
> 实现位置：`app/services/storage.py`、`scripts/storage_cache.py`

## 1. 机制定位

MediaForge 的正式媒体对象保存在 MinIO，文件元数据保存在 PostgreSQL。本地存储缓存只是按需生成的副本，用于向 ComfyUI、FFmpeg、Pillow 等只能接收本地路径的组件提供文件。

清理本地缓存不会：

- 删除 MinIO 对象；
- 删除或修改 PostgreSQL 文件记录；
- 改变用户素材、输入或输出文件的业务状态。

缓存被清理后，下次需要本地路径时会重新从 MinIO 下载。业务数据生命周期仍由 `storage_cleanup_loop()` 管理，与本文的缓存生命周期相互独立。

## 2. 目录结构

默认缓存目录为：

```text
/tmp/mediaforge-storage-cache
```

实际目录由 `STORAGE_CACHE_DIR` 控制。正式缓存文件按 MinIO bucket 和 object key 保存：

```text
${STORAGE_CACHE_DIR}/
├── mediaforge-private/
│   └── users/alice/outputs/2026/07/example.png
├── .locks/
│   └── <目标路径的 SHA-256>.lock
├── .cache-cleanup.lock
└── .cache-cleanup-state.json
```

对象下载过程中，会在目标文件所在目录创建隐藏临时文件：

```text
.<原文件名>.<随机字符>.tmp
```

建议将缓存放在本地 SSD，不要放到 MinIO 使用的网络挂载盘，否则无法降低网络读取和远端 I/O。

## 3. 文件物化流程

调用 `materialize_media_url()` 时：

1. 根据媒体 URL 或 `/api/files/{file_id}/...` 查询文件元数据。
2. 校验 bucket 和 object key，并计算缓存路径。包含 `.`、`..` 或逃逸缓存根目录的路径会被拒绝。
3. 如果正式缓存文件存在且大小与元数据一致，则命中缓存、按刷新间隔更新 mtime，并直接返回路径。
4. 缓存未命中时，对目标对象的锁文件取得跨进程排他锁。
5. 获得锁后再次检查缓存，避免并发请求重复下载。
6. 从 MinIO 分块下载到唯一临时文件，同时计算大小和 SHA-256。
7. 校验文件大小；元数据提供有效 SHA-256 时也会校验哈希。
8. 执行 `flush`、`fsync`、设置 `0640` 权限，再通过 `os.replace()` 原子替换正式缓存文件。
9. 删除遗留临时文件、更新访问时间并返回本地路径。

`STORAGE_CACHE_CLEANUP_ENABLED=false` 只关闭清理，不关闭上述物化能力。

## 4. 并发与在用文件保护

### 4.1 对象锁

每个正式缓存路径对应 `.locks/` 下的一个锁文件。物化和正式缓存淘汰使用同一把 `fcntl.flock()` 锁：

- 同一对象并发请求只有一个请求执行有效下载；
- TTL、孤儿、LRU 和手动清空会跳过正在物化的对象；
- 不同对象可以并行下载。

### 4.2 临时文件锁

下载进程在整个写入、校验和原子替换期间持有临时文件自身的排他锁。临时文件清理使用非阻塞加锁，无法获得锁时会跳过，因此即使下载停顿超过临时文件 TTL，也不会删除仍在写入的临时文件。

### 4.3 访问保护期

缓存命中或写入完成时会刷新文件 mtime。清理器不会淘汰 mtime 位于 `STORAGE_CACHE_ACCESS_GRACE_SECONDS` 保护期内的正式缓存，包括磁盘空间不足触发的 LRU 清理。

mtime 刷新受 `STORAGE_CACHE_ACCESS_TOUCH_INTERVAL_SECONDS` 限流，避免每次命中都产生文件系统元数据写入。

## 5. 自动清理流程

当 `STORAGE_CACHE_CLEANUP_ENABLED=true` 时，应用启动后创建独立后台任务。任务默认延迟 30 秒执行首轮，之后按照 `STORAGE_CACHE_CLEANUP_INTERVAL_SECONDS` 周期运行。

多个应用 worker 可能同时启动任务，但 `.cache-cleanup.lock` 使用非阻塞全局锁，同一时刻只有一个 worker 能执行清理。未取得锁的任务返回 `already_running`。

每轮按以下顺序执行，所有正式缓存淘汰共享 `STORAGE_CACHE_CLEANUP_BATCH_SIZE` 上限。

### 5.1 过期临时文件

扫描缓存根目录内名称符合 `.*.tmp` 的隐藏临时文件。文件 mtime 超过 `STORAGE_CACHE_TMP_TTL_SECONDS` 且能够取得其非阻塞排他锁时才会删除。

在线清理不会删除 `.locks/` 中的锁文件。

### 5.2 孤儿缓存

孤儿扫描按 `STORAGE_CACHE_ORPHAN_SCAN_INTERVAL_SECONDS` 低频执行，也可通过 CLI 强制触发。扫描器批量查询 PostgreSQL；不存在活动记录、记录已删除或状态为 `deleted` 的 bucket/object key 会被当作孤儿缓存删除。

保护规则：

- PostgreSQL 未启用时不执行孤儿扫描；
- 查询失败时跳过本轮孤儿删除，不根据不完整信息删除文件；
- 活跃对象锁仍会阻止删除。

### 5.3 空闲 TTL

当 `STORAGE_CACHE_IDLE_TTL_SECONDS` 大于 0 时，文件满足以下两个条件才会被删除：

```text
当前时间 - mtime >= STORAGE_CACHE_IDLE_TTL_SECONDS
当前时间 - mtime >= STORAGE_CACHE_ACCESS_GRACE_SECONDS
```

这表示 TTL 是“连续多久没有访问”的空闲时间，不是文件创建后的固定寿命。将 TTL 配置为 `0` 可关闭 TTL 淘汰。

### 5.4 容量与磁盘空间 LRU

满足任一条件时触发 LRU：

- 当前缓存大小大于 `STORAGE_CACHE_MAX_BYTES`；
- 缓存所在分区可用空间小于 `STORAGE_CACHE_MIN_FREE_BYTES`。

清理器按 mtime 从旧到新淘汰不在保护期内的文件，直到：

- 缓存大小降到 `STORAGE_CACHE_TARGET_BYTES`；并且
- 分区可用空间恢复到 `STORAGE_CACHE_MIN_FREE_BYTES`。

如果批次上限已达到，或者剩余文件都处于保护期/被锁定，结果中的 `limit_reached` 或 `capacity_unresolved` 会指出容量约束尚未解决。

### 5.5 空目录

正式删除完成后，清理器从最深层开始移除空目录，但保留缓存根目录及仍包含控制文件的目录。

## 6. 配置项

推荐配置示例：

```env
STORAGE_CACHE_DIR=/var/cache/mediaforge/storage
STORAGE_CACHE_CLEANUP_ENABLED=true
STORAGE_CACHE_MAX_BYTES=10737418240
STORAGE_CACHE_TARGET_BYTES=8589934592
STORAGE_CACHE_IDLE_TTL_SECONDS=604800
STORAGE_CACHE_CLEANUP_INTERVAL_SECONDS=600
STORAGE_CACHE_TMP_TTL_SECONDS=3600
STORAGE_CACHE_ACCESS_GRACE_SECONDS=900
STORAGE_CACHE_MIN_FREE_BYTES=10737418240
STORAGE_CACHE_ACCESS_TOUCH_INTERVAL_SECONDS=300
STORAGE_CACHE_ORPHAN_SCAN_ENABLED=true
STORAGE_CACHE_ORPHAN_SCAN_INTERVAL_SECONDS=86400
STORAGE_CACHE_CLEANUP_BATCH_SIZE=1000
STORAGE_CACHE_DRY_RUN=false
```

| 配置 | 默认值 | 说明 |
|---|---:|---|
| `STORAGE_CACHE_DIR` | `/tmp/mediaforge-storage-cache` | 本地缓存根目录 |
| `STORAGE_CACHE_CLEANUP_ENABLED` | `true` | 是否启动后台清理并允许策略清理 |
| `STORAGE_CACHE_MAX_BYTES` | 10 GiB | 缓存容量高水位，`0` 表示不按最大容量触发 |
| `STORAGE_CACHE_TARGET_BYTES` | 8 GiB | 容量清理的目标低水位 |
| `STORAGE_CACHE_IDLE_TTL_SECONDS` | 604800 | 空闲 TTL，默认 7 天，`0` 表示关闭 |
| `STORAGE_CACHE_CLEANUP_INTERVAL_SECONDS` | 600 | 后台清理间隔，代码最低按 60 秒执行 |
| `STORAGE_CACHE_TMP_TTL_SECONDS` | 3600 | 异常遗留临时文件 TTL，代码最低按 60 秒执行 |
| `STORAGE_CACHE_ACCESS_GRACE_SECONDS` | 900 | 最近访问文件保护期 |
| `STORAGE_CACHE_MIN_FREE_BYTES` | 10 GiB | 缓存分区最小可用空间，`0` 表示关闭此触发器 |
| `STORAGE_CACHE_ACCESS_TOUCH_INTERVAL_SECONDS` | 300 | 命中时刷新 mtime 的最小间隔 |
| `STORAGE_CACHE_ORPHAN_SCAN_ENABLED` | `true` | 是否执行周期孤儿扫描 |
| `STORAGE_CACHE_ORPHAN_SCAN_INTERVAL_SECONDS` | 86400 | 孤儿扫描间隔，默认 24 小时 |
| `STORAGE_CACHE_CLEANUP_BATCH_SIZE` | 1000 | 每轮最多淘汰的正式缓存文件数 |
| `STORAGE_CACHE_DRY_RUN` | `false` | 后台/默认策略清理是否只预演 |

若目标容量小于等于 0 或大于等于最大容量，运行时会自动使用最大容量的 80% 作为目标容量。

## 7. 管理命令

以下命令不会删除 MinIO 对象。

查看状态：

```bash
uv run python scripts/storage_cache.py status
```

预演一轮 TTL、孤儿和 LRU 清理：

```bash
uv run python scripts/storage_cache.py cleanup --dry-run
```

正式执行一轮策略清理：

```bash
uv run python scripts/storage_cache.py cleanup
```

强制执行 PostgreSQL 孤儿核对，不等待扫描间隔：

```bash
uv run python scripts/storage_cache.py cleanup --force-orphan-scan
```

预演或清空全部可识别的正式缓存文件：

```bash
uv run python scripts/storage_cache.py clear --dry-run
uv run python scripts/storage_cache.py clear --yes
```

`clear` 会跳过正在使用的对象，也不会删除临时文件、控制文件和 `.locks/` 锁文件。过期临时文件由 `cleanup` 处理。

锁文件只能离线回收。必须先停止所有 MediaForge worker，避免删除锁文件与新请求加锁之间形成不同 inode：

```bash
sudo systemctl stop mediaforge
uv run python scripts/storage_cache.py clear-locks --dry-run
uv run python scripts/storage_cache.py clear-locks --yes
sudo systemctl start mediaforge
```

命令仍会尝试跳过处于锁定状态的锁文件，但这不能替代“先停止全部 worker”的要求。

## 8. 状态、日志和指标

`status` 主要返回：

- `cleanup_enabled`：策略清理是否启用；
- `cache_dir`：缓存根目录；
- `files` / `bytes`：可识别正式缓存文件数和字节数；
- `lock_files`：`.locks/` 中的对象锁文件数；
- `free_bytes`：缓存所在分区可用空间；
- `max_bytes` / `target_bytes` / `idle_ttl_seconds`：当前阈值；
- `dry_run`：默认清理是否处于预演模式。

后台清理成功记录事件 `storage_cache_cleanup_completed`；异常记录 `storage_cache_cleanup_failed` 并带 `alert=true`。清理结果包含各原因淘汰数量、清理前后容量、耗时和容量是否仍未恢复。

Prometheus 指标包括：

```text
mediaforge_storage_cache_bytes
mediaforge_storage_cache_files
mediaforge_storage_cache_hits_total
mediaforge_storage_cache_misses_total
mediaforge_storage_cache_evictions_total{reason="ttl|lru|orphan|corrupt|tmp|manual"}
mediaforge_storage_cache_download_bytes_total
mediaforge_storage_cache_materialize_seconds{result="hit|miss|error"}
mediaforge_storage_cache_cleanup_failures_total
```

后台任务运行结果还计入通用的 `mediaforge_background_runs_total` 和 `mediaforge_background_failures_total`，其中 job 为 `storage_cache_cleanup`。

## 9. 排障建议

### 缓存持续超过上限

检查 `capacity_unresolved`、`limit_reached`、批次上限和访问保护期。批次上限导致的情况会在后续轮次继续清理；磁盘紧急时可以缩短保护期或增大批次，但应评估正在读取文件的风险。

### 临时文件持续增加

先执行 `cleanup --dry-run`。仍在写入的临时文件会因文件锁而跳过；长时间存在且没有锁的文件会在超过临时文件 TTL 后删除。

### 锁文件数量持续增加

锁文件在线阶段会复用且不会自动删除，这不代表对象仍在使用。选择维护窗口，停止全部 worker 后执行 `clear-locks`。

### 清理后文件再次出现

这是正常行为。业务处理再次需要本地路径时，系统会从 MinIO 重新物化该对象。

## 10. 当前边界

- 缓存扫描只识别 `${STORAGE_CACHE_DIR}/{bucket}/{object_key}` 结构的普通文件；根目录散落文件、符号链接及无法映射的异常路径会被跳过，不会进入 TTL、LRU、孤儿扫描或 `clear`。这类文件需要停机确认后人工处理。
- 缓存有效性在命中时主要校验文件大小；SHA-256 在新下载完成时校验，不会在每次命中时重新计算。
- 访问热度使用本地文件 mtime，是近似 LRU，而不是维护完整的逐次访问队列。
- Linux `flock` 是当前并发保护的基础，因此缓存目录应使用支持该锁语义的本地文件系统。
- `STORAGE_CACHE_DRY_RUN=true` 不会阻止文件物化，也不影响显式 `clear --yes`；它只作为策略清理的默认预演设置。
