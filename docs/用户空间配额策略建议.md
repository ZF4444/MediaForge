# 用户空间配额策略建议

本文讨论 MediaForge 当前统一存储下的用户空间配额策略，包括：

- 当前实现现状
- 现有策略的优点与缺口
- 更合理的配额模型建议
- 建议的默认值
- 后续落地优先级

## 1. 当前实现现状

### 1.1 当前默认配额

当前配置位于 [app/config.py](/home/zhang/workspace/MediaForge/app/config.py:64)：

- `STORAGE_QUOTA_ENABLED`
- `STORAGE_USER_QUOTA_BYTES`

默认值为：

- 配额开启
- 每用户 `10 * 1024 * 1024 * 1024` 字节
- 即 `10 GiB`

### 1.2 当前配额统计方式

统计逻辑位于 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:218) 的 `storage_quota_bytes_for_user()`。

当前做法：

- 统计 `files` 表中当前用户所有未删除文件的 `size_bytes` 总和
- 满足以下条件的记录会被计入：
  - `deleted_at IS NULL`
  - `status <> 'deleted'`

说明：

- 已软删除文件不再计入配额
- 这是合理的
- 当前统计维度是“用户总占用”，不是“按类别分别限额”

### 1.3 当前超限行为

校验逻辑在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:237) 的 `enforce_storage_quota()`。

当前行为：

1. 写入前先检查本次写入大小
2. 查询当前用户已用空间
3. 若 `used_bytes + incoming_bytes > quota_bytes`
4. 抛出 `StorageQuotaExceeded`

异常处理位于 [main.py](/home/zhang/workspace/MediaForge/main.py:518)。

前端会收到：

- HTTP `413`
- `error = "storage_quota_exceeded"`
- `quota_bytes`
- `used_bytes`
- `incoming_bytes`

### 1.4 当前哪些类别会触发配额校验

当前配额适用类别在 [app/services/storage.py](/home/zhang/workspace/MediaForge/app/services/storage.py:212)：

- `input`
- `uploads`
- `output`
- `library`
- `temp`

说明：

- 当前并没有把临时文件和长期资产区分开
- 所有这些类别都占用同一份用户空间

## 2. 当前策略的优点

我认为当前策略有几个明显优点：

### 2.1 模型简单

- 每用户一个总配额
- 一个总已用空间
- 一个统一拒绝逻辑

这让实现复杂度低，维护成本也低。

### 2.2 删除后可立即释放配额

由于配额只统计未删除记录，因此媒体一旦进入删除路径并被标记 `deleted`，配额会立即回收。

这比“删对象但元数据仍占配额”的设计更合理。

### 2.3 与对象存储解耦较好

当前配额并不是扫 MinIO 算出来，而是基于 PostgreSQL 元数据计算。

优点：

- 查询成本低
- 不依赖对象存储列举性能
- 可以稳定做实时配额判断

## 3. 当前策略的主要问题

### 3.1 只有总配额，没有类别策略

现在所有内容都共用同一份空间：

- 用户主动保存的长期资产
- 普通上传
- 模型输出
- 临时文件

这会带来一个问题：

- 短期中间结果可能把长期资产空间挤爆

### 3.2 temp 文件不该与长期资产同权

`temp` 的本质是短期中间文件，不适合与 `library`、`uploads`、`output` 一样长期占用用户空间。

如果 `temp` 也算长期配额：

- 会降低用户对“配额已满”的可理解性
- 用户可能根本不知道是哪些临时产物占满了空间

### 3.3 没有用户可见的空间视图

当前系统虽然有配额判断，但缺少用户侧可见能力：

- 当前已用多少
- 哪一类占用最多
- 哪些文件最大
- 哪些文件最久未用
- 删除什么最有效

没有这些信息，配额机制会变成“只会报错，不会自解释”。

### 3.4 没有专门的清理入口

当前释放配额主要靠删除底层媒体文件，但前端并没有一个统一的“空间管理 / 清理”入口。

这会导致：

- 用户不知道去哪里清空间
- 用户删画布、删引用后以为空间已经释放
- 实际上配额仍然不变

### 3.5 空间管理页不应直接拉原图或全量文件

如果空间管理页一次性拉全量文件，并且卡片直接使用原图 / 原视频 URL：

- 文件一多时首屏会很重
- 会触发大量原始媒体读取
- 翻页和筛选会退化成前端全量过滤

更合理的方式是：

- 先拉空间摘要
- 文件列表单独分页
- 卡片只显示 `/api/files/{file_id}/thumb`
- 详情区再按需显示原始预览

这样可以把“看列表”和“读原文件”解耦，避免空间管理页本身放大存储读取压力。

## 4. 建议的合理策略

我建议采用“总量限制 + 生命周期分层 + 用户可见清理入口”的模型。

### 4.1 保留每用户总配额

这一点不建议取消。

原因：

- 最直观
- 最容易控成本
- 适合单机部署和多人部署

建议：

- 保留总配额作为硬上限

### 4.2 增加类别分层思维

建议把文件分成两大类：

1. 长期资产
   - `library`
   - `uploads`
   - 用户明确保留的 `output`
2. 可回收产物
   - `temp`
   - 普通 `input`
   - 未收藏、未归档的 `output`

这样可以避免所有内容争同一块空间时的策略失真。

### 4.3 temp 不应按长期资产对待

建议：

- `temp` 可以占总配额，但 TTL 要非常短
- 更理想的做法是：
  - `temp` 单独池子
  - 更强制的自动回收
  - 不作为长期空间管理重点

如果短期无法改太多，最少也应该保证：

- `temp` 的自动清理足够快
- 用户界面里能看到这部分占用

### 4.4 派生文件不应重复计费

系统会生成：

- 缩略图
- 视频海报

这些文件是系统派生物，不是用户主动资产。

建议：

- 不把派生对象单独计入配额
- 当前实现基于 `files.size_bytes` 统计主对象，这个方向是正确的

### 4.5 配额应该有分层提示，而不是只在满了时报错

建议至少增加 3 个阈值：

- 80%：轻提示
- 95%：强提示
- 100%：拒绝新写入

这样比“直到 100% 才知道满了”更合理。

### 4.6 自动回收应优先作用于可回收内容

建议：

- `temp`：强制短 TTL
- `input`：较短保留期
- `output`：可配置保留期
- `library`：默认不自动清

核心原则：

- 自动回收优先清系统产物
- 用户主动保存的长期资产默认不自动删

## 5. 建议的默认数值

下面是我认为比较稳妥的默认建议。

### 5.1 单机 / 个人使用场景

- 总配额：`10 GiB`
- `temp`：3 天自动清
- `input`：30 天自动清
- `uploads`：30 或 60 天自动清
- `output`：30 天自动清
- `library`：默认不自动清

这套策略比较接近当前项目方向，迁移成本低。

### 5.2 多人共享部署场景

建议更保守：

- 总配额：`2-5 GiB / 用户`
- 必须有后台清理
- 必须有空间统计页
- 最好有管理员可调配额能力

原因：

- 多人部署时，10 GiB/人很容易导致总存储膨胀

## 6. 用户侧必须补的能力

如果只做后端配额，而不做前端空间管理，用户体验会很差。

建议前端至少具备：

- 当前已用空间
- 总空间
- 各类别占用
- 最大文件列表
- 最近生成结果列表
- 批量删除入口
- 一键清理临时 / 旧输出

建议新增独立页面或弹窗：

- “空间管理”
- 或 “存储管理”

## 7. 我认为最值得优先落地的 3 件事

### 7.1 增加空间统计接口

接口至少返回：

- `used_bytes`
- `quota_bytes`
- `remaining_bytes`
- `usage_by_category`
- `top_files`

### 7.2 增加统一清理入口

至少支持：

- 清理历史生成结果
- 清理本地上传素材
- 清理旧输出
- 清理临时文件

### 7.3 增加未引用文件识别能力

因为当前很多媒体是“被画布或历史引用”的，如果只给用户看文件列表，不知道哪些能安全删。

建议后续支持：

- 识别是否仍被画布引用
- 识别是否仍被历史记录引用
- 标记“孤儿文件”

## 8. 推荐结论

我认为当前项目最合理的配额策略不是单纯“每人 10GiB”，而是下面这套原则：

1. 保留每用户总配额上限
2. 把长期资产和可回收产物分层处理
3. 已删除媒体应立即释放配额
4. 派生文件不重复计费
5. 自动回收优先清临时与普通输出
6. 用户必须能看见空间去哪了
7. 用户必须有明确的释放配额入口
8. 空间管理列表应采用分页 + 缩略图，而不是全量原图加载

## 9. 适合当前仓库的实施顺序

建议按这个顺序推进：

1. 增加“当前已用空间 / 总空间”接口
2. 增加按类别统计
3. 增加前端“空间管理”入口
4. 增加批量删除能力
5. 再考虑更细的类别配额或管理员级配额配置

这样能先解决最真实的问题：

- 配额满了时用户不知道为什么
- 用户不知道删什么最有效
- 删了画布但空间不变造成困惑
