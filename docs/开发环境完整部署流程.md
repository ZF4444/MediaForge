# MediaForge 开发环境完整部署流程

本文适用于 Ubuntu 24.04，以及启用 systemd 的 WSL2 Ubuntu。所有命令如无特别说明，均在 Ubuntu 终端、项目根目录执行。

开发环境使用 Ubuntu 原生 Docker Engine 和 Docker Compose，运行 API、画布 Worker、PostgreSQL、Redis、MinIO，并通过 Node 容器构建前端。宿主机无需安装 Python、uv、Node.js、FFmpeg 或独立数据库服务。

## 1. 准备 Ubuntu

安装基本工具：

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl git openssl
```

WSL2 用户先确认 systemd 已启用：

```bash
systemctl is-system-running
```

如 systemd 未启用，在 `/etc/wsl.conf` 中保留已有配置，补充：

```ini
[boot]
systemd=true
```

然后在 Windows PowerShell 执行 `wsl --shutdown`，再打开 Ubuntu。该命令会停止当前所有 WSL 发行版，请先保存工作。

如果安装过 Docker Desktop，在其 Settings → Resources → WSL Integration 中关闭当前 Ubuntu 的集成。避免 Desktop 注入的 CLI、socket 和凭据助手与原生 Engine 混用。

项目建议放在 Ubuntu 文件系统中，例如 `~/workspace/MediaForge`，避免放在 `/mnt/c/` 下造成文件监听和大量小文件读写缓慢。

## 2. 安装原生 Docker Engine 和 Compose

以下使用 [Docker 官方 Ubuntu APT 安装方式](https://docs.docker.com/engine/install/ubuntu/)。已有 Docker Engine 的机器先检查版本，无需重复安装。如果装有 `docker.io`、旧版 `docker-compose` 或独立的 `containerd`，先按官方文档处理冲突软件包；不要删除已有容器数据。

配置仓库：

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker containerd
sudo usermod -aG docker "$USER"
```

重新登录 Ubuntu，使 docker 用户组生效，然后验证：

```bash
docker version
docker compose version
docker buildx version
systemctl is-active docker containerd
docker context show
docker info --format '{{.Name}} | {{.OperatingSystem}} | {{.DockerRootDir}}'
```

要求 Compose **2.24.4 或更新版本**，开发配置使用 `!override`。`docker info` 的服务端应显示当前 Ubuntu，默认数据目录为 `/var/lib/docker`，而非 Docker Desktop。

若当前 context 仍指向 Desktop，切换到原生 socket：

```bash
# ubuntu-native 尚不存在时创建；已有时检查其 Endpoint 即可。
docker context create ubuntu-native --docker host=unix:///var/run/docker.sock
docker context use ubuntu-native
```

镜像、容器和卷由 Ubuntu 管理。新安装的 Engine 如启用 containerd 镜像存储，镜像内容还会使用 `/var/lib/containerd`。日常通过 Docker 命令管理，不直接修改这些目录。

## 3. 准备代码和环境文件

从项目代码仓库检出代码，进入包含 `Dockerfile` 和 `README.md` 的项目根目录。

首次创建配置；已有配置不要覆盖：

```bash
cp config/dev/.env.example config/dev/.env
chmod 600 config/dev/.env
openssl rand -hex 32
```

将生成值填入 `config/dev/.env` 的 `APP_SECRET_KEY`。该密钥用于加密数据库中的 AI 连接密钥，创建后应固定保存并随数据备份。恢复已有数据库时必须使用原密钥。

重点配置：

| 变量 | 用途 |
| --- | --- |
| `APP_IMAGE` | 本地应用镜像名，默认 `mediaforge:dev` |
| `POSTGRES_IMAGE`、`REDIS_IMAGE` | 数据库和缓存镜像 |
| `MINIO_IMAGE`、`MINIO_SOURCE_REF` | MinIO 本地镜像名和源码版本 |
| `POSTGRES_USER`、`POSTGRES_DB`、`POSTGRES_PASSWORD` | PostgreSQL 初始化账号和数据库 |
| `REDIS_PASSWORD` | Redis 密码 |
| `MINIO_ROOT_USER`、`MINIO_ROOT_PASSWORD` | MinIO 账号密码 |
| `APP_SECRET_KEY` | 应用加密密钥，不能随意更换 |
| `DEV_HTTP_PORT` | 宿主机 HTTP 端口，默认 `3000` |
| `DEV_HTTP_BIND` | 默认 `127.0.0.1`；需通过 Ubuntu 网卡或局域网访问时设为 `0.0.0.0` |
| `DATA_ROOT` | 兼容生产 Compose 定义的插值变量；开发数据实际使用命名卷，不写入此路径 |

模板密码仅用于本地开发。自行设置密码时建议使用 `openssl rand -hex 24` 生成的十六进制字符串，避免连接 URL 的特殊字符编码问题。不要提交 `.env`。

API 和 Worker 的内部地址由 Compose 注入：PostgreSQL 使用 `postgres:5432`，Redis 使用 `redis:6379`，MinIO 使用 `minio:9000`。不要把它们改成容器内的 `127.0.0.1`。开发配置不需要再复制到 `config/.env`。

### 下载缓慢时配置镜像源

可在开发环境文件中启用：

```dotenv
DEBIAN_MIRROR=mirrors.ustc.edu.cn
GOPROXY=https://goproxy.cn,direct
```

分别影响应用/MinIO 镜像中的 Debian 包下载和 MinIO 的 Go 依赖下载；不会配置 Docker Hub、npm 或 Python 包镜像。

`FRONTEND_IMAGE` 默认无需填写。只有已导入并标记了本地 Node 镜像时，才使用对应本地标签；新部署不要直接填写不存在的 `mediaforge-node:22-dev`。

## 4. 构建并启动

```bash
# 仅检查配置，不输出展开后的密码
docker compose -f config/dev/compose.yml config --quiet

# 构建镜像并后台启动
./scripts/dev.sh up
```

等价命令：

```bash
docker compose -f config/dev/compose.yml up -d --build
```

首次启动会构建应用和 MinIO 镜像；MinIO 从指定版本源码编译，首次耗时较长。Node 容器执行 `npm ci && npm run build`，成功后退出，API 与 Worker 等待前端构建完成以及基础设施健康后启动。

查看进度：

```bash
./scripts/dev.sh ps -a
./scripts/dev.sh logs
# 前端构建输出单独查看
docker compose -f config/dev/compose.yml logs -f frontend
```

预期 API、PostgreSQL、Redis、MinIO 显示 `healthy`，Worker 保持 `Up`，frontend 为 `Exited (0)`。Worker 没有独立 HTTP 健康检查，应结合日志确认启动成功。

## 5. 验证部署

```bash
curl -fsS http://127.0.0.1:3000/health/live
curl -fsS http://127.0.0.1:3000/health/ready
```

就绪响应应包含 `ready: true`，以及 PostgreSQL、Redis、MinIO 三项 `ok`。

| 入口 | 默认地址 |
| --- | --- |
| 应用 | http://localhost:3000 |
| MinIO API | http://127.0.0.1:19000 |
| MinIO 控制台 | http://127.0.0.1:19001 |
| PostgreSQL 调试端口 | `127.0.0.1:15432` |
| Redis 调试端口 | `127.0.0.1:16379` |

浏览器打开应用，按页面流程注册/登录，在 API 设置页配置需要使用的供应商连接和模型。AI 连接及供应商密钥保存在数据库中。

WSL 用户还应从 Windows 浏览器检查 http://localhost:3000。若通过旧 Windows portproxy 转发到 Ubuntu 网卡地址，需设置 `DEV_HTTP_BIND=0.0.0.0`，并确认转发目标 IP 为当前 Ubuntu IP。此绑定也会允许网络访问；仅本机开发时优先使用模板的回环绑定。

## 6. 日常开发

| 修改内容 | 操作 |
| --- | --- |
| `app/`、`main.py` | API 自动重载；涉及 Worker 的改动还需执行 `./scripts/dev.sh worker` |
| `skills/` 中的技能正文和资源文件 | 已挂载到容器，下次读取时生效，无需构建镜像或重启；验证时发起新的 Agent 请求 |
| 新增技能或修改技能 manifest 元数据 | `docker compose -f config/dev/compose.yml restart api worker`，启动时同步数据库中的技能注册信息 |
| 前端源码 | `./scripts/dev.sh frontend`，成功后刷新浏览器 |
| `pyproject.toml`、`uv.lock`、Dockerfile | `docker compose -f config/dev/compose.yml up -d --build api worker` |
| `frontend/package-lock.json` | `./scripts/dev.sh frontend` 会重新执行 `npm ci` |
| `.env` 或 Compose 配置 | `docker compose -f config/dev/compose.yml up -d`；仅 `restart` 不会更新容器环境变量 |
| MinIO 构建参数 | `docker compose -f config/dev/compose.yml up -d --build minio`，更新版本前先备份 |

`skills/` 随项目源码挂载到 `/app/skills`。技能目录、`SKILL.md` 正文及文本资源由服务运行时从文件系统读取；已经加载到正在执行的 Agent 上下文中的内容不会因文件修改而自动替换。新增技能时，`SKILL.md` 的 manifest `name` 必须与目录名一致，且需要提供 `description`。启动时会同步技能描述和内容摘要到数据库，所以需要同步注册元数据时应重启 API 和 Worker。

Python 依赖位于镜像的 `/opt/venv`，不会使用或覆盖宿主机 `.venv`。API 只监听应用代码，避免扫描运行数据和构建目录。前端采用构建后刷新方式，没有启动 Vite HMR 服务。

常用命令：

```bash
./scripts/dev.sh logs
./scripts/dev.sh worker
./scripts/dev.sh test
# 可追加 pytest 参数
./scripts/dev.sh test tests/test_health.py -q

# 前端测试：复用 Node 容器及其 node_modules 卷
# 首次运行前先完成前端构建，确保依赖已安装
docker compose -f config/dev/compose.yml run --rm --no-deps frontend npm test

# 进入应用容器
docker compose -f config/dev/compose.yml exec api sh

# 停止服务并保留容器
./scripts/dev.sh stop
# 删除容器和网络，保留所有开发数据卷
./scripts/dev.sh down
# 再次启动
./scripts/dev.sh up
```

容器使用 `unless-stopped` 重启策略：Engine 重启后会恢复原本运行的服务；手动停止或 `down` 后需要手动启动。WSL 的 systemd 自启发生在 Ubuntu 启动时，不代表 Windows 启动后 Ubuntu 一定已经运行。

## 7. 数据保存和备份恢复

项目名固定为 `mediaforge-dev`。开发数据位于以下命名卷：

| 卷后缀（完整名以 `mediaforge-dev_` 开头） | 内容 |
| --- | --- |
| `postgres-data` | 数据库，包括用户、画布、配置、加密密钥 |
| `redis-data` | Redis AOF、任务队列和缓存 |
| `minio-data` | 文件对象和 MinIO 元数据 |
| `app-data` | 应用本地数据、缓存和临时文件 |
| `app-workflows` | 工作流文件 |
| `app-logs` | API、Worker 日志 |
| `frontend-static` | 前端构建产物 |
| `frontend-modules` | 前端 npm 依赖 |

宿主机的 `data/`、`logs/`、`workflows/` 不会自动合并到这些卷。不要执行 `down -v` 或删除上述卷，除非确实要清空开发数据。

### 停写备份整个开发环境

以下是适合开发环境的停机物理备份，保留全部卷、文件权限、环境配置和镜像。运行前先等待正在执行的生成任务结束。备份期间不要启动其他服务写入这些卷。

```bash
set -euo pipefail
backup_dir="$PWD/backups/dev-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
chmod 700 "$backup_dir"
cp config/dev/.env "$backup_dir/dev.env"
chmod 600 "$backup_dir/dev.env"

# 保存应用和基础设施的确切镜像，供同版本物理恢复使用
# 用容器的实际镜像 ID，兼容带摘要的 Node 镜像
docker compose -f config/dev/compose.yml ps -aq |
  xargs -r docker inspect --format '{{index .Config.Labels "com.docker.compose.service"}} {{.Config.Image}} {{.Image}}'   > "$backup_dir/images.txt"
mapfile -t image_ids < <(
  docker compose -f config/dev/compose.yml ps -aq |
    xargs -r docker inspect --format '{{.Image}}' | sort -u
)
docker image save -o "$backup_dir/images.tar" "${image_ids[@]}"

docker compose -f config/dev/compose.yml stop
mapfile -t volume_names < <(
  docker volume ls --filter label=com.docker.compose.project=mediaforge-dev --format '{{.Name}}'
)
for volume_name in "${volume_names[@]}"; do
  docker run --rm --network none --user 0 --entrypoint tar \
    -v "$volume_name:/volume:ro" mediaforge:dev \
    -C /volume -cpf - . > "$backup_dir/$volume_name.tar"
done
printf '%s\n' "${volume_names[@]}" > "$backup_dir/volumes.txt"
(
  cd "$backup_dir"
  sha256sum ./*.tar dev.env volumes.txt images.txt > SHA256SUMS
)
docker compose -f config/dev/compose.yml up -d
```

上述归档命令假设模板中的应用镜像名为 `mediaforge:dev`；若改过 `APP_IMAGE`，同步替换。备份前服务应已完整启动过，确保镜像和卷齐全。保存代码对应的 Git 提交及未提交改动，恢复时使用相同版本的代码和 Compose 定义。

备份包含密钥和业务数据，应限制访问并复制到独立存储。命令失败时先处理失败原因，确认备份完整后再恢复服务，不要误以为备份已经成功。

### 恢复备份

物理恢复须使用备份时相同版本的数据库和存储镜像。跨 PostgreSQL 主版本迁移应改用 `pg_dump` / `pg_restore`，不要直接复用数据目录。

1. 在空的目标开发环境中准备相同代码、Compose 配置和镜像标签；已有数据的环境先另行备份。
2. 将备份中的 `dev.env` 恢复到 `config/dev/.env`，保持原 `APP_SECRET_KEY`。
3. 校验归档并加载镜像：

   ```bash
   # 替换为实际备份目录
   backup_dir=/absolute/path/to/backups/dev-YYYYMMDD-HHMMSS
   (cd "$backup_dir" && sha256sum -c SHA256SUMS)
   docker image load -i "$backup_dir/images.tar"
   ```

   `images.txt` 每行记录服务名、原镜像引用、实际镜像 ID。按镜像 ID 导出的镜像可能没有原标签；使用 `docker tag <镜像ID> <原镜像标签>` 恢复应用、MinIO、PostgreSQL、Redis 的标签。带摘要的 Node 引用不能直接用作标签，可执行 `docker tag <Node镜像ID> mediaforge-node:restore`，再在 `config/dev/.env` 中设置 `FRONTEND_IMAGE=mediaforge-node:restore`。

4. 确认目标同名数据卷不存在或为空，不要将归档叠加恢复到已有数据库卷。停止所有目标服务后恢复：

   ```bash
   while IFS= read -r volume_name; do
     docker volume create \
       --label com.docker.compose.project=mediaforge-dev \
       --label "com.docker.compose.volume=${volume_name#mediaforge-dev_}" \
       "$volume_name"
     docker run --rm -i --network none --user 0 --entrypoint tar \
       -v "$volume_name:/volume" mediaforge:dev \
       -C /volume -xpf - < "$backup_dir/$volume_name.tar"
   done < "$backup_dir/volumes.txt"
   ```

5. 执行 `docker compose -f config/dev/compose.yml up -d --no-build --pull never`，核对就绪检查、登录、数据库记录、文件和任务状态。前端服务仍会执行依赖安装与构建，完全离线时还需预先准备 npm 缓存或可用包源。

## 8. 常见问题

### Docker 连接失败或连到了 Desktop

```bash
systemctl status docker --no-pager
docker context ls
ls -l /usr/bin/docker
printenv DOCKER_HOST DOCKER_CONTEXT
```

检查环境变量是否覆盖了 context；CLI 不应仍链接到 `/mnt/wsl/docker-desktop/`。如拉取镜像提示找不到 `docker-credential-desktop.exe`，检查 `~/.docker/config.json` 中残留的 Desktop 凭据助手配置，备份后移除相应引用。

### Docker socket 权限不足

确认当前用户属于 docker 组，并重新登录。不要通过把 socket 设置为全员可写来绕过权限。

### 3000 端口冲突或 Windows 无法访问

```bash
ss -lntp | rg ':3000'  # 无 rg 时可用 grep
docker compose -f config/dev/compose.yml ps
```

先在 Ubuntu 检查就绪接口，再检查 Windows 转发规则和绑定地址。可通过 `DEV_HTTP_PORT` 调整端口，修改后用 `up -d` 重建 API 容器。

### 数据库改密码后连接失败

`POSTGRES_*` 初始化变量仅在空数据库卷首次启动时初始化账号。修改 `.env` 不会自动更改已存在的 PostgreSQL 用户密码；应先通过数据库管理命令修改密码，再同步环境配置。不要通过删除卷解决密码不一致。

### API 一直未启动

查看 `ps -a` 和 `logs frontend postgres redis minio`。前端构建失败或基础设施未健康时，API 和 Worker 会等待。`frontend` 的退出码 0 正常，非零则需要排查。

### 前端改动未生效

执行 `./scripts/dev.sh frontend`，确认构建成功并刷新浏览器。宿主机直接构建的 `static/dist` 会被容器内的静态资源卷遮盖，应使用容器构建流程。

### 文件权限错误

应用镜像使用 UID 10001，MinIO 镜像也使用 UID 10001。自定义挂载目录需允许对应容器用户访问。不要递归修改整个仓库所有权；优先使用默认命名卷。

### 构建下载缓慢或失败

根据失败环节分别检查 Docker 镜像仓库、Debian、npm、Python 或 Go 包源。MinIO 首次编译耗时较长，通过构建日志确认进度。更改镜像源后重新执行 `./scripts/dev.sh up`，不要删除数据卷。
