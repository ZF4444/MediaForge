# 日志系统说明

> 文档日期：2026-07-13
> 适用范围：Infinite-Canvas 当前实现

## 一、当前状态

项目已经从分散的控制台输出切换为统一的结构化日志系统。目前已实现：

- JSON 行日志
- 应用、访问、审计、任务、错误五类日志分流
- HTTP 请求链路标识
- 登录用户上下文
- 异步生成任务上下文
- 敏感字段和本地绝对路径脱敏
- 按天轮转、gzip 压缩和分类保留
- HTTP 高频成功轮询降噪
- 核心异常堆栈记录
- 认证、删除、移动、导入和配置修改等操作审计

日志系统不改变现有接口的请求和响应模型。除响应增加 `X-Request-ID` 外，日志均作为业务旁路能力运行。

## 二、代码结构

```text
app/
  core/
    logging.py          # JSON 格式、脱敏、handler、分流和统一 logger API
    log_context.py      # request/user/task 上下文
  middleware/
    request_logging.py  # HTTP 请求上下文、访问日志和异常日志
main.py                 # 日志初始化、认证上下文绑定和任务日志接入
tests/
  test_logging.py       # 格式、脱敏、中间件、降噪和轮转测试
```

应用启动时由 `main.py` 调用 `configure_logging()`。该函数在单个 Python 进程内只初始化一次。

## 三、日志分类

默认日志目录为项目根目录下的 `logs/`。目录已加入 `.gitignore`，运行日志不会进入 Git。

| 文件 | Logger 命名空间 | 内容 | 默认保留 |
| --- | --- | --- | ---: |
| `app.log` | `aistudio.app.*` | 业务运行、外部调用、WebSocket 和普通异常 | 15 天 |
| `access.log` | `aistudio.access` | HTTP 方法、路径、状态码、耗时和客户端信息 | 15 天 |
| `audit.log` | `aistudio.audit` | 登录、删除、移动、导入和配置修改 | 180 天 |
| `task.log` | `aistudio.task.*` | 生成任务提交、轮询、完成和失败 | 30 天 |
| `error.log` | 所有命名空间 | 所有 `ERROR` 和 `CRITICAL` 记录的副本 | 30 天 |

日志文件使用延迟创建：某一分类第一次产生事件后，对应文件才会出现。因此刚启动但尚无审计操作时，没有 `audit.log` 属于正常现象。

应用日志默认还会输出到标准输出。访问、审计和任务日志默认只写对应文件，错误日志会额外写入 `error.log`。

## 四、JSON 格式

每行是一条独立 JSON 记录，便于使用 `jq`、Loki、ELK 或 OpenSearch 解析。

```json
{
  "ts": "2026-07-13T16:47:12.102+08:00",
  "level": "INFO",
  "logger": "aistudio.access",
  "event": "http_request",
  "message": "request completed",
  "request_id": "req_5e7ff9d6d7d04f8fb15bdacbb164ccdd",
  "trace_id": "trc_367606e73f74488c99502ae6290f20a1",
  "user_id": "alice",
  "username": "Alice",
  "task_id": null,
  "method": "GET",
  "path": "/api/providers",
  "status_code": 200,
  "duration_ms": 18.42,
  "client_ip": "127.0.0.1",
  "user_agent": "Mozilla/5.0"
}
```

### 4.1 公共字段

| 字段 | 说明 |
| --- | --- |
| `ts` | 带本地时区的 ISO 8601 时间，精确到毫秒 |
| `level` | `DEBUG`、`INFO`、`WARNING`、`ERROR` 或 `CRITICAL` |
| `logger` | Logger 完整命名空间 |
| `event` | 稳定的机器可检索事件名 |
| `message` | 面向开发者的简短说明 |
| `request_id` | 单次 HTTP 请求标识 |
| `trace_id` | 跨服务链路标识；当前未传入时在入口生成 |
| `user_id` | 当前认证用户 ID |
| `username` | 当前认证用户名 |
| `task_id` | 异步或上游生成任务标识 |

没有相应上下文的字段值为 `null`，不会从 JSON 中省略。

### 4.2 HTTP 字段

- `method`
- `path`
- `status_code`
- `duration_ms`
- `client_ip`
- `user_agent`

访问日志不记录请求体、响应体、Cookie、Authorization 和查询参数。

### 4.3 外部调用字段

现有外部调用按场景使用以下字段：

- `provider`
- `endpoint`
- `operation`
- `status_code`
- `retry_count`
- `error_type`
- `response_excerpt`

响应摘要会截断后再进入统一脱敏流程，不记录完整第三方响应。

### 4.4 审计字段

- `action`
- `resource_type`
- `resource_id`
- `result`
- `before`
- `after`
- `resource_ids`
- 计数字段，例如 `removed_count`、`moved_count`

`before` 和 `after` 只记录识别操作所需的关键摘要，不保存完整业务对象。

### 4.5 任务字段

- `task_id`
- `provider`
- `operation`
- `status`
- `retry_count`
- `duration_ms`
- `upstream_task_id`
- `model`

## 五、请求链路

### 5.1 Request ID

HTTP 请求进入应用时，中间件按以下规则确定 `request_id`：

1. 如果请求头 `X-Request-ID` 是 8 至 128 位的字母、数字、下划线、点、冒号或连字符，则沿用该值。
2. 否则生成 `req_<32位十六进制UUID>`。
3. 响应头写入 `X-Request-ID`。

发生问题时，前端或调用方应优先提供响应中的 `X-Request-ID`。运维人员可以用它关联 `access.log`、`app.log`、`audit.log` 和 `task.log`。

### 5.2 Trace ID

请求头 `X-Trace-ID` 的校验规则与 Request ID 相同。没有合法值时生成 `trc_<32位十六进制UUID>`。

当前实现使用自定义 `X-Trace-ID`，尚未解析 W3C `traceparent`。

### 5.3 用户上下文

认证中间件成功解析会话后，将 `user_id` 和 `username` 同时绑定到：

- 业务使用的 `current_user_var`
- 日志使用的 ContextVar
- `request.state`，用于请求结束后的访问日志

登录和注册请求在建立会话前没有认证上下文，因此审计事件使用 `resource_id` 标识目标用户；登录成功和 SSO 登录事件还会显式写入 `user_id`、`username`。

### 5.4 任务上下文

画布在线生图和 ComfyUI 后台任务在提交时写 `task_submitted`，执行协程启动后绑定 `task_id`，后续日志自动携带该任务标识。

ModelScope 角度生成、Z-Image 和通用生图在获得上游任务 ID 后绑定任务上下文。

## 六、访问日志规则

所有 HTTP 请求原则上记录一条 `http_request`。日志级别按状态码确定：

| 状态码 | 级别 |
| --- | --- |
| `< 400` | `INFO` |
| `400-499` | `WARNING` |
| `>= 500` | `ERROR` |

以下高频接口仅在状态码为 `200` 时静默：

- `/api/canvases`
- `/api/canvases/trash`
- `/api/canvases/*/meta`

这些接口的非 `200` 响应始终记录。应用已经关闭 `uvicorn.access`，避免同一请求产生两份访问日志。

客户端 IP 默认取 ASGI 连接地址。只有显式设置 `LOG_TRUST_PROXY_HEADERS=true` 后，才读取 `X-Forwarded-For` 的第一个地址。该选项只能在入口代理会覆盖外部同名请求头时开启。

## 七、脱敏规则

所有日志在 JSON 序列化前统一递归脱敏，业务模块不能绕过该过程直接写文件。

### 7.1 按字段名脱敏

字段名包含以下关键字时，字段值会被遮蔽：

- `authorization`
- `cookie`
- `password` / `passwd`
- `secret`
- `api_key`
- `access_key`
- `token`
- `session`
- `credential`

长度大于 8 的值保留前 4 位和后 4 位，例如：

```text
abcd1234567890wxyz -> abcd***wxyz
```

短值统一变为 `***`。

### 7.2 字符串内容脱敏

普通消息和异常文本中的以下形式也会被处理：

- `Bearer <credential>`
- `api_key=<credential>`
- `token: <credential>`
- `Authorization <credential>`
- Cookie、Secret 和 Access Key 的同类赋值形式

### 7.3 路径脱敏

- 项目目录内的文件路径转换为相对路径。
- 项目目录外的文件路径只保留文件名。
- 异常文本中位于 `/home`、`/root`、`/tmp`、`/var`、`/srv` 和 `/opt` 下的路径会被缩短。
- HTTP 路径如 `/api/providers` 保持原值，确保可以正常检索。

### 7.4 Prompt

不要把完整 prompt 写入日志。需要定位内容一致性时，使用：

```python
from app.core.logging import prompt_summary

logger.info(
    "prompt accepted",
    extra={"event": "prompt_accepted", "prompt": prompt_summary(prompt)},
)
```

该摘要只包含字符长度和 SHA-256 的前 16 位。

## 八、轮转与环境配置

日志使用 `TimedRotatingFileHandler`，按服务器本地时间每天午夜轮转。历史文件命名形如：

```text
app.log.2026-07-12.gz
access.log.2026-07-12.gz
```

可用环境变量：

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `LOG_DIR` | `<项目根>/logs` | 日志目录 |
| `LOG_LEVEL` | `INFO` | `aistudio` 根 Logger 级别 |
| `LOG_STDOUT` | `true` | 是否向标准输出同步写应用日志 |
| `LOG_TRUST_PROXY_HEADERS` | `false` | 是否信任 `X-Forwarded-For` |
| `LOG_APP_RETENTION_DAYS` | `15` | 应用日志历史文件数 |
| `LOG_ACCESS_RETENTION_DAYS` | `15` | 访问日志历史文件数 |
| `LOG_AUDIT_RETENTION_DAYS` | `180` | 审计日志历史文件数 |
| `LOG_TASK_RETENTION_DAYS` | `30` | 任务日志历史文件数 |
| `LOG_ERROR_RETENTION_DAYS` | `30` | 错误日志历史文件数 |

保留值至少按 1 处理。配置在进程导入日志模块时读取，修改后需要重启服务。

`LOG_LEVEL` 作用于整个 `aistudio` Logger 树。设置为 `WARNING` 或更高级别会同时丢弃正常访问、成功审计和任务生命周期的 `INFO` 事件，因此需要完整审计记录的生产环境应保持 `INFO`。

服务启动时会创建 `LOG_DIR`。运行账号必须对其父目录具有创建权限，并对日志目录具有持续写入和重命名权限，否则日志初始化或轮转可能失败。

生产环境建议：

```bash
LOG_LEVEL=INFO
LOG_STDOUT=true
LOG_TRUST_PROXY_HEADERS=false
```

只有确认反向代理可信且已清理外部 `X-Forwarded-For` 时，才将最后一项改为 `true`。

## 十、当前任务事件

任务日志目前覆盖画布生成、ComfyUI、ModelScope 和角度生成流程，使用的主要事件包括：

- `task_submitted`
- `task_started`
- `task_poll_started`
- `task_poll`
- `task_poll_retry`
- `task_poll_pending`
- `task_completed`
- `task_failed`

`task_poll` 使用 `DEBUG`，生产环境默认不输出每次成功轮询；重试使用 `WARNING`，提交、开始和完成使用 `INFO`，失败使用 `ERROR`。

## 十一、开发接入规范

### 11.1 应用日志

```python
from app.core.logging import get_logger

logger = get_logger("assets")

logger.info(
    "asset created",
    extra={
        "event": "asset_created",
        "resource_id": asset_id,
        "resource_type": "asset_item",
    },
)
```

要求：

- 每条业务日志提供稳定的 `event`。
- `message` 简短描述发生了什么，不拼接大对象。
- 结构化字段放在 `extra` 中。
- 不使用 Python `LogRecord` 的保留字段作为 `extra` 键。
- 不直接记录请求体、完整 prompt、文件内容或第三方完整响应。

### 11.2 异常日志

必须在异常处理块中使用 `logger.exception()`：

```python
try:
    await call_provider()
except Exception:
    logger.exception(
        "provider call failed",
        extra={
            "event": "provider_call_failed",
            "provider": "modelscope",
            "operation": "image_generation",
        },
    )
    raise
```

它会自动附带当前异常堆栈。可恢复问题使用 `WARNING`，明确失败使用 `ERROR`，不要重新使用 `print()`。

### 11.3 审计日志

```python
from app.core.logging import audit_event

audit_event(
    "asset_deleted",
    action="delete",
    resource_type="asset_item",
    resource_id=asset_id,
    before={"name": asset_name, "kind": asset_kind},
)
```

失败审计应显式设置：

```python
audit_event(
    "asset_delete_failed",
    action="delete",
    resource_type="asset_item",
    resource_id=asset_id,
    result="failure",
    error_type=type(exc).__name__,
)
```

不要在 `before`、`after` 中放完整数据库行、密钥或大型嵌套对象。

### 11.4 任务日志

```python
from app.core.log_context import bind_log_context
from app.core.logging import get_task_logger

task_logger = get_task_logger("export")

bind_log_context(task_id=task_id)
task_logger.info(
    "export started",
    extra={
        "event": "task_started",
        "operation": "export",
        "status": "running",
    },
)
```

后台任务从 HTTP 请求中创建时会继承 ContextVar 的当前副本，但仍应在任务入口显式绑定 `task_id`。

## 十二、排障方法

### 12.1 按 Request ID 查询

```bash
rg 'req_5e7ff9d6d7d04f8fb15bdacbb164ccdd' logs/*.log
```

查询压缩历史：

```bash
zgrep 'req_5e7ff9d6d7d04f8fb15bdacbb164ccdd' logs/*.gz
```

### 12.2 查看最近错误

```bash
tail -n 100 logs/error.log | jq .
```

### 12.3 查询某个用户的审计记录

```bash
jq 'select(.user_id == "alice")' logs/audit.log
```

### 12.4 查询失败任务

```bash
jq 'select(.event == "task_failed")' logs/task.log
```

### 12.5 查询慢请求

```bash
jq 'select(.duration_ms > 1000)' logs/access.log
```

排障顺序建议：

1. 从调用方获得 `X-Request-ID`。
2. 在 `access.log` 确认路径、状态码和耗时。
3. 用同一 ID 查询 `app.log` 和 `error.log`。
4. 涉及异步生成时，从记录中取得 `task_id`，继续查询 `task.log`。
5. 涉及删除或配置修改时，查询 `audit.log`。

## 十四、当前边界

以下能力尚未实现或不在当前版本范围内：

- 没有直接接入 Loki、ELK、OpenSearch 或 OpenTelemetry。
- `trace_id` 尚未支持 W3C `traceparent`。
- 审计日志是本地文件，不是防篡改审计存储。
- 没有为日志目录实现磁盘用量告警。
- WebSocket 尚未建立与 HTTP 等价的认证链路上下文。
- 不是所有业务成功事件都记录应用日志；当前优先覆盖异常、敏感操作和长任务。
- 当前文件轮转面向单服务进程。多个 Uvicorn worker 同时写同一组文件时，标准 `TimedRotatingFileHandler` 不能保证轮转互斥。

因此，当前部署应保持单 worker 写本地日志。需要多 worker 或多副本时，建议让各进程只写标准输出，由容器运行时或日志采集器统一收集；或者引入支持多进程并发的日志 handler，再启用共享文件轮转。

## 十五、后续演进建议

按优先级建议继续补充：

1. 将 stdout JSON 接入 Loki、ELK 或 OpenSearch。
2. 增加日志目录磁盘容量和写入失败监控。
3. 支持 W3C Trace Context，并向第三方 HTTP 调用透传链路标识。
4. 将高价值审计日志同步到独立、限制修改权限的存储。
5. 扩充上传、下载、导出、转码和存储清理的任务完成事件。
6. 为 WebSocket 建立用户和连接级上下文。
