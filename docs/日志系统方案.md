# 日志系统方案

> 日期：2026-07-08
> 适用范围：MediaForge 当前版本

## 一、背景和问题

当前项目不能算真正有日志系统，基本还是控制台输出阶段。

我看了一遍代码，现状比较明确：

- 业务异常和运行状态大量通过 `print(...)` 输出
- `uvicorn.access` 只做了简单静默过滤
- 没有统一日志格式
- 没有请求链路标识
- 没有审计日志
- 没有任务日志
- 没有日志轮转和保留策略

涉及的位置主要有：

- `main.py`
- `app/core/ws.py`
- `app/core/media.py`
- `app/core/auth.py`
- `app/routers/history.py`
- `app/services/prompts.py`

这种状态短期还能凑合看，系统一旦进入多人使用、外部平台调用增多、文件存储迁移、异步任务变多的阶段，问题就会集中暴露：

- 同一个时间段的日志混在一起，很难分清是谁触发的
- 一个请求里发生了什么，没有统一链路可追
- 出错时往往只有一句字符串，没有堆栈和上下文
- 安全相关操作没有单独留痕
- 日志量不可控，后面一样可能反过来把磁盘打满

所以这次要做的不是“把 print 改成 logger”，而是补一套能长期用的日志体系。

## 二、这套日志系统要解决什么

我这里把目标定得比较实际，不追求一步到位接全套可观测平台，先把这几件事解决掉：

### 2.1 排障

要能回答下面这些问题：

- 哪个用户调用了哪个接口
- 哪个请求失败了
- 失败前调用了哪些外部依赖
- 上传、下载、生成、轮询分别卡在哪一步
- 失败时的耗时、状态码、重试次数是多少

### 2.2 审计

要能单独追踪敏感操作：

- 登录 / 登出
- 删除历史记录
- 删除文件
- 删除或移动素材
- 共享目录登记 / 删除 / 导入
- 配置修改

### 2.3 扩展

后面无论是接：

- MinIO
- PostgreSQL
- S3
- 异步任务
- Loki / ELK / OpenSearch

日志字段和输出方式都不能成为阻碍。

### 2.4 控量

日志必须可控，不能再变成新的磁盘压力来源：

- 要轮转
- 要保留周期
- 要区分普通日志和审计日志
- DEBUG 不能在生产环境长期打开

## 三、总体设计

我把日志拆成四类，这样职责清楚，后面接平台也比较好接。

### 3.1 应用日志 `app`

记录业务运行过程里的普通事件：

- 接口内部状态
- 第三方调用摘要
- 文件处理过程
- 普通异常
- 初始化和后台流程

### 3.2 访问日志 `access`

专门记 HTTP 请求：

- 谁请求了什么
- 返回什么状态码
- 花了多久

### 3.3 审计日志 `audit`

专门记敏感操作：

- 谁在什么时间对什么资源做了什么

这个和普通应用日志一定要分开。

### 3.4 任务日志 `task`

专门记长耗时流程：

- 生图
- 生视频
- 上传
- 导出
- 轮询
- 转码
- 抽帧

## 四、日志格式

主格式统一用 JSON 行日志。每一行是一条完整事件，后面无论接文件、stdout、日志平台都方便。

我不建议继续把纯文本日志当主格式，因为后面做筛选、聚合、检索都会很难受。

日志字段先定成下面这一组：

```json
{
  "ts": "2026-07-08T10:23:45.123+08:00",
  "level": "INFO",
  "logger": "mediaforge.api.history",
  "event": "history_saved",
  "message": "history record saved",
  "request_id": "req_01JABCDEF",
  "trace_id": "trc_01JABCDEF",
  "user_id": "alice",
  "username": "alice",
  "path": "/api/history/save",
  "method": "POST",
  "status_code": 200,
  "duration_ms": 42,
  "client_ip": "10.0.0.8",
  "task_id": null,
  "provider": null,
  "resource_type": null,
  "resource_id": null,
  "extra": {}
}
```

### 4.1 必备字段

- `ts`
- `level`
- `logger`
- `event`
- `message`
- `request_id`
- `user_id`

### 4.2 HTTP 相关字段

- `path`
- `method`
- `status_code`
- `duration_ms`
- `client_ip`

### 4.3 任务相关字段

- `task_id`
- `provider`
- `operation`
- `retry_count`

### 4.4 审计相关字段

- `action`
- `resource_type`
- `resource_id`
- `result`
- `before`
- `after`

这里有两个约束：

- `before` / `after` 只存关键差异，不存完整大对象
- `extra` 只做补充，不要把一堆非结构化文本全塞进去

## 五、日志级别约定

日志级别如果不提前定规范，后面一定会失控。这里直接约束死：

### 5.1 DEBUG

只用于开发期排查：

- 临时调试
- 参数摘要
- 第三方响应截断片段

生产默认关闭。

### 5.2 INFO

用于正常业务事件：

- 请求成功
- 文件上传成功
- 任务开始 / 完成
- 状态切换

### 5.3 WARNING

用于可恢复问题：

- 外部依赖波动
- 自动重试
- 回退逻辑
- 非关键功能失败但主流程还能继续

### 5.4 ERROR

用于明确失败：

- 请求失败
- 文件处理失败
- 第三方调用失败
- 数据解析失败
- 任务失败

### 5.5 CRITICAL

只留给系统级故障：

- 服务起不来
- 核心配置损坏
- 关键依赖不可用导致主服务不可用

## 六、当前项目需要记的重点事件

结合现有业务，我这里先把必须纳入日志的事件列清楚，后面按这个清单收口。

### 6.1 认证

- 登录成功
- 登录失败
- 登出
- 会话失效
- 未登录访问受保护资源

### 6.2 文件

- 上传开始 / 成功 / 失败
- 下载开始 / 成功 / 失败
- 删除文件
- 导入本地文件
- 共享目录文件导入

### 6.3 历史和资产库

- 保存历史记录
- 删除历史记录
- 新增素材
- 删除素材
- 移动素材
- 批量操作

### 6.4 外部平台调用

- RunningHub
- ModelScope
- APIMart
- 即梦 CLI
- 后续 MinIO / S3

### 6.5 长任务

- 提交任务
- 开始轮询
- 轮询重试
- 任务完成
- 任务失败
- 导出压缩包
- 视频转码 / 抽帧

### 6.6 WebSocket

- 建连
- 断连
- 广播失败
- 在线人数变化

## 七、日志文件规划

日志目录不要混进业务数据目录，单独放到 `logs/` 下。

```text
logs/
  app.log
  access.log
  audit.log
  task.log
  error.log
```

### 7.1 各文件职责

`app.log`

- 普通应用日志

`access.log`

- 所有 HTTP 访问日志

`audit.log`

- 登录、删除、配置修改这类敏感操作

`task.log`

- 长耗时任务过程日志

`error.log`

- `ERROR` 和 `CRITICAL`

### 7.2 保留和轮转

这里先定一个务实一点的口径：

- `app.log`：按天切分，保留 7 到 15 天
- `access.log`：按天切分，保留 7 到 15 天
- `task.log`：按天切分，保留 15 到 30 天
- `error.log`：保留 30 天
- `audit.log`：保留 180 天以上

旧日志压缩是必须项，不然后面还是会占盘。

## 八、请求链路

当前项目已经通过 `contextvars` 管理用户上下文，这一点正好可以继续利用。日志上下文也按同样方式做。

### 8.1 需要透传的上下文

- `request_id`
- `trace_id`
- `user_id`
- `username`
- `task_id`

### 8.2 请求进入系统时要做的事

1. 生成 `request_id`
2. 读取当前登录用户
3. 记录请求开始时间
4. 请求结束时记录状态码和耗时
5. 如果异常，记录完整堆栈

后面一个请求相关的所有日志，都要能用 `request_id` 串起来。

## 九、代码结构

日志相关代码我建议单独收口，别散在各处。

建议新增：

```text
app/
  core/
    logging.py
    log_context.py
  middleware/
    request_logging.py
```

### 9.1 `app/core/logging.py`

职责：

- 初始化日志配置
- 配置 formatter / handler / filter
- 提供统一的 `get_logger(...)`
- 做 JSON 输出
- 把 `ERROR` 级别日志单独分流到 `error.log`

### 9.2 `app/core/log_context.py`

职责：

- 基于 `contextvars` 管理
  - `request_id`
  - `trace_id`
  - `user_id`
  - `username`
  - `task_id`

### 9.3 `app/middleware/request_logging.py`

职责：

- 建立请求上下文
- 写访问日志
- 写异常日志
- 给后续业务日志补齐请求字段

## 十、访问日志

现在 `main.py` 里只是对 `uvicorn.access` 做了静默过滤，这还不够。访问日志应该在应用层自己补一层。

### 10.1 访问日志至少要有这些字段

- `request_id`
- `user_id`
- `method`
- `path`
- `status_code`
- `duration_ms`
- `client_ip`
- `user_agent`

### 10.2 噪音控制

高频轮询接口可以做降噪，但不能无脑丢：

- `/api/canvases`
- `/api/canvases/*/meta`

这里的规则我定成：

- `200` 成功请求可以按白名单降噪
- `4xx / 5xx` 一律保留

## 十一、应用日志

应用日志是这次改造里最实际的一块，因为它直接对应当前仓库里的大量 `print(...)`。

### 11.1 统一写法

后面不再写：

```python
print(f"下载图片失败: {e}")
```

改成：

```python
logger.exception("download image failed", extra={"event": "image_download_failed"})
```

### 11.2 原因

`logger.exception(...)` 会保留：

- 错误消息
- 堆栈
- 请求上下文
- 用户上下文

单纯 `print(f"{e}")` 只剩一行字符串，排障价值很低。

### 11.3 优先改的地方

我会优先替换这些区域：

1. `main.py` 里第三方调用、轮询、上传下载相关输出
2. `app/core/ws.py`
3. `app/core/media.py`
4. `app/core/auth.py`
5. `app/routers/history.py`
6. `app/services/prompts.py`

## 十二、审计日志

审计日志和应用日志一定要分开。普通异常和“谁删了什么东西”不是一回事。

### 12.1 必须进审计日志的操作

- 登录
- 登出
- 删除历史记录
- 删除本地素材
- 删除资产库条目
- 资产库批量移动
- 共享目录登记 / 删除
- API 配置修改

### 12.2 审计日志字段

```json
{
  "ts": "2026-07-08T10:30:00.123+08:00",
  "level": "INFO",
  "logger": "mediaforge.audit",
  "event": "asset_deleted",
  "action": "delete",
  "user_id": "alice",
  "resource_type": "asset_item",
  "resource_id": "asset_123",
  "result": "success",
  "request_id": "req_01J...",
  "before": {"name": "角色图1"},
  "after": null
}
```

这里的重点是“谁、在什么时候、对什么资源、做了什么、结果如何”。

## 十三、任务日志

这个项目里有很多流程不是一个请求结束就完了，尤其是云任务轮询、生成、上传、转码。这里单独拉一类 `task` 日志比较合适。

### 13.1 适用场景

- 生图
- 生视频
- 上传
- 导出
- 轮询
- 视频转码
- 抽帧

### 13.2 任务日志字段

- `task_id`
- `provider`
- `operation`
- `status`
- `retry_count`
- `duration_ms`
- `user_id`

### 13.3 典型事件

- `task_submitted`
- `task_poll_started`
- `task_poll_retry`
- `task_completed`
- `task_failed`
- `upload_started`
- `upload_completed`

## 十四、外部依赖调用日志

当前项目外部依赖比较多，这部分日志不能每个地方各写各的。字段要统一。

建议每次调用至少记录：

- `provider`
- `endpoint`
- `operation`
- `status_code`
- `latency_ms`
- `retry_count`
- `error_type`

这里有个边界要守住：

- 只记摘要
- 不记完整响应体
- 错误响应最多截断前几百字符
- 所有敏感字段先脱敏再记录

## 十五、脱敏要求

日志系统必须默认带脱敏，不允许靠开发时自觉。

### 15.1 严禁直接入日志的内容

- `API Key`
- `Access Key`
- `Secret Key`
- `token`
- `cookie`
- `Authorization`
- 原始会话凭证
- 完整本地绝对路径中的敏感目录
- 完整超长 prompt

### 15.2 脱敏规则

- 长 token 只保留前 4 位和后 4 位
- 路径只保留相对路径或文件名
- prompt 只保留长度和摘要
- 第三方响应先截断再过滤敏感字段

### 15.3 统一入口

脱敏逻辑要收口到日志模块里，不要让业务代码自己拼。

## 十六、异常记录要求

异常日志统一用：

- `logger.exception(...)`
- `logger.error(..., extra={...})`

不要继续保留：

- `print(f"...{e}")`

这件事要明确下来，否则后面日志风格会继续发散。

当前优先要替换的异常输出主要集中在：

- 第三方平台调用
- 文件上传和下载
- 轮询任务
- WebSocket 广播
- JSON 文件读写失败

## 十七、实施顺序

这套东西我不建议一次改太多，按四步推进更稳。

### 第一步：搭基础设施

先完成：

- 统一 logging 配置
- JSON 输出
- 文件落盘
- 轮转和保留
- `get_logger(...)`

### 第二步：接请求日志

再补：

- 请求日志中间件
- `request_id`
- 用户上下文
- 耗时和状态码记录

### 第三步：替换核心 `print`

按优先级逐步替换：

- `main.py`
- `app/core/ws.py`
- `app/core/media.py`
- `app/core/auth.py`
- 关键 router / service

### 第四步：补审计和任务日志

最后把：

- `audit.log`
- `task.log`

补齐。

## 十八、第一版先做到什么程度

如果只做第一版，我认为没必要一上来做得太重。先落这几项就够了：

1. 统一 `logging` 配置
2. JSON 行日志
3. `request_id`
4. `access / app / error` 三类日志
5. 脱敏
6. 日志轮转
7. 替换关键路径上的 `print`

这套先跑起来，已经足够把当前项目从“控制台输出”拉到“能排障、能留痕、能控量”的水平。

## 十九、和后续存储方案的关系

后面文件系统迁到 MinIO、元数据迁到 PostgreSQL 以后，日志字段不能重来一次，所以现在就要按后端无关的方式设计。

### 19.1 MinIO 相关

后续要记录：

- 对象上传
- 对象删除
- 预签名 URL 获取
- bucket / object_key 摘要
- 失败原因

### 19.2 PostgreSQL 相关

后续要记录：

- 关键表写入失败
- 慢查询摘要
- 迁移任务状态

### 19.3 S3 迁移相关

如果后面从 MinIO 迁 S3，需要能记录：

- 迁移任务
- 源存储 / 目标存储
- 成功数 / 失败数
- 校验结果

所以现在这套字段命名尽量保持“存储后端无关”，不要把 MinIO 细节写死进日志模型。

## 二十、最终口径

这套日志系统最终要达到的状态很明确：

- 全项目统一 `logging`
- JSON 结构化输出
- 请求链路可追
- 用户维度可追
- 敏感操作单独审计
- 长任务单独留痕
- 日志量可控
- 后续可平滑接日志平台

按当前项目的实际情况，优先级最高的还是三件事：

- 先把 `request_id` 建起来
- 先把 `access.log / app.log / error.log` 跑起来
- 先把关键路径上的 `print` 换掉

这三件事做完，整个系统的可维护性会先上一个台阶。后面的审计、任务、平台对接，再在这个基础上补。
